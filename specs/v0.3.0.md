# OrgTop v0.3.0

**Status:** Draft - Not Implementation-Ready

## Release Intent

OrgTop v0.3.0 adds an Intelligence layer that surfaces activity which is unusual or
consequential rather than merely recent. It turns retained, normalized activity into
historical baselines, deterministic derived signals, and explainable scope rankings
without hiding the underlying evidence.

This release inherits the normative v0.1.0 behavior and assumes completion of the
intended v0.2 boundaries: path-aware scopes, changed-path enrichment, bounded local
persistence, and Rain. v0.3.0 does not weaken v0.1 freshness, security, source
normalization, deterministic ordering, or responsive-TUI requirements. It does not
silently absorb unfinished v0.2 work; missing prerequisite capabilities block the
dependent intelligence feature or produce an explicit unavailable state.

The source-feasible candidate signal set is:

- `ACTIVITY_BURST`;
- `REVIEW_STORM`;
- `LARGE_CHANGE`;
- `STALE_PR_WOKE_UP`;
- `PR_CHURN`.

This Draft does not select which candidates are required for v0.3.0. The revised
implementation-ready contract must select a cohesive initial subset and define each
algorithm. `CI_THRASHING` and `SHIPPING` are conditional because the inherited GitHub
repository-event source does not provide the required CI-run and deployment evidence.
They must not be emitted unless a separately specified source contract supplies that
evidence.

This Draft intentionally leaves algorithm formulas, comparison windows, thresholds,
history retention, and signal lifecycle rules unresolved. The readiness gates below
must be closed by a spec revision before implementation tasks are eligible.

## Terminology

- **Observation:** a normalized Event or enriched entity fact eligible for historical
  analysis after Scope filtering.
- **Intelligence scope:** a repository Scope or path Scope inherited from v0.2 for
  which baselines, scores, and signals are computed.
- **Current window:** the approved interval of recent observations evaluated for a
  metric. Its duration is unresolved in this Draft.
- **Baseline:** a historical, scope-specific, metric-specific expectation computed
  from eligible observations outside the current window using an approved,
  versioned algorithm.
- **Baseline cohort:** the historical observations selected for one baseline,
  including any approved time-of-day, day-of-week, event-kind, repository, path, or
  entity partitioning.
- **Baseline eligibility:** the approved minimum history and data-quality conditions
  required before a baseline may be used for scoring.
- **Insufficient history:** a truthful state in which baseline eligibility is not
  met. It is not equivalent to normal activity or a zero score.
- **Metric:** a deterministic measurement over observations, such as review count,
  event rate, change size, or time since prior activity.
- **Score:** a deterministic, versioned numerical value used to compare current
  activity. A score has documented inputs, units or normalization, and explanation.
- **Derived signal:** a typed, deterministic interpretation of current observations
  and, where required, an eligible baseline.
- **Signal evidence:** the observations, current metric values, baseline values,
  thresholds, and contributions that explain a signal.
- **Signal lifecycle:** the unresolved rules by which a signal opens, updates,
  coalesces, expires, or resolves.
- **Hot Now / Radar:** Overview's ordered list of currently important intelligence
  scopes, with a visible score and primary reason for each rank.
- **Signal Breakdown:** the explanation region showing the measurements and signal
  contributions responsible for a scope's rank.
- **Cluster:** a deterministic presentation grouping of related events and signals;
  it does not replace or mutate source observations.
- **Degraded intelligence:** a state in which current activity may remain available
  but one or more intelligence results are unavailable or incomplete because history,
  enrichment, persistence, or source data is missing, stale, or invalid.

## Functional Requirements

### FR-001 Inherited Release Boundaries

- All applicable v0.1.0 requirements remain in force, including source normalization,
  Scope filtering before aggregation, polling semantics, stale-state honesty,
  responsive input, deterministic behavior, credential safety, and no telemetry.
- Path scopes, changed-path enrichment, local persistence, and Rain are v0.2
  prerequisites. v0.3.0 consumes their specified domain outputs rather than GitHub
  transport payloads or view-specific state.
- Repository scopes remain valid intelligence scopes. Path scopes behave as virtual
  scopes and receive first-class baseline, score, ranking, breakdown, Stream, Rain,
  and Inspect treatment when their enrichment is complete.
- A change may match multiple path scopes under the inherited v0.2 matching rules.
  Each scope's evidence must identify that shared observation without duplicating the
  underlying persisted observation.
- Missing v0.2 prerequisites must be reported as unavailable or degraded. The UI must
  not substitute repository-level results and label them as path-level intelligence.

### FR-002 Historical Observation Store

- OrgTop must retain enough normalized observations and enrichment facts to compute
  approved historical baselines across application restarts.
- Historical records must preserve stable source identity, timestamp, repository,
  matched path scopes, event category, entity identity when available, and only the
  metric inputs required by approved signal definitions.
- Source payloads remain adapter-owned and must not become the historical domain
  contract. Complete raw GitHub payload retention is not required and is prohibited
  by default.
- Ingestion is idempotent by stable observation identity. Replaying the same source
  data must not increase historical counts or alter results.
- History used by a result must exclude observations that fail normalization, Scope
  matching, required enrichment, or the approved quality rules for that metric.
- The retention duration, compaction policy, schema evolution policy, and treatment
  of observations that later change or disappear are unresolved readiness gates.
- Until retention and migration behavior are approved, implementation of the
  historical store and all dependent intelligence is blocked.

### FR-003 Baseline Computation

- Every baseline-backed score or signal must use retained historical observations;
  current-session counts alone must never be labeled a historical baseline.
- Baselines are computed independently for each intelligence scope and metric unless
  an approved algorithm explicitly defines a broader comparison cohort.
- Path-level baselines use observations attributed to that path scope. A repository
  baseline must not be presented as a path baseline.
- Baseline computation must be deterministic for the same ordered observations,
  algorithm version, configuration, and evaluation time.
- Each result must carry or reference its algorithm version, cohort definition,
  observation coverage, baseline value, and evaluation time.
- Current-window observations must not leak into the historical comparison cohort
  unless an approved formula explicitly requires it and documents the consequence.
- Baselines must account honestly for missing intervals, failed polling, incomplete
  path enrichment, and source latency according to approved data-quality rules.
- If baseline eligibility is not met, the state is `INSUFFICIENT HISTORY`; OrgTop
  must not emit a baseline ratio, anomaly claim, normality claim, or synthetic zero.
- The baseline algorithms, cohort rules, eligibility minimums, windows, and update
  cadence are unresolved readiness gates.

### FR-004 Deterministic Explainable Scoring

- Ranking and signal evaluation must use deterministic statistics or heuristics. The
  same eligible input and versioned configuration must produce the same output.
- Every displayed score must have a documented range or unit, ordering direction,
  tie-break rule, and meaning. Bars must represent that documented score and must not
  imply a percentage unless a valid denominator exists.
- A ranked result must expose at least the current metric, historical expectation when
  applicable, comparison or deviation, triggered rule, and the contributions used to
  obtain its score.
- A score must not be presented as an `AI score`, confidence of an AI model, or other
  opaque judgement.
- Missing inputs must not be silently imputed. The result is unavailable, partial, or
  insufficient-history according to approved per-signal data requirements.
- Scores rank engineering activity scopes and signals, never people. Actor data may
  explain collaboration evidence but must not produce person-level productivity,
  quality, performance, or attention rankings.
- Score formulas, normalization, weighting, threshold values, tie-breaking across
  unlike signals, and partial-input policy are unresolved readiness gates.

### FR-005 Candidate Derived Signals

- The implementation-ready v0.3.0 contract must select one or more initial signal
  kinds from the source-feasible candidates after their data requirements,
  algorithms, lifecycle, and validation value are established.
- `ACTIVITY_BURST` identifies an elevated rate of eligible activity for an
  intelligence scope relative to its approved historical baseline.
- `REVIEW_STORM` identifies unusually concentrated pull-request review activity
  relative to its approved baseline and preserves the pull-request and participating
  review evidence.
- `LARGE_CHANGE` identifies a change whose approved size metric is consequential
  relative to an approved comparison. It requires complete size inputs and must not
  estimate missing changed-file or line data.
- `STALE_PR_WOKE_UP` identifies renewed eligible activity on a pull request after an
  approved inactivity condition. Its explanation includes the measured inactive
  duration and the activity that resumed.
- `PR_CHURN` identifies repeated material revision of one pull request under an
  approved change and time definition. It must not equate ordinary iteration with a
  negative quality or productivity judgement.
- Each emitted signal has a stable identity, kind, intelligence scope, subject when
  applicable, first and latest evidence time, score or rank contribution, algorithm
  version, availability state, and Signal evidence.
- Multiple observations for one developing condition must follow an approved signal
  lifecycle rather than creating an unbounded sequence of duplicate signals.
- Signal-specific formulas, windows, thresholds, minimum samples, and lifecycle rules
  and the required initial subset are unresolved readiness gates. The signal names
  above are not permission to guess those decisions in implementation.

### FR-006 Conditional Signals and Source Honesty

- `CI_THRASHING` is unavailable under the inherited repository-event source because
  no normative CI-run source supplies workflow identity, attempts, outcomes, and
  commit association.
- `SHIPPING` is unavailable under the inherited source because no normative release
  or deployment source proves delivery to an environment or supplies merge-to-deploy
  evidence.
- Neither conditional signal may be inferred from push, pull-request, merge, status,
  check-like glyphs, branch names, tags, or elapsed time alone.
- A future spec may enable either signal only after defining source acquisition,
  normalization, freshness, identity, permissions, failure handling, and test
  fixtures. Absence of those sources is not a v0.3.0 implementation failure.
- OrgTop must not display CI, deployment, incident, agent, or shipping claims merely
  because future visual designs contain those categories.

### FR-007 Hot Now / Radar

- Overview includes a `HOT NOW` or `RADAR` region that ranks eligible intelligence
  scopes by the approved deterministic score.
- Each visible row includes the scope, numerical score or meaningful comparison, a
  non-color visual bar or equivalent magnitude encoding, and the primary signal or
  reason for ranking.
- Ordering is score descending with an approved deterministic tie-break. It is not
  alphabetical and is not ordered by actor.
- Repository and path scopes may appear together only when the approved score makes
  their values comparable. Otherwise the UI must separate the cohorts or label the
  distinction.
- Scopes with insufficient history or unavailable required inputs are not assigned a
  normal or zero score. They remain discoverable through an explicit status or a
  clearly separated unranked region.
- Hot Now must remain usable in narrow terminals by removing secondary explanation
  before removing scope identity, score meaning, freshness, or degraded state.

### FR-008 Signal Breakdown

- Overview includes a Signal Breakdown for the selected or highest-ranked scope when
  terminal space permits.
- The breakdown shows why the scope ranks where it does, including signal kind,
  current measurement, expected or comparison value when applicable, deviation or
  rule outcome, and score contribution.
- Users must be able to distinguish measured facts from derived interpretation.
- The breakdown must identify unavailable inputs, incomplete path enrichment, stale
  history, and insufficient history rather than omitting those limitations.
- Color and bar length may reinforce meaning but may not be the only explanation.
- On constrained terminals, the breakdown may collapse before Hot Now, but Inspect
  must provide the complete available explanation for a selected ranked item.

### FR-009 Signal-Ranked Rain Strip

- Rain retains the ambient activity field inherited from v0.2 and adds a bounded,
  readable signal strip ranked by the same approved intelligence semantics as
  Overview.
- The strip contains only current eligible signals and includes scope or subject,
  signal kind, concise evidence, score or comparison, and recency.
- Rain density is not itself an anomaly score. Glyph frequency, animation, or visual
  emphasis must not create an intelligence claim without an evaluated signal.
- The strip and Hot Now must produce consistent ordering for the same eligible signal
  cohort and evaluation time, subject to documented view capacity.
- When intelligence is unavailable, Rain may continue to show direct activity but
  the strip must say that signals are unavailable, degraded, or awaiting history. It
  must not fall back to unlabeled heuristics.
- Deterministic paging or truncation is required when the strip cannot fit; freshness
  and degraded-state context remain visible.

### FR-010 Clustered Stream

- Stream may replace repetitive visible event rows with deterministic multi-line
  clusters that summarize a derived signal or one coherent activity sequence.
- A cluster identifies signal kind or activity type, scope and subject, time span,
  event count, concise explanation, and the comparison responsible for significance
  when available.
- Cluster membership is based on approved keys, time rules, and signal lifecycle.
  The same ordered inputs and configuration must produce the same clusters.
- Observations must not disappear semantically: Inspect exposes cluster evidence, and
  counts and time ranges make aggregation apparent.
- Unrelated scopes, pull requests, or signal kinds must not be merged merely to reduce
  row count.
- Events that are not eligible for a cluster remain visible under inherited Stream
  behavior. Insufficient history does not hide raw activity.
- Cluster keys, temporal boundaries, update behavior, and interaction with resolved
  signals are unresolved readiness gates.

### FR-011 Context-Preserving Inspect

- `enter` opens Inspect for the selected Hot Now row, Signal Breakdown entry, Rain
  strip item, Stream cluster, or eligible underlying event.
- Inspect is a contextual drilldown, not a fourth primary view. It overlays or
  temporarily replaces content while retaining the originating view's state.
- Inspect shows the signal kind and status, scope and subject, current metrics,
  baseline or comparison, score contributions, algorithm version, evidence timeline,
  relevant path scopes, data limitations, and source links when safely available.
- Closing Inspect with `esc` returns to the same originating view, selection, scroll
  position, active Scope/filter, and Rain position or page. Data refresh may update
  values but must not reset unrelated navigation context.
- If the inspected signal changes or expires during refresh, Inspect displays that
  lifecycle state and retained evidence according to the approved lifecycle policy;
  it must not silently switch to another item.
- Inspect must distinguish source facts, enrichment, baseline values, and derived
  conclusions.

### FR-012 Path-Level Intelligence

- Every required signal is evaluated for path scopes when its required observations
  can be completely and unambiguously attributed under v0.2 rules.
- Path-level current metrics are compared with path-level historical cohorts, not
  repository-wide history presented under a path label.
- Repository and path signals may coexist for the same observation. Their evidence
  must identify the applicable scopes and avoid implying independent source events.
- If changed-path enrichment is incomplete for a current or historical cohort, the
  affected path result is degraded or unavailable according to approved quality
  rules. Repository-level intelligence may remain available when valid.
- Overview, Signal Breakdown, Rain, Stream, and Inspect use one consistent path Scope
  identity and make path-level anomalies visible even when repository-level activity
  is not unusual.

### FR-013 Insufficient-History and Degraded Behavior

- Startup and all primary views expose whether intelligence is ready, building
  history, insufficient, stale, partially degraded, or unavailable.
- `INSUFFICIENT HISTORY` includes useful progress evidence defined by the approved
  eligibility policy, without predicting a ready time that cannot be guaranteed.
- A failed current refresh preserves the last complete activity snapshot under the
  inherited `STALE` semantics. Intelligence computed from stale or incomplete data
  must also be marked stale and must not look current.
- Persistence failure, corrupt history, algorithm-version incompatibility, missing
  enrichment, and missing required source fields produce sanitized, actionable
  degraded states. They do not become a normal score.
- One unavailable signal kind does not suppress valid independent signals. The UI
  identifies per-signal availability and the overall intelligence state.
- Rebuilding or migrating history must not block keyboard, resize, view navigation,
  Inspect close, or clean exit.
- OrgTop must describe the inherited source as `POLLING`, never `LIVE`. v0.3.0 does
  not add webhooks, a collector, or a real-time transport.

### FR-014 Configuration and Version Visibility

- The active algorithm/configuration version is available in help or Inspect and is
  attached to persisted derived results where needed for reproducibility.
- Changing a formula, threshold, cohort rule, window, or lifecycle rule requires a
  version change and an approved policy for existing history and open signals.
- User-facing configuration, if approved, validates before use and cannot select an
  internally inconsistent combination of windows or thresholds.
- OrgTop must not expose arbitrary score weights or thresholds until their semantics,
  validation, migration, and support expectations are specified.

## Non-Functional Requirements

### NFR-001 Determinism and Reproducibility

- Baseline, score, signal, ranking, and cluster tests use a controllable clock and
  deterministic fixture history.
- Evaluation does not depend on map iteration, wall-clock reads hidden inside domain
  functions, network ordering, locale, terminal color support, or random values.
- A fixture replay records enough algorithm and configuration metadata to explain any
  changed result across versions.

### NFR-002 Responsiveness and Resource Bounds

- Historical loading, migration, baseline computation, scoring, and clustering run
  outside rendering and input handling and support cancellation where work may be
  long-running.
- Evaluation and storage are bounded by approved retention, current-window, query,
  and displayed-result limits. Those limits must be specified before implementation.
- The TUI remains responsive while intelligence is unavailable, rebuilding, or
  degraded and continues to provide inherited direct-activity views where possible.

### NFR-003 Explainability and Accessibility

- Every ranking has a text and numeric explanation available without relying on
  color, animation, or an undocumented glyph.
- Normal operation is visually calm; emphasis identifies a documented signal state
  rather than decorative urgency.
- Rendered language uses `observed`, `expected`, `compared with`, or similarly precise
  terms and avoids anthropomorphic or predictive AI language.

### NFR-004 Security and Privacy

- Historical storage contains only data needed for specified intelligence behavior,
  is local by default, and never contains authentication tokens or authorization
  headers.
- OrgTop sends no activity, baseline, score, signal, or actor data to an LLM,
  third-party analytics service, or OrgTop-operated collector.
- Actor evidence is displayed only to explain source activity; it is not transformed
  into person-level rankings or persisted beyond the approved intelligence need.
- Storage location, retained fields, retention behavior, and deletion controls must be
  documented before release.

### NFR-005 Architecture and Maintainability

- Source acquisition and normalization, history persistence, baseline calculation,
  signal evaluation, application state, and TUI rendering remain distinct current
  responsibilities.
- Domain intelligence functions do not import GitHub adapter, persistence driver,
  Bubble Tea, or Lip Gloss types.
- Views render precomputed explanations and do not calculate baselines, thresholds,
  scores, signal lifecycle, or cluster membership.
- No generic machine-learning, plugin, collector, or distributed-processing framework
  is introduced for this release.

### NFR-006 Verification Quality

- Tests cover historical deduplication, cohort selection, current-window exclusion,
  baseline eligibility, deterministic scoring, tie-breaking, all selected signal
  kinds, lifecycle transitions, path attribution, and degraded inputs.
- TUI tests cover Hot Now, Signal Breakdown, Rain strip consistency, clustered Stream,
  Inspect context restoration, insufficient history, stale intelligence, partial
  signal availability, narrow terminals, and resize.
- Conditional signals have negative tests proving they are not inferred without their
  required source contracts.
- Ordinary tests use synthetic fixtures and do not contact live GitHub, require user
  credentials, or contain private organization activity.
- The repository's full local quality gate must pass before release.

## Acceptance Scenarios

### A-001 Historical Baseline Becomes Eligible

Given synthetic retained observations that satisfy the approved eligibility and
cohort rules, evaluating a repository metric produces a versioned baseline with the
expected cohort coverage. Replaying the same observations produces the identical
baseline and does not duplicate history.

### A-002 Insufficient History Is Not Normal

Given a newly observed scope that does not satisfy baseline eligibility, Overview
shows `INSUFFICIENT HISTORY` or equivalent and provides no `normal`, anomaly, ratio,
or zero-score claim. Stream and Rain may continue to show direct activity.

### A-003 Deterministic Hot Now Ranking

Given approved fixture inputs that produce multiple eligible scope scores, Hot Now
orders them by the approved score and tie-break rule. Each row shows its numerical
meaning and primary reason, and the same replay produces the same ordering.

### A-004 Explainable Selected Signals

For every signal selected by the implementation-ready contract, a fixture satisfying
the approved rule emits the typed signal, while a boundary fixture that does not
satisfy it emits none. Inspect and Signal Breakdown identify the exact evidence,
comparison, threshold, and algorithm version used. Unselected candidates are not
emitted merely because their names appear in this Draft.

### A-005 No Guessing for Missing Inputs

Given incomplete changed-file data for a potential `LARGE_CHANGE` or incomplete path
enrichment for a path scope, OrgTop marks the affected result unavailable or degraded
and does not estimate a size, path baseline, or signal.

### A-006 Path-Level Anomaly

Given a monorepo whose repository-level metric is within its approved baseline but
whose `services/payments/**` scope satisfies an approved signal rule, Hot Now ranks
and labels the path scope independently. Its breakdown uses path history and Inspect
shows the matching changed-path evidence.

### A-007 Signal-Ranked Rain Consistency

Given more current eligible signals than Rain can display, its strip selects and
orders a deterministic bounded subset consistent with Hot Now for the same evaluation
time. The ambient field remains direct activity visualization and is not labeled an
anomaly score.

### A-008 Clustered Stream Evidence

Given repetitive observations belonging to one approved cluster, Stream renders one
multi-line summary with count, time range, scope, subject, and explanation. Inspect
reveals the member evidence. An unrelated event remains a separate Stream item.

### A-009 Inspect Preserves Context

Given a selected Hot Now row after scrolling Overview, opening Inspect and then
closing it returns to the same view, selection, scroll position, Scope/filter, and
freshness context. If the signal changed while open, Inspect reports that state and
does not select another signal.

### A-010 Degraded History and Recovery

Given valid current activity but unavailable or corrupt historical storage, the TUI
remains responsive, marks intelligence degraded, and does not show stale scores as
current. After a successful approved recovery, eligible intelligence reappears
without duplicating observations.

### A-011 Stale Polling Remains Honest

After a successful evaluation, a failed GitHub refresh retains the prior snapshot and
marks activity and dependent intelligence `STALE` with last-success context. No view
uses `LIVE`, and a later complete refresh clears stale state and reevaluates results.

### A-012 Conditional Signals Stay Unavailable

Given repository events containing merges, pushes, branch names, or check-like text
but no specified CI or deployment source, OrgTop emits neither `CI_THRASHING` nor
`SHIPPING` and makes no CI-success, deployment, or shipping claim.

### A-013 No Person Ranking or Opaque AI Score

Given activity involving multiple actors, explanations may state observed review or
collaboration facts, but no view orders or scores actors. Rendered output contains no
opaque `AI score`, productivity score, or performance judgement.

### A-014 Narrow Terminal and Asynchronous Evaluation

At the inherited minimum supported terminal size, active view, `POLLING`/freshness,
scope or signal identity, score meaning or unavailable state, and quit navigation
remain readable. Slow baseline evaluation does not block navigation, resize, Inspect
close, or exit.

## Explicit Non-Goals

v0.3.0 does not include:

- an LLM dependency, model-provider integration, embeddings, generated summaries, or
  opaque machine-learning scores;
- person-level productivity, performance, quality, contribution, reviewer, or actor
  ranking;
- webhooks, a daemon, central collector, shared baseline service, event stream, or
  claims of real-time or `LIVE` behavior;
- mandatory `CI_THRASHING` or `SHIPPING` without separately specified CI and
  deployment sources;
- incident, coding-agent, external CI, deployment, or other engineering-system data
  sources;
- forecasting, causal claims, recommendations, automatic remediation, or notification
  delivery;
- organization-to-organization comparison or global cross-customer baselines;
- a generic anomaly-detection platform, user-authored rule language, arbitrary score
  scripting, or plugin framework;
- silent estimation of missing changed paths, change size, review history, CI state,
  or deployment state;
- replacing raw activity access with clusters or hiding evidence behind a score;
- final algorithm, window, threshold, retention, or lifecycle values in this Draft.

## Open Decisions and Readiness Gates

This specification is not implementation-ready. Every gate below requires an
explicit normative spec revision, deterministic fixtures, and acceptance boundaries
before dependent implementation work starts.

### RG-001 Observation and Retention Contract

Define retained fields, storage limits, retention duration, deletion behavior,
compaction, schema migration, corrupt-store recovery, and treatment of source updates
or deletions. Confirm that the resulting privacy and disk-use contract is acceptable.

### RG-002 Time and Cohort Semantics

Define current windows, baseline windows, timezone behavior, clock-skew handling,
source-latency treatment, cohort partitioning, missing intervals, and exclusion of
current observations from historical comparisons.

### RG-003 Baseline Eligibility

Define minimum history, minimum samples, coverage quality, enrichment completeness,
and transition rules among building, eligible, insufficient, stale, and degraded
states for every metric and scope type.

### RG-004 Scoring and Ranking

Select formulas, units or ranges, normalization, contribution combination,
cross-signal comparability, partial-input policy, deterministic tie-breaks, and
versioning. Supply fixtures that establish exact expected values and boundaries.

### RG-005 Required Signal Definitions

For each selected initial signal, define required observations, subject identity,
metric formula, baseline dependency, windows, thresholds, minimum samples, evidence,
and negative boundaries. Confirm that inherited sources can supply complete inputs.

### RG-006 Signal Lifecycle

Define stable identity, opening, updating, coalescing, escalation, expiry, resolution,
reopening, retained evidence, and behavior across restart and algorithm-version
changes.

### RG-007 Stream Clustering

Define cluster keys, temporal boundaries, maximum size, ordering, update behavior,
relationship to signal lifecycle, and how users inspect member evidence.

### RG-008 UI Capacity and Interaction

Define Hot Now and Rain strip capacities, score-bar scaling, unlike-cohort treatment,
selection behavior during refresh, Inspect layout, narrow-terminal priorities, and
the exact representation of partial and insufficient intelligence.

### RG-009 Path Data Quality

Approve completeness rules for historical and current path attribution, overlapping
path scopes, renames, deleted files, unmatched events, and repository-level fallback.
No fallback may be labeled path-level intelligence.

### RG-010 Conditional Source Contracts

Keep `CI_THRASHING` and `SHIPPING` disabled unless future normative source contracts
define acquisition, normalization, identity, permissions, freshness, failure modes,
and fixtures for CI runs and deployments. Decide separately whether either signal
belongs in v0.3.0 after those contracts exist.

### RG-011 Performance and Storage Budgets

Set measurable startup, evaluation, refresh, memory, disk, and migration budgets
using representative repository and monorepo histories. Confirm that local-only
operation remains viable within those bounds.

### RG-012 Release Readiness

Revise status from Draft only after v0.2 prerequisites are normative and complete,
all gates required by selected features are closed, docs describe retained data and
limitations, fixture-based acceptance tests are concrete, and the repository quality
gate passes.

## Potential Features

Taskrail requires `###` headings in this section as coverable decomposition areas.
These areas describe intended v0.3.0 work, but no implementation task is eligible
while its applicable readiness gates remain open.

### Historical Observation Persistence

Retain the minimum normalized and enriched history needed for reproducible local
intelligence, with idempotent ingestion, bounded storage, migrations, and recovery.

### Baseline Engine

Compute scope-specific and path-specific historical expectations with explicit
eligibility, cohort, coverage, algorithm-version, and degraded-state semantics.

### Explainable Score and Ranking Engine

Evaluate deterministic metrics and contributions, rank comparable scopes, and expose
the numerical evidence behind every result.

### Initial Derived Signals

Implement the approved initial subset of source-feasible signals after their data
requirements, algorithms, lifecycle, and acceptance boundaries are specified.

### Intelligence Availability Lifecycle

Represent building-history, eligible, insufficient-history, partial, stale,
unavailable, and recovery transitions without converting missing data into normality.

### Hot Now and Signal Breakdown

Add Overview ranking and explanations that remain consistent, accessible, responsive,
and explicit about path scope and data quality.

### Signal-Ranked Rain Strip

Rank a bounded set of current signals in Rain while preserving direct-event ambient
semantics and honest unavailable behavior.

### Clustered Stream

Group repetitive related activity into deterministic narrative entries while keeping
underlying evidence inspectable and unrelated activity visible.

### Context-Preserving Inspect

Provide detailed evidence and algorithm context from Overview, Stream, and Rain, then
return users to the exact originating interaction context.

### Path-Level Intelligence

Apply baselines, required signals, ranking, breakdown, clustering, and inspection to
v0.2 path scopes without substituting repository-level history.

### Intelligence Verification and Documentation

Build deterministic historical fixtures and boundary tests, verify negative safety
properties, document local retention and interpretation, and pass release gates.

## Implementation Notes (Informative)

- A pure evaluation boundary accepting observations, an explicit evaluation time,
  and versioned configuration is likely to make determinism straightforward.
- Persist observations rather than rendered scores where practical; cache derived
  values only when invalidation and algorithm-version behavior are defined.
- SQLite may remain the local implementation inherited from v0.2, but this Draft does
  not prescribe schema, indexes, retention jobs, or migration tooling.
- Explanations are better modeled as typed domain output than reconstructed from
  formatted strings in each view.
- Synthetic fixture generators may help exercise long histories, but checked-in
  boundary fixtures should remain reviewable and deterministic.
- The selected signal names describe product outcomes, not implementation packages.
  Add packages only when a current responsibility justifies them.
- No readiness gate should be closed solely by choosing a conventional-looking
  number. Decisions need product rationale, data feasibility, and boundary fixtures.
