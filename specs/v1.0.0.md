# OrgTop v1.0.0

## Status

**Status:** Draft

This document is a non-normative validation and product-vision contract. It is not
an implementation contract, is not active for delivery, and does not authorize any
v1.0.0 behavior, architecture, source integration, or task decomposition.

No implementation task should reference this spec before it is revised with
validated evidence, converted into a normative implementation contract, and
explicitly activated through the repository's supported Taskrail workflow.

## Release Intent

OrgTop v1.0.0 may graduate from GitHub activity awareness to engineering-system
activity awareness. Its candidate purpose is to help a user answer:

> What is happening across the engineering system now, how are related activities
> connected, and what deserves investigation?

The candidate release should preserve OrgTop's terminal-native, calm,
information-dense operating model. Overview remains the operating picture, Stream
supports investigation, and any ambient view remains secondary to understandable
information.

The long-term opportunity includes activity from source control, CI, deployments,
incidents, and coding agents. That list is a discovery space, not a promise that
v1.0.0 will integrate every source. The actual release scope must be re-specified
from validated usage of earlier releases and source-specific research. It must not
be produced by mechanically implementing the roadmap or every candidate in this
draft.

## Draft Authority and Activation Rule

This draft has authority only to:

- preserve the v1.0.0 product hypothesis and its safety boundaries;
- identify questions that validation must answer;
- define evidence expected before implementation scope is selected;
- prevent speculative roadmap work from being treated as committed behavior.

This draft does not define functional requirements, implementation acceptance
criteria, required packages, source adapters, storage, protocols, or deployment
topology. Terms such as `should`, `may`, and `candidate` express hypotheses unless
this document explicitly states a prohibition.

Activation requires all of the following:

1. Evidence from real OrgTop usage is summarized in the revised spec.
2. Selected user problems and target users are stated more narrowly than the full
   candidate vision.
3. Selected sources, source coverage, data limits, and freshness semantics are
   explicit.
4. Identity, correlation, authorization, privacy, retention, and metric semantics
   are resolved for the selected scope.
5. Measurable release success criteria and normative acceptance scenarios replace
   this draft's validation scenarios.
6. Collector and infrastructure choices, if any, are justified by measured needs.
7. The revised document is explicitly marked normative for implementation and is
   activated through Taskrail.

Until those conditions are met, decomposition may cover research and specification
work only. It must not create implementation work anchored to this draft.

## Terminology

- **Source:** An engineering system that provides observations, such as source
  control, CI, a deployment system, an incident system, or a coding-agent system.
- **Source event:** A source-owned payload or record before OrgTop normalization.
- **Normalized event:** A source-independent OrgTop occurrence with explicit source,
  time, subject, actor, entity, scope, and provenance semantics where available.
- **Actor:** The identity responsible for or associated with an event. An actor may
  be classified as `human`, `agent`, `automation`, or `unknown` without implying
  productivity or intent.
- **Entity:** A source object involved in activity, such as a change, pull request,
  workflow run, build, artifact, deployment, service, incident, or agent task.
- **Scope:** The engineering boundary a user observes. Its future shape may include
  repositories, paths, services, environments, teams, or another validated unit.
- **Identity resolution:** Evidence-based mapping of source-specific actor, entity,
  repository, service, environment, and organization identifiers into stable
  identities. Similar display names are not sufficient evidence.
- **Correlation:** An explainable relationship between events supported by explicit
  identifiers or documented source semantics.
- **Causality:** A stronger claim that one activity produced or materially led to
  another. Temporal proximity alone does not establish causality.
- **Derived signal:** A reproducible interpretation of one or more normalized events
  that includes its inputs, rule, confidence or limitations, and explanation.
- **Operational aggregate:** A group-level situational-awareness measure. It is not
  an individual performance or productivity measure.
- **Mature Overview block:** A source-backed organization-level summary such as
  CODE, REVIEWS, CI, DEPLOYS, INCIDENTS, or AGENTS whose population, denominator,
  freshness, and missing-data behavior are defined.
- **Collector:** A possible shared component for receiving, normalizing, enriching,
  correlating, retaining, and serving events. Its existence and topology are not
  assumed by this draft.

## Candidate Functional Outcomes

The revised v1.0.0 contract may select a strict subset of these outcomes when
validation supports them:

- Combine useful activity from GitHub and one or more additional source classes,
  potentially CI, deployments, incidents, or coding agents.
- Normalize selected sources into events without leaking source transport payloads
  into domain aggregation or TUI models.
- Represent source provenance, observed time, source time, actor classification,
  entities, scopes, and source-specific identifiers without inventing unavailable
  facts.
- Resolve cross-source identities only where stable mappings or configured
  relationships exist, and preserve unresolved or ambiguous identity explicitly.
- Correlate events through evidence such as commit SHA, change or pull-request ID,
  workflow run, artifact digest, deployment record, service/environment identity,
  incident link, traceable agent task, or another documented join key.
- Distinguish correlation from causality and expose the evidence used for either.
- Show source health, coverage, freshness, permissions, partial failure, and missing
  data so a partial operating picture cannot be mistaken for a complete one.
- Add mature Overview blocks only when the selected sources reliably support them.
  A block must not appear merely because it exists in a future-state mockup.
- Present aggregate `human`, `agent`, `automation`, and `unknown` activity when
  classification quality, privacy review, and operational usefulness are validated.
- Surface explainable cross-source signals, potentially including change-to-build,
  build-to-deploy, deploy-to-incident, incident-to-change, or agent-to-change
  relationships.
- Allow a user to move from an aggregate or signal to the normalized events,
  relationships, and source references that explain it.
- Preserve a coherent Overview and Stream when only some selected sources are
  configured, authorized, current, or available.

Candidate cross-source signals must be phrased according to available evidence. For
example, a `SHIPPED` signal may be appropriate only if a merged change can be joined
to a successful build artifact and an authoritative deployment record for a defined
environment. A merge followed by an unrelated deployment in the same time window is
not enough.

## Non-Functional Guardrails

- Source coverage and freshness must be honest and visible. `LIVE`, `POLLING`,
  `STALE`, delayed, partial, and unavailable states are not interchangeable.
- Absent, unauthorized, filtered, delayed, unsupported, or failed source data must
  remain unknown or unavailable. It must never be silently represented as zero.
- Metrics must document unit, population, time window, denominator, aggregation,
  source coverage, missing-data treatment, and update latency.
- Cross-source joins and signals must be deterministic and explainable by default.
  Opaque AI-generated scores, narratives, or causal claims are prohibited.
- A signal must retain enough provenance for a user to inspect the contributing
  events and understand why it appeared.
- Person-level rankings, productivity scores, comparative leaderboards, and proxy
  measures of individual performance are prohibited.
- Aggregate human, agent, and automation classifications must remain operational,
  privacy-reviewed, and robust to `unknown`; they must not become surveillance.
- Tokens, source credentials, sensitive payloads, private code metadata, incident
  details, and actor identity mappings require least-privilege access and explicit
  handling rules.
- Telemetry or third-party transmission of organization activity must not be enabled
  by default. Any shared service requires a dedicated security and privacy design.
- Partial failures must not corrupt a previously coherent view or present mixed-age
  data without visible source-level freshness.
- Network, processing, and enrichment work must not block terminal interaction.
- Retention, cardinality, API usage, and resource bounds must be selected from the
  validated product scope rather than unlimited ingestion assumptions.
- Source-specific transport models remain inside source boundaries. Normalization,
  identity resolution, correlation, aggregation, application state, and rendering
  remain distinct responsibilities.
- A generic plugin framework is prohibited unless multiple selected, implemented
  sources demonstrate concrete extension requirements that simpler adapters cannot
  meet.
- No database, queue, daemon, webhook service, cloud service, Kafka, PostgreSQL,
  Kubernetes, WebSocket, SSE, gRPC, or other infrastructure is implied by v1.0.0.
  Technology choices must follow measured volume, latency, retention, fan-out,
  reliability, and operating constraints.

## Validation Scenarios (Not Implementation Acceptance Until Revised)

These scenarios guide product discovery. They are not implementation acceptance
criteria and must not be copied into implementation tasks before revision and
activation.

### V-001 Cross-Source Investigation Value

Given representative activity from a validated set of source-control and additional
engineering sources, a target user can identify an important current situation and
explain it faster or with less context switching than by visiting each source UI.
Research records which source combination provided the value and which data was
noise.

### V-002 Incomplete Source Coverage

Given one configured source that is current, one that is stale, and one that is not
authorized, a user correctly understands the limits of every aggregate and does not
interpret absent data as no activity.

### V-003 Identity Ambiguity

Given actor or entity identifiers that cannot be reliably mapped across sources,
OrgTop preserves separate or `unknown` identities and communicates uncertainty. It
does not merge identities based only on display name, email similarity, or timing.

### V-004 Evidence-Based Correlation

Given a change, CI run, artifact, and deployment with explicit join keys, a user can
inspect the relationship and its provenance. Removing the join keys prevents the
same causal claim even if timestamps remain close.

### V-005 Mature Overview Eligibility

Given candidate CODE, REVIEWS, CI, DEPLOYS, INCIDENTS, and AGENTS blocks, user
research and source audits identify which blocks answer recurring operational
questions. Only blocks with adequate data, definitions, coverage indicators, and
validated usefulness remain candidates for the activated contract.

### V-006 Actor Classification Safety

Given human, agent, automation, and ambiguous activity, classification supports a
useful aggregate operating picture while retaining `unknown`. Users cannot derive a
person ranking or unsupported productivity conclusion from the presentation.

### V-007 Explainable Signal

Given a candidate cross-source signal, a user can inspect its source events, join
keys, time bounds, calculation, and limitations. If the user cannot explain why the
signal appeared, the signal is not ready for the implementation contract.

### V-008 Authorization and Privacy Boundary

Given sources with different permissions and sensitivity, research establishes the
minimum permissions, redaction, retention, local/shared processing, and audit needs.
No credential or inaccessible source detail leaks through aggregates or errors.

### V-009 Operational Shape

Given measured event volume, latency, enrichment, retention, and fan-out needs,
research determines whether local acquisition remains sufficient or a collector is
necessary. A distributed architecture is not considered validated merely because it
could support future scale.

### V-010 Product Success Evidence

In sustained use, target users return to the multi-source operating picture, follow
signals into investigation, and report decisions or understanding improved by
cross-source context. Novelty, animation, event throughput, and number of connectors
alone do not count as success.

## Explicit Non-Goals

This draft does not authorize or require:

- integrating every candidate source or every vendor in a source category;
- a generic source/plugin marketplace or public plugin framework;
- an opaque AI assistant, LLM event summarizer, unexplained score, or generated
  causal narrative;
- person-level activity rankings, productivity scores, performance assessment,
  surveillance, or employee comparison;
- treating missing, delayed, unauthorized, unsupported, or failed data as zero;
- correlating events solely because they occurred near each other in time;
- assuming a collector, hosted service, daemon, webhook topology, database, queue,
  stream processor, or orchestration platform;
- deployment orchestration, incident response management, CI execution, code review,
  project management, or mutation of source systems;
- a compliance archive or authoritative audit log;
- displaying mature Overview blocks without reliable backing data and documented
  metric semantics;
- preserving roadmap labels or mockup metrics when validation recommends a different
  product scope;
- implementation tasks that reference this draft before revision and activation.

## Open Decisions and Readiness Gates

Every gate below must be resolved in the revised normative contract for the selected
scope. A decision may deliberately exclude a candidate capability.

### Source Choice Gate

- Which user problem requires a second or later source?
- Which source categories and specific providers are in scope?
- What event coverage, history, latency, ordering, duplication, and outage behavior
  does each source actually provide?
- Is each source's marginal value greater than its setup and noise cost?

### Identity and Causality Gate

- What stable actor, entity, service, environment, change, artifact, and execution
  identifiers exist?
- Which mappings are authoritative, configured, inferred, ambiguous, or forbidden?
- Which relationships are correlations and which may support causal language?
- How are remapping, deletion, collisions, and `unknown` represented?

### Authentication and Authorization Gate

- Is acquisition local, shared, or hybrid for each source?
- What minimum scopes and organization approvals are required?
- How are credentials obtained, isolated, rotated, revoked, and prevented from
  entering logs or persisted events?
- How does the UI distinguish lack of permission from zero activity?

### Privacy and Governance Gate

- Which event fields and actor identities are necessary for the validated outcome?
- What is redacted, retained, exported, or processed centrally?
- What controls apply to private code, incidents, environments, and agent prompts or
  outputs?
- Has the aggregate human/agent/automation presentation been reviewed for misuse and
  re-identification risk?

### Metric Semantics Gate

- What question does each metric or Overview block answer?
- What are its population, denominator, window, units, baseline, coverage threshold,
  missing-data semantics, and freshness requirements?
- Can a user inspect the inputs and avoid interpreting activity as productivity?
- Under what conditions is the metric hidden or marked unavailable?

### Success Criteria Gate

- Which target users and recurring workflows define v1.0.0 success?
- What observed behavior or measured outcome demonstrates improved situational
  awareness or investigation?
- What false-positive, trust, setup-cost, performance, and reliability thresholds
  are acceptable?
- What evidence would cause a candidate source, signal, or block to be dropped?

### Collector Evolution Gate

- Do measured freshness, API duplication, shared baseline, retention, fan-out, or
  governance needs require a collector?
- Which responsibilities must be shared and which should remain local?
- What threat model, tenancy, failure isolation, operating ownership, and migration
  path apply?
- Can the requirement be met without introducing shared infrastructure?

## Potential Features

The `###` areas below are discovery and future-contract areas only. They make the
validation surface visible; they do not make implementation work eligible.

### Validated Source Portfolio

Discover the smallest source combination that materially improves the operating
picture. Candidate additions include CI systems, deployment systems, incident
systems, and coding-agent systems, but no category or provider is assumed.

### Cross-Source Event Contract

Define source-independent event semantics, provenance, source and observed times,
entities, scopes, lifecycle states, deduplication, ordering, correction, and missing
fields for only the selected sources.

### Identity and Actor Classification

Validate stable cross-source identity mappings and safe aggregate classifications
for humans, agents, automation, and unknown actors without ranking people or
asserting intent from weak evidence.

### Correlation and Causality Evidence

Identify authoritative join keys and relationship types for changes, builds,
artifacts, deployments, incidents, and agent tasks. Specify explainable uncertainty
and prohibit temporal-only causal inference.

### Source-Backed Overview

Validate which mature blocks, potentially CODE, REVIEWS, CI, DEPLOYS, INCIDENTS, and
AGENTS, answer real questions. Define their data eligibility, units, coverage,
freshness, absent-data behavior, and drilldown before contracting their display.

### Aggregate Human, Agent, and Automation Activity

Test whether organization-level classifications improve awareness, how `unknown` is
handled, and what presentation prevents individual comparison or surveillance.

### Explainable Cross-Source Signals

Evaluate deterministic signals whose contributing events, joins, calculations, and
limitations can be inspected. Candidate relationships include change-to-CI,
CI-to-deploy, deploy-to-incident, and agent-to-change, subject to source evidence.

### Authorization, Privacy, and Governance

Determine least-privilege access, credential boundaries, redaction, retention,
export, local-versus-shared processing, and source-level visibility for the selected
portfolio.

### Collector and Delivery Evolution

Measure whether a collector is needed and, only if it is, specify its current
responsibilities and operational constraints without defaulting to a generic data
platform.

### Validation Evidence and Release Contract

Synthesize usage research, source audits, prototypes, safety review, metric
definitions, and measurable success criteria into a narrower normative v1.0.0 spec
that can be activated for implementation.

## Implementation Notes (Informative)

- The existing source-to-normalization-to-scope-to-aggregation-to-application-to-TUI
  flow is a useful conceptual boundary, not proof that its current types fit every
  future source.
- Prefer one or two concrete source integrations over a generic plugin abstraction.
  Extract common contracts only after real integrations establish common behavior.
- Preserve source-native identifiers and provenance alongside normalized identities;
  normalization should not erase evidence needed for explanation or correction.
- Model unknown and unavailable states explicitly. Numeric APIs and renderers should
  not force unknown values into zero-valued fields.
- Correlation may be represented as typed edges with evidence rather than flattening
  all activity into a single synthetic event. The normative spec should choose the
  smallest model required by validated scenarios.
- Deterministic rules and statistics are the default for signals. Any future AI use
  would require a separate, explicit contract covering data handling,
  reproducibility, explanation, failure behavior, and user value.
- A local, shared, or hybrid acquisition model may be valid. Do not select one until
  source APIs, authorization, privacy, freshness, and measured scale are known.
- Existing Go, Bubble Tea, and Lip Gloss choices may remain appropriate for the
  terminal client. They do not decide collector language, storage, transport, or
  deployment architecture.
- Revision should delete unsupported candidates rather than carrying every roadmap
  item forward for compatibility with this draft.
