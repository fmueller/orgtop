# OrgTop v0.2.0

**Status:** Implementation-Ready

## Release Intent

OrgTop v0.2.0 extends the shipped v0.1 repository activity model so large
monorepositories can be observed as meaningful path-based components. Repository
and path selections become one Scope model, changed-file enrichment supplies the
evidence needed for path membership, and bounded local SQLite caching limits
repeated enrichment work.

Given valid existing GitHub credentials, a user will be able to select ordinary
repositories, monorepo path scopes, and whole GitHub organizations in one
invocation. RG-001 through RG-012 are closed normative contracts and form the
implementation baseline for the tracked v0.2.0 tasks.

The existing Overview and Stream consume the same scoped event set, and path scopes
appear as first-class rows and labels rather than as an unrelated filter mode. A
third primary view, Rain, provides a compact ambient representation of the same
directly observable activity plus a bounded `Interesting Now` strip.

This release remains a local, GitHub-polling situational-awareness tool. It does not
claim real-time delivery, anomaly detection, historical normality, productivity, or
support for sources other than the shipped GitHub repository activity source.

This contract is implementation-ready. Product behavior remains delivered only by
eligible Taskrail implementation tasks and their required verification.

## Terminology

- **Repository identifier:** the exact GitHub `owner/repository` identity retained
  from v0.1.0.
- **Repository scope:** a Scope selecting all eligible activity for one repository.
- **Path scope:** a Scope selecting eligible activity in one repository whose known
  changed-file set matches the scope's path matcher.
- **Scope:** a source-independent selection unit with a repository identity and,
  optionally, a path matcher. Repository scopes and path scopes use the same domain,
  filtering, aggregation, application-state, and rendering pipeline.
- **Scope set:** the validated, deduplicated set of configured Scopes.
- **Scope identity:** the stable identity used to deduplicate, aggregate, label, and
  retain view state for a Scope. It is distinct from the repository/entity evidence
  identity used to coalesce enrichment and key the SQLite cache. Its exact canonical
  representation is closed under RG-002.
- **Virtual repository:** the presentation of a path scope alongside repository
  scopes in Overview, Stream context, and Rain. It remains a Scope and is not
  represented as a synthetic GitHub repository.
- **Organization selector:** a selection input naming a GitHub organization rather
  than one repository. It is not a Scope. It is expanded into repository Scopes
  before filtering, aggregation, or rendering.
- **Expansion:** the bounded listing that turns an organization selector into a
  concrete, ordered set of repository Scopes.
- **Selection snapshot:** the expanded Scope set a refresh polls. It is fixed for
  the duration of a refresh so an atomic refresh keeps one meaning.
- **Truncated selection:** an expansion whose organization holds more eligible
  repositories than the capacity bound admits. The retained subset is deterministic
  and the omission is disclosed.
- **Changed-file set:** the normalized repository-relative paths known to be touched
  by an event's entity, obtained from the event payload or enrichment.
- **Enrichment:** cancelable GitHub lookup work that obtains changed-file evidence
  not present in the source event.
- **Membership:** the result of evaluating an event against a Scope: `member`,
  `not-member`, or `unknown`.
- **Unknown membership:** the explicit state in which OrgTop lacks sufficient
  changed-file evidence to decide path-scope membership. Unknown is not equivalent
  to member or not-member.
- **Cache:** bounded local SQLite data used to avoid unnecessary repeated enrichment.
  It is derived, disposable product state and never an authentication store.
- **Rain:** the third primary TUI view, consisting of a bounded activity field and a
  bounded `Interesting Now` strip.
- **Rain item:** a visual representation of one normalized event's membership in one
  visible Scope. An event that belongs to several visible Scopes has one independently
  bounded item in each matching Scope column. Item motion and lifetime are
  deterministic and bounded.
- **Interesting Now:** a small readable list of current, directly observable events.
  In v0.2.0 it is not an anomaly list, baseline ranking, or derived-signal feed.
- **Directly observable:** supported by normalized source or enrichment facts without
  historical comparison, inferred normality, or opaque scoring.
- **Current and stale:** retain the v0.1.0 meanings for atomic polling snapshots.
  Enrichment and cache degradation add visible qualification; they do not permit
  stale data to be presented as current or `LIVE`.

## Functional Requirements

### FR-001 v0.1 Compatibility and Release Boundary

- The standalone binary, existing local authentication, exact repeated `--repo`
  selection, GitHub polling, normalized events, atomic refresh lifecycle, Overview,
  Stream, responsive input, clean exit, and loading/current/empty/error/stale states
  from v0.1.0 remain supported unless this specification explicitly extends them.
- Existing exact `--repo owner/repository` invocations retain their v0.1.0 meaning
  and do not require path enrichment.
- Repository identifier validation, case-insensitive comparison, source identity
  checks, credential precedence and secrecy, polling/rate-limit discipline,
  deterministic event deduplication and ordering, and the 500-event in-memory
  snapshot bound remain unchanged.
- v0.2.0 continues to label transport as `POLLING`, never `LIVE`.
- Overview remains the initial and canonical operating view. Rain complements but
  does not replace Overview or Stream.
- The distribution channels FR-014 adds do not change the standalone contract:
  `orgtop` remains directly executable with neither the GitHub CLI nor Homebrew
  installed.

### FR-002 Unified Scope Model

- Repository and path selection are represented by one Scope domain model before
  filtering, aggregation, application state, or rendering.
- A repository scope selects eligible normalized activity for its exact repository.
  A path scope additionally requires path-membership evaluation.
- A Scope belongs to exactly one repository. One repository may have any number of
  selected path scopes and may also be selected as a repository scope.
- A single event may be a member of multiple path scopes. Such membership is
  retained independently for each Scope and is not collapsed into an arbitrary
  single owner.
- Scope filtering occurs after normalization and required enrichment but before
  view-specific aggregation.
- Scope parsing, canonical identity, deduplication, repository/path composition, and
  matching semantics must be shared by the CLI, domain, tests, and TUI. Enrichment
  cache keys use a separate stable repository/entity evidence identity so adding a
  Scope cannot create redundant cached evidence or GitHub work.
- Path scopes appear as first-class labeled Scopes wherever repository scopes are
  shown. The UI must not imply that a path scope is a real GitHub repository.
- Empty path scopes are valid display states after a successful, sufficiently known
  refresh.
- Exact CLI syntax, inclusive path pattern grammar, canonicalization, case behavior,
  rename behavior, and invalid-pattern diagnostics are defined by RG-001 and RG-002.

### FR-003 Changed-File Enrichment

- Path membership is based on normalized changed-file evidence, not event type,
  entity title, description text, actor, branch name, or repository activity alone.
- When a normalized event already carries authoritative changed-file evidence, the
  Scope engine may evaluate it without another lookup.
- When evidence is absent and the event/entity is eligible for enrichment, OrgTop
  obtains changed files through a cancelable GitHub adapter operation before deciding
  membership.
- GitHub request/response and pagination types remain inside the adapter. The domain
  receives normalized repository-relative paths and explicit enrichment outcomes.
- Enrichment accounts for all pages required by the selected API contract and does
  not silently treat a truncated file list as complete.
- Enrichment work is deduplicated for entities shared by events or Scopes. Adding
  path scopes must not cause one identical lookup per Scope.
- Enrichment obeys the effective polling, concurrency, cancellation, timeout, and
  rate-limit constraints of the source adapter. It must not introduce a tight retry
  loop or block Bubble Tea input/render handling.
- Changed-file evidence may make one event a member of zero, one, or many path
  scopes.
- Rename representation, entity eligibility, endpoint choice, pagination limits,
  freshness inputs, and API failure behavior are defined by the closed RG-003
  contract; reusable cache freshness is closed separately under RG-005.

### FR-004 Explicit Membership Outcomes

- Every path-membership evaluation produces `member`, `not-member`, or `unknown`.
- `member` requires sufficient evidence and a successful matcher result.
- `not-member` requires sufficient evidence and no matcher result.
- Missing, incomplete, expired, unsupported, rate-limited, denied, or failed
  enrichment must not be silently converted into either `member` or `not-member`.
- Unknown membership must remain distinguishable in domain/application state so the
  product can communicate incomplete path coverage and recover after later success.
- Repository scopes remain evaluable from repository identity when path evidence is
  unavailable.
- The closed RG-004 policy defines how unknown events affect path-scope counts,
  Stream inclusion, Rain, snapshot currentness, retry/recovery, and combined
  degraded presentation.

### FR-005 Bounded SQLite Enrichment Cache

- v0.2.0 uses a local SQLite cache for reusable changed-file enrichment results.
- The cache persists only information required for enrichment reuse and its safe
  validation. It does not persist credentials, authorization headers, raw GitHub
  payloads, rendered screens, or speculative baseline history.
- Cache reads and writes occur outside rendering and keyboard handling and are
  cancelable where the underlying operation permits.
- A valid cache hit may satisfy enrichment without a GitHub lookup. Invalid,
  incomplete, or expired entries must not be treated as complete evidence.
- Cache writes are transactional enough that interruption cannot expose partial file
  evidence as a complete changed-file set.
- Cache size and retention are bounded by an enforceable policy. Cleanup is
  deterministic, occurs without an unbounded foreground pause, and converges toward
  its documented retained targets in bounded refresh batches.
- The CLI provides a process-local cache-disable control and a safe cache-reset
  control. Disabling the cache performs no cache reads, writes, schema setup, or
  cleanup for that process. Reset removes only derived OrgTop enrichment state and
  never credentials or unrelated user data; exact invocation and startup behavior
  are closed under RG-001 and RG-005.
- Corrupt, unavailable, unwritable, or schema-incompatible cache state never
  causes a panic and never compromises token secrecy. The application exposes an
  honest actionable failure or degraded state according to the closed cache policy.
- The cache is disposable: removing it may increase API work but must not alter Scope
  matching semantics when equivalent complete evidence is reacquired.
- Exact location/configuration, schema/versioning contract, cache keys, freshness,
  negative-result handling, byte/row/age bounds, cleanup trigger, and cache-failure
  product behavior are defined by RG-005.

### FR-006 Scoped Snapshot and Aggregation

- A successful v0.2.0 application snapshot retains normalized events, repository
  identity, known changed paths as needed, per-Scope membership outcomes, and direct
  per-Scope aggregates independently of rendering.
- Repository-scope aggregates preserve v0.1.0 direct count semantics.
- Path-scope aggregates use the same event categories and counting rules, restricted
  to events whose membership is `member`, subject to the policy closed under RG-004.
- Scope rows use RG-012's deterministic mixed repository/path ordering and
  tie-breaks.
- One event matching multiple Scopes contributes to each matching Scope. Product
  copy must not present a sum across overlapping Scopes as a deduplicated organization
  total unless it is actually deduplicated.
- Counts remain direct observations from the bounded current snapshot. They do not
  represent percentages, expected values, baselines, anomaly scores, productivity,
  or normality.

### FR-007 Overview and Stream Scope Presentation

- Overview renders repository and path scopes in one Scope-oriented table or
  equivalent responsive structure.
- Each visible Scope has an unambiguous repository/path label and the direct activity
  counts supported by the scoped snapshot.
- Stream continues to use deterministic reverse-chronological event order and makes
  active Scope context visible.
- Where one event matches multiple selected path scopes, Stream uses a deterministic,
  bounded presentation that does not duplicate or conceal membership accidentally.
  Its exact compact rendering and event-detail interaction are defined by RG-012.
- Overview and Stream visibly distinguish empty activity from incomplete or unknown
  path membership. They do not label unknown coverage as no activity.
- Existing loading, first-load error, stale-after-success, recovery, scrolling, view
  state retention, and narrow-terminal guarantees continue to apply.

### FR-008 Rain View

- Rain is the third primary view in the same Bubble Tea application and consumes the
  same normalized, filtered application state as Overview and Stream.
- `3` opens Rain. `1`, `2`, and `3` open Overview, Stream, and Rain respectively;
  `tab` cycles through all three without losing loaded data or per-view state.
- The shared header identifies OrgTop, Rain, `POLLING`, Scope context, freshness, and
  degraded state under the same semantics as the other views.
- Each Rain column represents a visible Scope. Repository scopes and path scopes use
  the same column model and remain distinguishable by label.
- An event that is a member of multiple visible Scopes produces one Rain item in
  every matching Scope column. Each representation counts against that column's
  bound and the global Rain bound; deterministic admission under pressure is closed
  under RG-006 and RG-009.
- New scoped events enter a deterministic activity field, move only on Bubble Tea
  ticks, and disappear after a bounded lifetime. The field has bounded item count and
  memory use independent of process runtime.
- `p` toggles Rain motion pause. Pausing freezes movement and expiry advancement but
  does not stop polling or refreshes. Arrivals are queued in deterministic order
  within the existing Rain bounds and are considered for deterministic fair
  admission when motion resumes; pause never permits unbounded state.
- Rain visual density represents only the density of displayed direct events. It is
  never labeled as severity, significance, anomaly, unusualness, or deviation from
  normal.
- Rain remains useful without color. Repeating motion communicates event arrival and
  ongoing window presence; RG-008 intensity and bounded removal communicate factual
  recency. Neither is an arbitrary particle effect or unsupported signal.
- Exact tick cadence, event placement, collision behavior, lifetime, field bounds,
  and catch-up behavior after delayed ticks are defined by RG-006.

### FR-009 Bounded Interesting Now

- Rain includes a readable `Interesting Now` strip distinct from the activity field.
- The strip contains only a bounded number of normalized, in-Scope, directly
  observable events from the current snapshot.
- Each entry identifies enough event, Scope/entity, and recency context to explain
  why it is shown without relying on color or the Rain field.
- Entries must not claim an anomaly, baseline comparison, inferred importance,
  severity, productivity, or derived signal.
- The strip is not a second Stream and does not grow with event volume or terminal
  uptime.
- Selection and ordering are deterministic and explainable from direct event facts.
  Exact eligibility, ordering, tie-breaks, maximum entries, retention window, and
  refresh interaction are defined by RG-007 and do not invent a ranking.

### FR-010 Shared Event and Recency Semantics

- Overview, Stream, Rain, and shared chrome use one semantic event-category and
  recency vocabulary owned outside rendering functions.
- A category has the same meaning in every view. A glyph or style must not mean push
  in one view and review, merge, failure, or priority in another.
- Existing v0.1.0 event categories remain `push`, `pull_request`, `review`, `comment`,
  and `other`; v0.2.0 does not fabricate categories unsupported by the source.
- Category always has a non-color encoding through stable glyph and/or text. Color
  reinforces meaning but is never the sole encoding.
- Recency uses a small discrete semantic progression equivalent to new, recent,
  aging, and expired. Expired Rain items are removed.
- Recency changes visual emphasis only. It does not imply importance, quality,
  severity, or anomaly.
- The exact shared glyph table, ASCII fallback, recency thresholds, and style mapping
  are defined by the closed contract under RG-008 and preserve shipped v0.1 meanings.

### FR-011 Responsive and Degraded Behavior

- All three views respond safely to resize and remain interactive during polling,
  enrichment, cache maintenance, rate limiting, and source/cache failure.
- At `40x10`, each view retains active view, transport/freshness state, one primary
  content or explicit state line, and a quit hint, preserving the v0.1.0 minimum.
- Constrained layouts preserve primary content, shorten only unambiguous labels, hide
  secondary detail before primary data, and keep freshness/degraded state visible.
- A list longer than its available area is never silently truncated. Every hidden
  entry is either reachable by scrolling or accounted for by an explicit position or
  overflow indicator, so a shortened view is never indistinguishable from a complete
  one. This closes the v0.1.0 Overview behavior, where rows past the body budget were
  dropped without a hint.
- Mixed-Scope row ordering, compact Stream overlap labels, label shortening, and the
  non-Rain overflow interaction are closed together under RG-012.
- Rain reduces, pages, or scrolls visible columns deterministically instead of
  shrinking labels into unreadable output. The chosen behavior is consistent across
  renders and does not starve a Scope indefinitely.
- `Interesting Now` may show fewer entries or collapse before the Rain activity field
  becomes unusable, but its presence/absence must remain understandable.
- Smaller positive dimensions are best effort and must not panic, corrupt output,
  allocate without bound, or cause an unbounded update/render loop.
- Unknown membership, enrichment failure, cache failure, and stale source data have
  distinct honest presentation where their user consequences differ. None may be
  presented as `LIVE`, complete, or empty by default.

### FR-012 Documentation

- README and help text document the closed unified Scope syntax, examples mixing
  repository and path scopes, path matching semantics, unknown-membership behavior,
  local cache location/bounds/cleanup/disable/reset controls, controls, Rain pause
  semantics, and overlapping Rain membership.
- Documentation states that changed-file enrichment can consume additional GitHub
  API requests and explains visible rate-limit/degraded behavior.
- Documentation describes `Interesting Now` as direct recent activity, not
  intelligence or anomaly detection.
- Documentation preserves v0.1.0 authentication, polling/not-live, and secret-safety
  guidance and does not depend on the external product design document.

### FR-013 Organization Selection

- An organization selector selects the eligible repositories of one GitHub
  organization without the user naming each repository. It complements exact
  `--repo` selection and never replaces it.
- An organization selector is not a Scope and has no identity in the domain,
  cache keys, aggregation, or views. It is expanded into ordinary repository
  Scopes at the CLI/adapter boundary, and everything downstream sees only the
  Scope model of FR-002.
- Expansion is a bounded, cancelable GitHub listing operation. Its request,
  response, and pagination types stay inside the adapter.
- Expansion is subject to an explicit capacity bound. When an organization holds
  more eligible repositories than the bound admits, the retained subset is
  chosen deterministically by declared, source-backed repository facts, and the
  omission is disclosed in the TUI rather than presented as the whole
  organization.
- Eligibility is decided by RG-010's declared source-backed facts: disabled
  repositories are always excluded; archived and fork repositories are excluded
  unless their process flags include them; no activity or permission probe occurs.
- Expansion results are deduplicated against exact `--repo` selections and
  against other organization selectors by canonical Scope identity. A repository
  reachable through several selectors is polled once and appears once.
- An expanded repository Scope is indistinguishable from a `--repo` Scope in the
  domain, in aggregation, and in view state. The Scope set's provenance may be
  presented, but must not change how a Scope behaves.
- Each refresh polls one selection snapshot, so a repository added to or removed
  from the organization mid-refresh cannot make a refresh partially describe two
  different selections. FR-001's atomic-refresh guarantee is preserved.
- Re-expansion is a separate bounded operation from event polling and, after success,
  does not run on every refresh. A failed due attempt may retry at the next explicitly
  allowed time defined by RG-010. A failed due re-expansion retains the last fixed
  selection and adds `SELECTION STALE`; source polling independently determines
  `CURRENT`, `STALE`, or `ERROR`. It never silently narrows or empties the selection.
- Organization selection must not raise per-refresh request volume beyond the
  discipline NFR-002 already imposes. The capacity bound, the request budget per
  refresh, and the re-expansion interval are one coherent contract, not three
  independent choices.
- An organization that yields no eligible repository is a valid, explicit,
  successful empty state and not an error.
- Path scopes remain per repository. Organization selectors create repository Scopes
  only and cannot carry a path matcher in v0.2.0.
- Exact selector syntax, eligibility defaults, ordering and truncation rule,
  capacity bound, re-expansion interval, disclosure copy, and invalid-input
  behavior are defined by RG-010.

### FR-014 Distribution Channels

- The released artifact stays one standalone `orgtop` executable. A distribution
  channel redistributes that executable; it may not change the invocation, the
  credential precedence, or the behavior when the distributing tool is absent.
- v0.2.0 publishes through the GitHub CLI extension channel alongside the
  release archives v0.1.0 established. A build installed that way runs as
  `gh orgtop`, receives its arguments unchanged, and remains a standalone executable
  directly invocable at its installed path. GitHub CLI need not add an `orgtop` alias
  to `PATH`; archives and Homebrew retain the ordinary `orgtop` command name.
- That channel requires a companion repository whose name begins with `gh-`,
  carrying the `gh-extension` topic, with raw executables attached to each
  release named `gh-orgtop-<os>-<arch>` and suffixed `.exe` on Windows. Archives
  are not installable through it.
- The GitHub CLI places no credential in an extension's process environment. A
  `gh orgtop` launch therefore resolves its token through the unchanged v0.1.0
  precedence, whose third step is `gh auth token --hostname github.com`. No
  gh-specific credential path is added, and no channel may supply a token by a
  route FR-001 of v0.1.0 does not already define.
- v0.2.0 publishes a Homebrew formula through a tap, installing the same
  executable at the same version the tag publishes.
- Every channel publishes one version per tag. For a given operating-system and
  architecture target, every channel applicable to that target redistributes the
  byte-identical published executable proven by its checksum; Windows has no Homebrew
  channel, and installer-required host-local code signing does not create a second
  distributed artifact. Each applicable channel publishes checksums and source
  provenance or an exact reference to them. RG-011 defines staged publication,
  idempotent retry, reconciliation, and withdrawal so a partial external failure is
  never reported as a successful release.
- Channel availability is documented per FR-012, while installing GitHub CLI or
  Homebrew is never presented as a runtime requirement: the release archives remain
  a complete installation path on a host with neither tool.

## Non-Functional Requirements

### NFR-001 Responsiveness and Cancellation

- Network, enrichment, SQLite, cleanup, and tick work never runs synchronously in
  rendering or keyboard handling.
- Application shutdown cancels source/enrichment work and does not wait indefinitely
  for GitHub, credential, cache, or timer operations.
- Existing v0.1.0 HTTP timeout and non-overlapping refresh guarantees remain in force.
- Expensive work is bounded per command/message so high event or path counts do not
  monopolize Bubble Tea's update loop.

### NFR-002 Resource and API Discipline

- The in-memory snapshot remains bounded to the newest 500 source events.
- Rain state, `Interesting Now`, enrichment concurrency, queued enrichment work, and
  SQLite cache growth use the closed RG-005/RG-009 bounds.
- Enrichment reuses complete valid evidence and coalesces duplicate work.
- Polling and enrichment honor GitHub guidance and returned rate-limit delays. Cache
  misses must not trigger tight retries or unbounded fan-out.
- RG-009 defines one combined per-cycle work ledger across organization expansion,
  repository polling, pagination, enrichment, and SQLite work. It also defines where
  the 500-event limit is applied, prohibits enriching events discarded before
  membership evaluation, and gives exact selections deterministic precedence when
  expanded selectors would exceed the global Scope capacity.

### NFR-003 Correctness and Determinism

- Identical validated Scope configuration, normalized events, enrichment outcomes,
  cache state, terminal dimensions, and tick inputs produce identical membership,
  aggregation, ordering, and Rain state.
- Unknown evidence remains explicit across adapter, domain, application, and view
  boundaries.
- No incomplete file list is treated as complete solely because a request returned
  some paths.
- Overlapping Scope behavior and Rain/strip bounds are testable without live GitHub,
  wall-clock sleeps, or terminal-dependent color support.

### NFR-004 Security and Privacy

- v0.1.0 token and authorization-header protections remain mandatory.
- Cache and logs minimize private repository data. Raw authenticated payloads are not
  persisted or logged by default.
- OrgTop has no telemetry and transmits activity only to GitHub.
- Cache files use RG-005's user-local location, ownership, and platform permissions.
- Cache byte limits measure the total on-disk database, WAL, SHM, and temporary
  cleanup footprint; logical record limits are additional bounds rather than a
  substitute. Concurrent OrgTop processes follow a bounded lock/busy policy and
  cannot expose partial bootstrap or cleanup state.

### NFR-005 Architecture and Maintainability

- GitHub payload, transport, pagination, and API error types remain in the adapter.
- Scope matching and direct aggregation remain domain responsibilities; SQLite and
  Bubble Tea types do not enter the domain model.
- Cache access is behind the smallest boundary required for enrichment tests and is
  not a generic persistence framework.
- Views consume prepared state and do not perform matching, enrichment, ranking,
  recency calculation, or aggregation during rendering.
- No abstraction is introduced for future sources, webhooks, baselines, signals, or
  central storage.

### NFR-006 Verification Quality

- Tests are deterministic, fixture-driven, and independent of live GitHub and user
  credentials.
- Domain tests cover unified Scope identity, all closed matcher semantics, overlap,
  member/not-member/unknown outcomes, direct aggregation, and deterministic ordering.
- Adapter tests cover complete and paginated enrichment, incomplete/malformed data,
  cancellation, authorization/rate-limit failures, and sanitized errors according to
  the closed API contract.
- Cache tests cover hits, misses, expiry, atomic writes, corruption, version handling,
  cleanup, disable/reset, concurrent-process locking, physical storage growth, and
  every configured bound according to the closed cache contract.
- TUI tests cover mixed Scopes, unknown/degraded states, three-view navigation, Rain
  deterministic ticks and expiry, bounded `Interesting Now`, shared semantics,
  resizing, narrow terminals, stale recovery, and clean shutdown.
- `task check` and Taskrail validation pass before release verification.

## Acceptance Scenarios

### A-001 v0.1 Repository Invocation Remains Valid

Given valid auth and the same fixture responses, an existing exact repeated `--repo`
invocation produces the same repository membership, atomic snapshot, Overview
counts, Stream order, polling label, and stale behavior as v0.1.0 without requiring
changed-file enrichment.

### A-002 Mixed Unified Scopes

Given one repository scope and two valid path scopes under another repository, the
closed v0.2.0 CLI form launches one TUI whose Overview shows all three as Scopes and
whose header represents the selected Scope set unambiguously.

### A-003 Overlapping Path Membership

Given complete changed-file evidence that matches two selected path scopes, the
event is a member of both, contributes to both direct Scope aggregates, and remains
one normalized source event. No view arbitrarily assigns it to only one Scope.

### A-004 Known Non-Membership

Given a complete changed-file set that matches none of a path scope's patterns, the
event is `not-member` for that Scope and does not contribute to its activity. The
same event may still contribute to its repository scope or another matching Scope.

### A-005 Unknown Membership Is Not Guessed

Given missing or incomplete evidence and an enrichment outcome classified as
unknown by the closed contract, the event remains `unknown`. Tests demonstrate the
RG-004 policy consistently in counts, Stream, Rain, freshness/degraded presentation,
and later recovery; neither inclusion nor exclusion occurs as an undocumented
fallback.

### A-006 Enrichment Cache Reuse

Given a complete valid cached changed-file set for an entity referenced by multiple
events or Scopes, one normalized result serves all evaluations and no redundant
GitHub request occurs. Removing the cache and reacquiring equivalent evidence yields
the same memberships.

### A-007 Cache Bounds and Failure

Given cache data beyond the closed logical/retention targets but within its physical
ceiling, deterministic cleanup converges toward the documented targets in bounded
batches without blocking TUI interaction. A cache already above the retained
physical ceiling is bypassed and safely reset by explicit user action. Given corrupt
or unwritable cache state, OrgTop follows the documented error/degraded policy,
remains secret-safe, and never presents incomplete evidence as complete.
Given cache-disable mode, no SQLite operation occurs and equivalent reacquired
evidence yields identical membership. Given cache reset, only OrgTop's derived
enrichment state is removed and the application safely continues according to the
closed startup contract.

### A-008 Rain Navigation and Determinism

From populated Overview, `3` opens Rain, `2` opens Stream, `1` returns to Overview,
and `tab` cycles all three. Given identical events, dimensions, and explicit tick
messages, Rain produces identical placement, movement, expiry, and bounded state.
Given an event matching several visible Scopes, Rain creates one bounded item in each
matching column. Pressing `p` freezes movement and expiry while bounded arrivals
continue to queue; pressing `p` again fairly considers them with retained field
items, admits the capacity-selected subset at row zero, accounts for omissions, and
resumes deterministically.

### A-009 Interesting Now Uses Direct Facts

Given more eligible current events than the closed strip limit, `Interesting Now`
shows no more than that limit using the documented deterministic selection rules.
Every entry is explainable from direct event facts and contains no baseline,
anomaly, unusualness, productivity, or opaque-score claim.

### A-010 Shared Semantics

Given the same event in Stream and Rain, its event category has the same glyph/text
meaning. Advancing recency changes only the documented discrete emphasis and expiry;
it does not change category or imply importance.

### A-011 Enrichment Failure and Recovery

After successful scoped data, a later source or enrichment failure preserves or
qualifies data exactly as the closed atomicity and unknown-membership policy defines,
shows honest stale/degraded context, and leaves navigation responsive. A later full
success clears the applicable state and recomputes membership atomically.

### A-012 Responsive Mixed-Scope Views

At `40x10`, Overview, Stream, and Rain retain active view, transport/freshness state,
one primary content or explicit state line, and a quit hint. Rain applies its closed
column-reduction strategy without unreadable labels, panic, starvation, or an
unbounded render loop.

### A-013 Rate-Limit Discipline

Given many events sharing enrichment entities and a rate-limited fixture adapter,
work is coalesced and bounded, returned delay metadata is honored, no tight retry

### A-014 Organization Expansion, Deduplication, and Truncation

Given a fixture organization whose eligible repositories exceed the capacity

selection does not change; a failed re-expansion keeps the last successful
selection snapshot visible with a degraded state rather than narrowing or
emptying it. An organization with no eligible repository renders an explicit
empty state, not an error.

### A-015 Channel Parity for a Published Tag

Given a published tag, the release archives, the GitHub CLI extension assets, and
the Homebrew formula each install the same version of the same executable. Each
installed form reports that version from `--version`, accepts an identical
invocation, and resolves credentials by the unchanged precedence. A `gh orgtop`
launch forwards its arguments unchanged and needs no gh-specific credential.
A host with neither the GitHub CLI nor Homebrew installed still has a complete
installation path. A channel that fails to publish for that tag fails the release
workflow and leaves an explicitly partial, non-complete state for RG-011 retry or
withdrawal; differing public channel availability is never reported as completion.

Given the same valid repeated `--repo` arguments accepted by v0.1.0 and no bare

### RG-001 Unified CLI Contract

This gate is closed by the following normative CLI contract. RG-002 defines the
contents and canonical identity of `PATTERN`; this gate defines how a pattern is
associated with a repository and does not depend on shell interpretation.

- `--repo OWNER/REPOSITORY` retains its exact v0.1.0 lexical validation, accepted
  flag forms, case-insensitive comparison, repetition, first-spelling retention,
  and repository-only meaning when no bare `--path` is present. Existing
  repository-only invocations therefore produce the same repository Scope set.
- `--path` is repeatable and accepts either bare `PATTERN` or qualified
  `OWNER/REPOSITORY:PATTERN`. If a value contains an unescaped colon, exactly one is
  permitted; it is the qualified-form delimiter, and the complete prefix before it
  must pass exact `--repo` lexical validation. Literal pattern colons are `\:`.
  RG-002 defines escaping and rejects an empty or invalid pattern.
- A qualified `--path` produces one path Scope and does not require a matching
  `--repo`. It composes independently with repository Scopes, so
  `--repo acme/api --path 'acme/api:src/**'` selects both the whole repository
  Scope and the qualified path Scope.
- One or more bare `--path` values filter all repositories supplied by `--repo`.
  In that form each `--repo` supplies a repository to the filter and does not also
  produce a repository Scope. The result is the Cartesian product in request
  order, with repositories as the outer sequence and bare patterns as the inner
  sequence. Thus two repositories and two bare patterns produce four path Scopes,
  not two repository Scopes plus four path Scopes. A bare path without `--repo`
  is invalid.
- Qualified and bare path forms may be mixed. Bare patterns apply only to
  exact `--repo OWNER/REPOSITORY` values; they never apply to RG-010's
  `--repo 'ORGANIZATION/*'` selector alias. Qualified patterns retain their named
  repository. At least one repository/path Scope or organization selector must
  result unless help, version, or cache reset was requested.
- v0.2.0 path scopes are inclusive only. No CLI form composes an exclusion into a
  Scope, and a leading punctuation character is not interpreted as an implicit
  exclusion. Repeated path values create separate Scopes rather than several
  matchers in one Scope.
- After bare-path expansion, equivalent Scopes are deduplicated by the canonical
  Scope identity closed under RG-002. The first occurrence and its requested
  spelling are retained. Repetition is not an error. Configuration order does not
  override the deterministic presentation order closed under RG-012.
- `--no-cache` is a process-local launch flag. It requires a valid non-empty Scope
  or organization-selector input and causes that process to perform no cache open, schema setup, read,
  write, cleanup, checkpoint, or reset operation. It does not change enrichment or
  matching semantics when equivalent complete evidence is acquired from GitHub.
- `--reset-cache` is a standalone administrative action. It accepts no `--repo`,
  `--path`, `--org`, `--include-archived`, `--include-forks`, `--no-cache`, positional
  argument, or other launch selection. It resolves the closed RG-005 cache
  location, safely removes only OrgTop enrichment state, reports success, and
  exits zero without resolving credentials, making a network request, or starting
  the TUI. Failure reports one actionable cache error and exits non-zero without
  launching. RG-005 defines locking and failure safety.
- `--help`/`-h` and `--version`/`-v` retain their v0.1.0 precedence and zero-exit
  behavior. Version retains its exact output; help expands usage to document the
  new flags and forms. Neither action resets or opens the cache, resolves
  credentials, makes a network request, or starts the TUI, even when another
  supplied argument would otherwise be invalid or administrative.
- Every value flag accepts both `--flag VALUE` and `--flag=VALUE`; this includes
  `--repo`, `--path`, and `--org`. Boolean flags accept their ordinary bare form only.
- Launch input is validated before credential, network, cache, or TUI work.
  Help/version precedence is applied first. Otherwise argument scanning from left to
  right reports its first unknown flag, missing value, malformed value, or positional
  argument. If scanning succeeds, post-parse validation reports the first applicable
  class in this order: incompatible administrative/cache controls; selector-only
  flag misuse; missing selection; bare path without an exact repository; canonical
  repository/Scope capacity; then organization-selector capacity. Within one class,
  first argument occurrence wins. Parsing writes usage and that cause once to standard
  error and exits with status 2.
- Usage presents these supported forms and documents every accepted flag:

  ```text
  orgtop --repo OWNER/REPOSITORY [--repo OWNER/REPOSITORY ...] [--path (PATTERN | OWNER/REPOSITORY:PATTERN) ...] [--no-cache]
  orgtop --path OWNER/REPOSITORY:PATTERN [--path OWNER/REPOSITORY:PATTERN ...] [--repo OWNER/REPOSITORY ...] [--no-cache]
  orgtop (--org ORGANIZATION | --repo 'ORGANIZATION/*') [...] [--repo OWNER/REPOSITORY ...] [--path OWNER/REPOSITORY:PATTERN ...] [--include-archived] [--include-forks] [--no-cache]
  orgtop (--org ORGANIZATION | --repo 'ORGANIZATION/*') [...] --repo OWNER/REPOSITORY [--repo OWNER/REPOSITORY ...] --path PATTERN [--path PATTERN ...] [--path OWNER/REPOSITORY:PATTERN ...] [--include-archived] [--include-forks] [--no-cache]
  orgtop --reset-cache
  orgtop --version
  ```

RG-010 owns validation, deduplication, and behavior of the two organization-selector
spellings and inclusion flags. They do not reinterpret either `--path` form or the
cache controls closed here.

### RG-002 Path Matcher Contract

This gate is closed by the following source-independent matcher and identity
contract. A shell only supplies an argument string; OrgTop alone parses and matches
it. Examples quote patterns so a shell cannot expand them first.

#### Pattern Grammar

- A pattern is a non-empty sequence of non-empty segments separated by `/`. `/`
  is the only separator on every operating system. Leading, trailing, and repeated
  separators and the complete segments `.` and `..` are invalid rather than
  cleaned. Patterns must be valid UTF-8 and contain no NUL.
- Ordinary Unicode code points are case-sensitive literal text. OrgTop performs no
  Unicode normalization or locale-dependent comparison. Dot-prefixed names are
  ordinary names: `*` may match `.github` without a special opt-in.
- `*` is the only wildcard within a segment and matches zero or more code points
  other than `/`. Adjacent unescaped stars within a non-recursive segment are
  invalid. `?`, bracket expressions, braces, and shell character classes have no
  special meaning and match literally.
- A segment consisting of exactly `**` is recursive and matches zero or more
  complete path segments. Unescaped `**` anywhere inside a larger segment is
  invalid. Consecutive recursive segments are accepted and canonicalized to one.
- Backslash escapes only `*`, `:`, or backslash itself. `\*`, `\:`, and `\\`
  therefore produce literal matcher tokens; a trailing backslash or any other
  escape is invalid. Backslash is never a path separator.
- In a `--path` value, one unescaped colon is the qualified-form delimiter closed
  by RG-001. If present, everything before it must be a valid
  `OWNER/REPOSITORY`; any colon in the pattern is written `\:`. With no unescaped
  colon, the complete value is a bare pattern. More than one unescaped colon is
  invalid.
- v0.2.0 has no exclusion grammar. In particular, `!` is ordinary literal path
  text and never negates another pattern. Each accepted pattern defines one
  inclusive path Scope.
- Pattern diagnostics are deterministic. Invalid UTF-8 is checked first, then NUL.
  Otherwise tokenization scans code points left to right and reports the first
  invalid escape, second unescaped colon, separator/empty segment, `.`/`..` segment,
  or invalid star construction encountered; ties at one position use that listed
  order. Offsets are zero-based UTF-8 byte indexes: empty input is offset zero,
  leading slash names byte zero, repeated slash names the second slash, and trailing
  slash names the final slash. For a qualified value, repository-prefix validation
  precedes pattern tokenization and reports its zero-based prefix offset. The
  diagnostic names that exact cause and offset.

#### Matching and Normalization

- A changed path uses the same strict repository-relative representation as a
  pattern after escapes and wildcards are excluded: valid UTF-8, non-empty
  slash-separated segments, no leading, trailing, or repeated slash, no `.` or
  `..` segment, and no NUL. No host filesystem cleanup, case folding, symlink
  resolution, or separator conversion occurs.
- A pattern matches a changed path when its glob tokens match either the complete
  changed path or a segment-boundary prefix of that path. Consequently a literal
  component pattern such as `services/payments` matches that exact path and paths
  below it, and `services/*` matches each immediate child and everything below a
  matched child. It does not match `service/payments` or `services-payments`.
- `*` does not cross `/`. `**` may match no segment, so
  `services/**/api` matches both `services/api` and
  `services/region/api`. `**` by itself matches every valid known changed path
  but remains a path Scope requiring changed-file evidence; it is not converted
  into a repository Scope.
- Matching is case-sensitive and code-point exact on every host. For example,
  `Services/*` does not match `services/api`, while `*` does match `.github`.
- A rename contributes both its normalized old path and normalized new path to
  matcher evaluation. Matching both names still produces one `member` result for
  a given Scope; moving a file between two selected components may make the event
  a member of both Scopes.
- Any malformed path in an otherwise returned changed-file set makes that entire
  evidence result incomplete. No malformed path is dropped to manufacture a
  complete set, and membership remains `unknown` until equivalent complete valid
  evidence is available.

#### Canonical Scope Identity

- Repository Scope identity is the tuple `(repository, repository-key)`, where
  `repository-key` is the existing lowercase canonical repository identity. Path
  Scope identity is the distinct tuple `(path, repository-key, matcher-tokens)`.
  The leading kind keeps a `**` path Scope distinct from its repository Scope.
- `matcher-tokens` are case-sensitive parsed literal, single-segment wildcard,
  recursive-segment, and separator tokens after escapes are decoded. Adjacent literal
  code points, including decoded escapes, coalesce into one maximal literal token.
  Separators are emitted only between retained segments. Consecutive recursive
  segments are normalized by repeatedly rewriting `D X D` to `D`. When a terminal
  recursive segment follows another retained segment, both that terminal `D` and its
  preceding `X` are removed; a sole `D` remains the all-path matcher. Identity encoding
  occurs only after these rewrites. Terminal `/**` is redundant because every matcher
  includes descendants.
- No other semantic-glob equivalence is attempted. Distinct canonical token
  sequences remain distinct Scopes even if a particular repository currently
  contains paths for which they happen to select the same files.
- Deduplication compares the complete typed identity. The first requested
  repository and pattern spelling is retained for presentation. Overlapping but
  non-identical Scope identities remain independent, and one event may be a
  member of each.
- Scope identity is used consistently by CLI expansion, domain state, tests, view
  state, aggregation, and presentation. It is never used as an enrichment cache
  key: RG-005 separately defines repository/entity evidence identity so adding or
  renaming a Scope cannot duplicate GitHub evidence work.

### RG-003 GitHub Enrichment Contract

This gate is closed by the following GitHub REST adapter contract. Transport JSON,
pagination links, headers, status classification, and endpoint-specific types remain
private to the adapter. Downstream code receives normalized evidence descriptors,
paths, provenance, and typed outcomes only.

#### API and Authentication

- Every polling, organization, and enrichment request sends
  `Accept: application/vnd.github+json`,
  `X-GitHub-Api-Version: 2026-03-10`, the existing safe user agent, and the token
  selected by the unchanged v0.1.0 credential precedence. v0.2.0 upgrades the
  existing Events request version and its fixtures together; it adds no credential
  source or interactive authorization flow.
- The selected read operations are `GET /repos/{owner}/{repo}/events`,
  `GET /repos/{owner}/{repo}/commits/{sha}`,
  `GET /repos/{owner}/{repo}/compare/{base}...{head}`, and, only for the explicit
  current-PR exception below, `GET /repos/{owner}/{repo}/pulls/{number}`. RG-010
  defines the organization-listing endpoint.
- Enrichment requires the same repository read access as polling plus read access
  to repository contents and pull requests for the selected operations. A token
  that can poll but cannot read one enrichment resource yields `denied` evidence for
  that resource; OrgTop never requests broader permissions or prints a token.
- Complete immutable evidence is served from the cache without a conditional HTTP
  request. A cache miss uses an ordinary request. v0.2.0 stores no ETag or other
  transport validator and performs no conditional enrichment revalidation.

#### Evidence Eligibility and Identity

Evidence provenance is one of `direct-event`, `event-time`, or `current-pr` and is
retained with the outcome. Stable evidence identity is separate from Scope identity:

- A valid object SHA is exactly 40 ASCII hexadecimal digits normalized to lowercase;
  all-zero is invalid. Push facts are `payload.before`, `payload.head`, and the
  non-negative integer `payload.size`. PR/PR-review event-time facts are
  `payload.pull_request.base.sha` and `.head.sha`. A direct review-comment path is
  `payload.comment.path`. An ordinary PR issue comment requires
  `payload.issue.number` plus a non-null `payload.issue.pull_request` marker.
- Event classification is ordered. `PushEvent` first validates SHA syntax, treats
  equal valid `before`/`head` as complete empty regardless of `payload.size`, then
  uses commit work only for distinct SHAs with size 1 and compare work for other
  distinct valid SHAs. `PullRequestReviewCommentEvent` is direct-only: a present
  valid `payload.comment.path` is complete singleton evidence, while missing,
  empty, or malformed path is incomplete and never falls back to PR SHAs.
  `PullRequestEvent` and `PullRequestReviewEvent` use event-time base/head.
  `IssueCommentEvent` with the PR marker uses current-PR metadata; issue-only comments
  and every other event type are unsupported.

| Normalized event fact | Evidence operation and identity | Provenance |
| --- | --- | --- |
| File-specific PR review comment with valid payload path | Complete singleton path set keyed by event ID; no request | `direct-event` |
| One-commit push with valid distinct nonzero `before`, `head`, and size 1 | Commit work/cache result keyed by repository and head SHA; applicability verifies each event's `before` independently | `event-time` |
| Other push with valid distinct nonzero `before` and `head` | Immutable compare keyed by repository, before SHA, and head SHA | `event-time` |
| PR or PR-review event carrying valid event-time base/head SHAs | Immutable compare keyed by repository, base SHA, and head SHA | `event-time` |
| Ordinary issue comment known to be on PR number N | Capture current PR base/head once per PR per refresh, then use the immutable compare identity for that pair | `current-pr` |
| Any other event or missing/zero/malformed required identity | No request | unsupported |

- A direct review-comment path describes that comment, not every file in its PR.
  It is normalized under RG-002; malformed direct evidence is `incomplete` rather
  than unsupported or silently discarded.
- An ordinary PR issue comment has no event-time SHA pair in the Events payload.
  The chosen exception captures the PR's current base/head once in the refresh and
  then compares those immutable SHAs. `current-pr` provenance is retained in every
  membership and aggregate influenced by it, quantitatively disclosed as
  `current PR evidence`, and never described as the files at comment time. RG-004
  closes how that qualification composes with unknown and degraded presentation.
- Equal repository/operation/SHA descriptors coalesce across retained events and
  Scopes. Different base/head observations of one PR are different evidence
  identities. PR number alone and Scope identity are never cache keys for changed
  paths. Direct event paths require no persistent cache entry.
- Commit coalescing shares one request/cache result containing normalized paths and
  the verified sole-parent SHA. Each event independently receives `complete` only
  when its normalized `before` equals that parent; another event sharing the head but
  carrying a different `before` receives `incomplete`. Compare results remain directly
  applicable to their exact base/head key.
- A push with equal valid before/head has a complete empty set without a request.
  A creation/deletion event with an all-zero side, a missing size needed for the
  one-commit optimization, or otherwise insufficient immutable facts does not infer
  branch contents. It uses immutable compare when both sides are valid or is
  unsupported.

#### Completeness Proof

- A one-commit push first requests the exact head SHA with `per_page=100`. Every
  response page must report that exact commit SHA and the same parent list, and the
  event's before SHA must be its sole parent. If parent verification fails, the
  adapter discards commit-page paths and returns incomplete for that event; it does
  not fall back to compare.
- Commit-file pagination follows only the response's `rel="next"` Link. The next
  URL must be HTTPS on `api.github.com`, target the same canonical repository and
  exact commit SHA, contain only the expected page/per-page query, advance to an
  unseen page, and stay within RG-009's 10-page and 1,000-path limits. Missing,
  malformed, cyclic, cross-host, cross-repository, or inconsistent pagination is
  incomplete. A final page without `next` proves completeness, including an empty
  set; a `next` link at either bound proves incompleteness.
- Multi-commit push and PR evidence requests the exact immutable
  `base...head` SHA pair without commit-pagination parameters. Response identity
  must agree with the requested base and head. GitHub documents that the response's
  file list describes the entire comparison but is capped at 300 files. Therefore
  zero through 299 valid unique file records with a complete response are complete;
  exactly 300 is always incomplete even when no pagination link is present.
- A current-PR metadata response must report the requested repository/number and
  valid current base/head SHAs. Those SHAs are frozen for every matching issue
  comment in that refresh and passed to the same immutable-compare proof. A later
  refresh may capture a different pair and must retain `current-pr` provenance.
- Every file record requires a valid normalized `filename` and status exactly one of
  `added`, `removed`, `modified`, `renamed`, `copied`, `changed`, or `unchanged`.
  A rename additionally requires a valid `previous_filename`; both old and new
  paths enter the normalized set under RG-002. Other statuses contribute `filename`.
  A commit response requires exact requested `sha`, one consistent `parents[].sha`
  list, and valid files. The HTTP client does not follow redirects for these
  operations; every `3xx` is the failed outcome below. For compare and PR responses,
  both the dispatched request URL and the JSON `url` member must parse as HTTPS on
  `api.github.com`, with no query, fragment, credentials, or trailing slash.
  `EscapedPath` must contain no percent escape. Literal owner/repository path
  components must canonically equal the request;
  SHA/number path components must equal the lowercase exact request. A compare path
  is exactly `/repos/{owner}/{repo}/compare/{base}...{head}` and also requires
  `base_commit.sha=base`; its complete files are bound to that immutable request. A PR
  path is exactly `/repos/{owner}/{repo}/pulls/{number}` and also requires exact
  `number`, `base.repo.full_name` canonically equal to the requested repository, and
  valid base/head SHAs. Unknown object members are ignored;
  invalid JSON, wrong field types, missing required fields, unknown statuses,
  duplicate file records, malformed paths, identity mismatch, conflicting repeated
  page metadata, or any invalid file record makes the whole outcome incomplete. No
  valid-looking subset is admitted.
- Endpoint success never overrides RG-009. Exceeding page, per-entity path, global
  path, request, queue, or local-work capacity is incomplete for affected evidence.

#### Mutation, Deletion, and Repeated Observation

- Event-time descriptors contain immutable object IDs, never branch names or PR
  number alone. A force-push or later PR update therefore cannot change evidence
  already acquired for an exact descriptor. If GitHub no longer serves an exact
  commit or comparison, the result is unavailable; current branch/PR files are not
  substituted for event-time evidence.
- Complete cached evidence for the exact immutable descriptor may continue to serve
  after its commit, fork, branch, or PR becomes unavailable, subject to RG-005. An
  unavailable lookup with no valid cache entry remains unavailable and produces
  unknown path membership.
- Repeated observations with the same descriptor share one in-flight request/cache
  result; per-event commit-parent applicability is then evaluated independently. A
  later event carrying a changed SHA pair gets a new identity.
  Commit pages cannot mutate by contract; any repeated SHA/parent mismatch is
  treated as malformed incomplete evidence rather than mixed across pages.
- Repository renames continue to require the user's canonical selection behavior
  from v0.1.0. Redirects may not silently change repository evidence identity; the
  final response must still satisfy the selected repository and exact object facts.

#### Typed Outcomes and Failure Handling

The adapter returns exactly one of these normalized outcomes for each evidence
descriptor:

| Outcome | Meaning |
| --- | --- |
| `complete(paths, provenance)` | Fully proven valid set, including empty; may decide member/not-member |
| `unsupported(reason)` | Event lacks a supported evidence form; membership is unknown |
| `incomplete(reason)` | Hard cap, budget, malformed data, or failed completeness proof; membership is unknown |
| `unavailable(reason)` | Exact repository/entity no longer exists or cannot be resolved; membership is unknown |
| `denied(reason)` | Authentication or authorization does not permit the lookup; membership is unknown |
| `rate-limited(retry-at)` | GitHub instructed delayed work; membership is unknown |
| `failed(reason)` | Timeout, transport, or temporary server failure; membership is unknown |
| `canceled` | Refresh/shutdown canceled the operation; no partial outcome is published |

- Only `complete`, including qualified `current-pr` completeness, may feed the
  matcher. No other outcome is converted to an empty set. Domain/application code
  receives no HTTP status, JSON payload, Link, or response-header type.
- Each HTTP request retains the shipped 30-second timeout. The complete enrichment
  phase has a 60-second deadline within the parent refresh context. Shutdown or
  superseding cancellation stops queued/in-flight work promptly. There is no
  application-level same-refresh retry; a later refresh may retry within a fresh
  RG-009 ledger.
- Expiry of that 60-second phase deadline after a successful source poll converts
  every unsettled admitted work unit to `failed(timeout)`, stops dispatch, and permits
  one atomic `CURRENT` publication with quantitative unknown outcomes. Parent refresh,
  shutdown, or superseding cancellation instead publishes nothing and retains the
  previous snapshot; it is not converted into timeout unknowns.
- A successful PR-metadata result whose derived compare has not yet entered the
  second-stage queue still receives exactly one terminal outcome if dispatch stops:
  phase deadline gives `failed(timeout)`, a GitHub rate stop gives the same
  `rate-limited(retry-at)`, and queue/request capacity gives `incomplete(budget)`.
  No current-PR event remains outcome-less because its compare key was derived after
  the stop condition.
- `401` is denied. `403` without rate-limit evidence is denied. `404`/`409` for an
  exact entity or immutable object is unavailable. Unexpected `3xx`, unsolicited
  `304`, and `400`/`406`/`422` without rate-limit evidence are failed adapter/API
  operations. `5xx`, timeout, and transport failures are failed. A `2xx` that fails
  schema, identity, path, pagination, or completeness checks is
  incomplete/malformed.
- `403` or `429` with valid `Retry-After`, or exhausted
  `X-RateLimit-Remaining` with valid `X-RateLimit-Reset`, is rate-limited until the
  latest instructed time. A `429` or documented secondary-limit response without a
  usable time uses a minimum 60-second delay. New enrichment dispatch stops, queued
  work receives the same bounded rate-limit outcome, and polling resumes no earlier
  than both GitHub's existing poll interval and that retry time. No immediate retry
  is attempted.
- User-visible errors contain only the operation class, selected repository/entity
  reference safe for display, sanitized outcome, and retry timing where applicable.
  They never contain authorization values, raw response bodies, request dumps,
  transport structs, private payload fields unrelated to the message, or stack
  traces.

#### Atomic Refresh Impact

- Direct evidence, valid cache hits, and all bounded attempted enrichment outcomes
  are collected before membership and aggregates are published. One refresh emits
  one complete prepared outcome set; it never progressively publishes memberships
  as requests finish.
- Mixed complete, unsupported, incomplete, unavailable, denied, rate-limited, and
  failed results do not invalidate repository identity evidence. Repository Scopes
  remain evaluable; path Scopes retain explicit outcomes for RG-004 to present.
- Cancellation before publication leaves the previous successful snapshot intact.
  A later successful refresh recomputes all retained-event memberships against its
  own fixed evidence set and clears only conditions that actually recovered.

### RG-004 Unknown-Membership Product Policy

This gate is closed by the following lower-bound, inspectable-unknown policy. Each
retained normalized event has exactly one `member`, `not-member`, or `unknown(reason)`
outcome for every selected path Scope in the event's repository. Repository Scope
membership remains independently known from repository identity.

#### Aggregation and Coverage

- Path-Scope category/activity counts include only `member` events. `not-member`
  and `unknown` never contribute. An unknown count is maintained independently for
  each Scope, so one event may be a member of one Scope and unknown in another.
- Every path Scope retains `member`, `not-member`, `unknown`, total evaluated, and
  qualified `current-pr` counts outside rendering. Overview always presents activity
  with unknown coverage: `N activity` when unknown is zero, or
  `N activity · U unknown` when nonzero. The activity count is a lower bound with
  respect to unknown evidence and product copy says so in detailed help/context.
- Complete `current-pr` evidence selected under RG-003 may decide member or
  not-member and member events contribute to activity. The Scope also reports
  `Q current PR`, counting only `member` outcomes decided from complete evidence with
  that provenance. It does not count not-member or incomplete attempts, is visibly
  qualified, and is never described as event-time evidence. Activity copy
  therefore reads, for example, `12 activity · 2 current PR · 3 unknown`, where the
  two qualified members are included in 12.
- Each unknown has exactly one primary reason group: `unsupported`, `incomplete`
  (including malformed, hard-cap, queue, request, path, or matcher budget),
  `unavailable`, `denied`, `rate-limited`, or `failed`. The total is always
  visible. Detailed/wide context provides a deterministic breakdown in that order
  and actionable retry/permission timing where available.
- Zero confirmed members with zero unknown renders `No activity`. Zero confirmed
  members with unknown evidence renders `No confirmed activity · U unknown`; an
  all-unknown Scope remains a visible configured row and never renders as empty.

#### Stream, Rain, and Interesting Now

- Stream includes a normalized event once when it is a member of any active Scope
  or unknown for any active path Scope. It retains reverse-chronological event order.
  The row lists confirmed member Scope context and explicit `? scope`/`unresolved`
  context for unknown Scopes; current-PR member context carries `current PR`. An
  event that is only not-member for all active Scopes is omitted.
- Unknown Stream rows are investigatory context, not members: they do not increment
  activity, Rain, or strip counts. Multi-Scope membership and unknown labels remain
  on one source-event row and follow RG-012's bounded overlap presentation.
- Rain creates items only for `member` outcomes. An event unknown in a column creates
  no item there, while that column/header retains its unknown count. A member based
  on current-PR evidence is admitted but uses a non-color `~` qualifier alongside
  its category glyph and is included in the column's `current PR` count.
- `Interesting Now` selects only events with at least one confirmed member outcome.
  Unknown-only events are ineligible; unknown counts remain visible in Rain/strip
  context. An eligible event with current-PR membership labels that Scope
  `current PR`. If it is member in one Scope and unknown in another, only confirmed
  member context makes it eligible and the other Scope's unknown counter remains.
- Responsive layouts may collapse reason detail before totals, but every hidden
  unknown/current-PR/status detail is reachable or represented by RG-012's overflow
  accounting. Color is never the only unknown or qualification encoding.

#### Freshness and Combined State

Source freshness and secondary conditions are orthogonal prepared-state dimensions:

| Source state | Meaning |
| --- | --- |
| `LOADING` | No source refresh has completed |
| `ERROR` | No successful source snapshot exists and source/required initial selection failed |
| `STALE` | A previous atomic snapshot remains after the latest source poll failed |
| `CURRENT` | The latest source poll succeeded, including a vacuous zero-repository phase after successful expansion, even if some path evidence is unknown |

- A successful source poll with unknown enrichment publishes `CURRENT` repository
  data plus `PATH ?U`; it is not relabeled stale or empty. After prior complete data,
  a new successful poll atomically replaces it with the new current event set and
  explicit unknowns. Old memberships are never attached to different current events.
- A failed source poll publishes no new partial snapshot. The previous snapshot,
  including its prior path coverage and qualifications, remains `STALE`; with no
  previous success the state is `ERROR`. Repository rows never become stale solely
  because path evidence is unknown.
- Cache disable is intentional context, not degradation. Cache failure is
  `CACHE DEGRADED`; if bounded GitHub fallback reacquires every needed set, path
  coverage may remain complete. Otherwise both `CACHE DEGRADED` and `PATH ?U` remain.
- A failed re-expansion with a previous selection is `SELECTION STALE` while polling
  that fixed selection may still produce `CURRENT` event data. Initial organization-
  only expansion failure has no selection and is `ERROR`; RG-010 closes its copy.
- Source/enrichment rate limiting adds `RATE LIMITED <retry>` and does not erase
  `CURRENT`, `STALE`, path, cache, selection, or truncation truth. A source request
  rate limit produces `ERROR`/`STALE`; an enrichment-only limit may coexist with
  `CURRENT` and `PATH ?U`.
- After the mandatory primary source state, secondary badges use this fixed narrow-
  width priority: `RATE LIMITED`, `SELECTION STALE`, `PATH ?U`, `CURRENT PR Q`,
  `CACHE DEGRADED`, then `TRUNCATED`. All applicable badges remain in prepared
  state. If dimensions hide any, the last visible slot becomes `+N status`, with
  detail reachable from the applicable view/help contract.

#### Atomicity, Retry, and Recovery

- One refresh evaluates every retained event against every applicable Scope after
  all bounded evidence outcomes settle, then publishes events, memberships, direct
  aggregates, coverage counts, causes, and qualifications atomically. Rendering does
  not infer unknown from errors or missing rows.
- Incomplete, unavailable, denied, rate-limited, failed, and budget-limited evidence
  is retried in deterministic RG-009 order on the next
  scheduled or manual refresh allowed by GitHub retry/poll timing. There is no
  independent background or tight retry loop.
- A successful retry replaces the affected outcome and recomputes every dependent
  Scope atomically. Each reason counter and badge clears only when no current outcome
  still requires it. Partial recovery clears recovered causes without clearing
  unrelated unknown, stale, selection, cache, rate, qualification, or truncation
  state.
- Cancellation before publication retains the previous complete prepared snapshot.
  Unknown is never synthesized for canceled partial work, and recovery never mixes
  results from different refresh ledgers or selection snapshots.

### RG-005 SQLite Cache Contract

This gate is closed by the following disposable, enrichment-only cache contract. A
cache result can avoid GitHub work but cannot change evidence identity,
completeness, provenance, matching, or publication semantics.

#### Location, Ownership, and Contents

- The fixed cache directory is `orgtop` beneath Go's `os.UserCacheDir`; the database
  is `enrichment-v1.db` and the maintenance lock is `enrichment-v1.lock`. An empty or
  failed user-cache lookup is cache unavailable, never a fallback to the working,
  home, or configuration directory. There is no v0.2.0 cache-path override.
- On POSIX systems OrgTop creates the directory with mode `0700` and database, lock,
  and SQLite sidecar files with mode `0600`, narrows broader existing permissions
  before use, and rejects symlinks or non-directory/non-regular objects at those
  paths. The directory and mutable files must be owned by the effective user; files
  must have one link. Path inspection and mutation use no-follow, directory-relative
  operations where the platform supports them, under the maintenance lock and a
  restrictive creation mask, so a check cannot be raced into following another
  object. On Windows OrgTop uses handle-based type/owner checks, rejects reparse
  points, and requires the cache directory and mutable files to be owned by the
  current user under inherited ACLs that do not grant another user write access.
  Permission/ownership repair failure follows the degraded policy below.
- The only persistent records are a typed immutable commit or compare descriptor,
  the proof facts needed to validate that descriptor, normalized changed paths,
  acquisition/use times, and schema bookkeeping. Repository keys are canonical
  case-folded `owner/name`; SHAs are normalized 40-digit lowercase hexadecimal.
  Scope identity, event identity, PR number, provenance, credentials, authorization
  or response headers, validators, raw payloads, rendered state, errors, retry data,
  and historical or speculative observations are not stored.
- Direct-event singleton paths, unsupported evidence, and every non-`complete`
  RG-003 outcome bypass persistence. Both a complete non-empty path set (positive
  evidence) and a complete empty path set (negative membership evidence) are stored.
  A denied, unavailable, incomplete, rate-limited, failed, or canceled result is
  never a persistent negative cache entry.

#### Version 1 Schema and Atomic Records

- The database uses 4 KiB pages, foreign keys, WAL journal mode, `synchronous=NORMAL`,
  `auto_vacuum=INCREMENTAL`, application ID `0x4f524754` (`ORGT`), and
  `PRAGMA user_version=1`. Version 1 has these private logical tables; equivalent
  SQLite declarations may differ only in non-semantic index/layout details:

  ```text
  evidence(
    id INTEGER PRIMARY KEY,
    repository_key TEXT NOT NULL,
    operation TEXT NOT NULL CHECK(operation IN ('commit','compare')),
    base_sha TEXT NOT NULL,
    head_sha TEXT NOT NULL,
    verified_parent_sha TEXT NOT NULL,
    complete INTEGER NOT NULL CHECK(complete = 1),
    path_count INTEGER NOT NULL CHECK(path_count BETWEEN 0 AND 1000),
    acquired_at INTEGER NOT NULL,
    last_used_at INTEGER NOT NULL,
    UNIQUE(repository_key, operation, base_sha, head_sha)
  )
  evidence_path(
    evidence_id INTEGER NOT NULL REFERENCES evidence(id) ON DELETE CASCADE,
    ordinal INTEGER NOT NULL,
    path TEXT NOT NULL,
    PRIMARY KEY(evidence_id, ordinal),
    UNIQUE(evidence_id, path)
  )
  ```

- A compare key has exact base/head SHAs and an empty `verified_parent_sha`. A commit
  key has an empty `base_sha`, the exact head SHA, and the sole parent proven by the
  adapter in `verified_parent_sha`; a hit is usable only when that parent equals the
  requesting event's before SHA. Provenance belongs to the requesting descriptor,
  so one immutable compare may serve either event-time or qualified current-PR use
  without storing or changing provenance.
- Paths are stored once in ascending normalized byte order. A hit requires the exact
  typed key, `complete=1`, valid proof fields, exact child count, contiguous ordinals,
  unique normalized paths, and all per-entity bounds, including at most 4,096 UTF-8
  bytes in one path and 1 MiB across one evidence set. Empty child rows with
  `path_count=0` prove a complete empty set. A failed row invariant is a miss and
  queues that exact record first in RG-009's single bounded cleanup batch; reads do
  not create invalidation transactions. Malformed tables, indexes, or integrity are
  structural corruption, never a partial hit.
- One replacement uses one immediate transaction: remove the old exact-key record,
  insert its complete parent and all children, verify their count, and commit. The
  parent may exist before its children only inside that transaction. Readers observe
  either the previous complete record or the replacement, never working rows.
  Cancellation or failure rolls the transaction back; acquired API evidence remains
  valid for the current refresh even when its cache write is skipped.

#### Versioning, Freshness, and Reuse

- Bootstrap is a maintenance-lock-protected state machine, not a migration from an
  arbitrary version-0 file. With no canonical database, OrgTop first removes only
  orphaned known sidecars/tombstones, creates `enrichment-v1.bootstrap` exclusively,
  sets 4 KiB pages and incremental auto-vacuum before schema creation, and creates
  the complete v1 schema, application ID, and `user_version` in one transaction. It
  closes and atomically renames that file to the canonical name. On first open it
  enables and verifies WAL outside a transaction. A crash leaves no canonical file,
  a complete v1 file awaiting WAL enablement, or an owned bootstrap file that the
  next locked launch discards; it never exposes partial v1 tables as canonical.
- v0.2.0 defines fresh version-1 creation only and performs no in-place migration.
  Every future schema revision must add its exact one-version migration, validation,
  physical pre/post states, and crash vectors before that revision ships. Until then,
  every version other than exact v1 follows the unknown-version policy below.
- A nonzero different application ID is foreign and is preserved and bypassed. A
  pre-existing zero-ID database is ambiguous and is also preserved; only the
  exclusively created bootstrap file is eligible for zero-to-v1 initialization.
  Malformed schema carrying OrgTop's exact ID and a known version is structural
  corruption. A newer or unknown older `user_version` is not deleted or migrated:
  the process bypasses it with `CACHE DEGRADED` and directs the user to update
  OrgTop or run `--reset-cache`.
- Complete evidence is fresh for exactly 30 days from `acquired_at`; at the boundary
  it is expired. Immutable fresh evidence is reused without conditional HTTP
  validation. Expired, missing, or invalid evidence is a miss and remains stored
  only until bounded cleanup or successful exact-key replacement.
- Times are signed Unix seconds from the refresh's fixed clock. Negative values,
  overflow, or values more than five minutes in the future invalidate that record;
  smaller forward skew has age zero. Exact-key replacement sets `acquired_at` and
  `last_used_at` to refresh time, or to the maximum of refresh time and only valid
  concurrent stored timestamps. Negative, overflowing, or too-far-future stored
  timestamps are discarded rather than preserved by replacement. The one
  best-effort batched hit-touch transaction updates only `last_used_at` to that
  maximum; cache reuse never changes `acquired_at` or extends the 30-day TTL. Touch failure
  does not invalidate a proven hit, but is reported as cache degradation. Timestamps
  never determine evidence semantics.

#### Bounds and Deterministic Maintenance

| Resource | Limit |
| --- | ---: |
| Evidence records | 10,000 |
| Child path records | 250,000 |
| Hit freshness TTL | 30 days |
| Retained physical ceiling and cleanup trigger | 128 MiB |
| Temporary physical operation envelope | 160 MiB |
| SQLite busy wait per normal transaction | 250 ms |

- Physical accounting sums the main database, WAL, SHM, rollback journal if left by
  recovery, maintenance lock, and any OrgTop-owned bootstrap/reset file.
  The metric is the sum of apparent file lengths, not allocated filesystem blocks.
  Mutating transactions are serialized across processes through an exclusive
  admission region of the maintenance lock; reads hold its shared admission region
  only for their transaction. Every admission-region acquisition has the same
  250 ms limit as SQLite busy handling. The separate lifecycle region coordinates
  setup/reset.
- Replacement and batched touch reserve exactly 8 MiB of temporary WAL/sidecar
  headroom; cleanup plus incremental vacuum and its final checkpoint reserve exactly
  32 MiB. Cleanup selection is shortened to at most 8 MiB of stored path bytes.
  Admission requires `current apparent bytes + reservation <= 160 MiB` and projected
  post-checkpoint `page_count * 4,096 + other retained files <= 128 MiB`. A
  replacement also projects the exact-key deletion and must commit no more than
  10,000 evidence and 250,000 child rows. SQLite page/WAL fixtures must prove the
  fixed reservations at each maximum operation; an operation that cannot prove its
  reservation or projected state is skipped. Two processes cannot both pass
  admission. A skipped persistence write never invalidates current API evidence.
- At startup and after functional reads/writes, expiry, projected or committed row
  counts reaching either hard logical limit, or the 128 MiB trigger requests
  maintenance. Admission rejects operations projected above a hard limit. The refresh
  may perform RG-009's one batch:
  at most 100 complete evidence records and 10,000 child rows in one transaction.
  It deletes queued invalid records first, then expired records by `acquired_at`,
  then evicts least-recently-used records by `last_used_at`, `acquired_at`, and stable
  typed key. Invalid/expired ties use acquisition time and stable typed key.
  Selection is further shortened at 8 MiB of stored path bytes. It stops when no
  invalid/expired selectable row remains and row counts and apparent bytes are at or
  below 75% targets (7,500
  evidence, 187,500 paths, 96 MiB), or a batch/byte bound is spent. Expired records
  are never hits but may remain physically until later batches. Further refreshes
  continue the same order; no unbounded startup catch-up occurs.
- `wal_autocheckpoint` is 1,000 pages. After a committed deletion batch OrgTop
  runs at most 1,024 pages of incremental vacuum and then attempts one truncate
  checkpoint, under exclusive admission, the same 250 ms busy limit, and physical
  accounting. The checkpoint result must report completion; busy/incomplete
  checkpointing is deferred only when final apparent use remains at or below 128 MiB;
  otherwise cache use is disabled pending reset. OrgTop never performs full `VACUUM`.
- If pre-existing, externally grown, or interrupted files exceed 128 MiB, the
  process admits no hit or mutation and directs the user to `--reset-cache`; GitHub
  fallback and `CACHE DEGRADED` remain available rather than risking further growth.

#### Concurrency, Reset, and Failure

- Normal SQLite transactions wait at most 250 ms for busy/locked state. A contended
  SQLite or admission lock makes a read a miss for that refresh; a contended write,
  touch, checkpoint, or cleanup is skipped. The process remains interactive,
  publishes `CACHE DEGRADED`, and may try the cache again on the next refresh. It
  never opens a second cache or waits in a tight loop.
- Creation, version validation, structural rebuild, and reset use the lifecycle region of the
  private sidecar maintenance lock. Cache operations hold shared lifecycle access;
  setup/rebuild acquires exclusive access with the 250 ms startup bound and
  `--reset-cache` waits up to two seconds. Permission repair and every path mutation
  occur only after exclusive lifecycle acquisition. Lock failure changes no files,
  and no database handle remains open after releasing shared lifecycle access.
  SQLite transactions remain the record-consistency authority.
- `--reset-cache` validates the fixed location, takes the exclusive lock, closes any
  local handle, and atomically renames the main database to
  `enrichment-v1.resetting`. It then deletes original-name `-wal`, `-shm`, and
  `-journal` sidecars before deleting the tombstone and syncs the directory where
  supported. An absent cache succeeds after orphan cleanup. At every restart, a
  tombstone or absent main with known sidecars forces the same sidecar-first cleanup
  before any canonical create/open. It reports success and exits as RG-001 requires;
  any failure is sanitized and nonzero, and no fresh main opens beside stale WAL.
- Reset removes only an exact-application-ID OrgTop database or a bootstrap/tombstone
  created by OrgTop. A foreign nonzero application ID or ambiguous pre-existing
  zero-ID database is preserved and reset fails with a sanitized ownership error.
- Confirmed structural corruption of exact v1 gets one rebuild attempt per process
  using the same tombstone procedure under the exclusive lock. OrgTop never
  auto-deletes for contention, unavailable/unwritable
  storage, permission failure, or a newer/unknown schema. Rebuild failure disables
  cache work for that process.
- Unavailable, unwritable, permission-invalid, newer-version, or unrecovered cache
  state never fails an otherwise valid interactive launch. OrgTop bypasses cache,
  performs bounded GitHub fallback, and exposes a sanitized `CACHE DEGRADED` cause
  with reset/update/permission guidance. Failed fallback evidence independently
  produces RG-004 `PATH ?U`; cache failure alone cannot make complete reacquired
  evidence unknown. `--no-cache` performs no path resolution, lock, SQLite, reset,
  cleanup, or status work and is intentional rather than degraded.

### RG-006 Rain Field Contract

This gate is closed by the following bounded repeating-field contract. Rain is an
ambient view of direct current-snapshot facts: motion is decorative arrival context,
and continuing motion means only that an event remains in the selected recency
window; shared RG-008 style and removal communicate exact factual age. Motion never
encodes severity, importance, anomaly, productivity, or source outcome.

#### Item Identity, Eligibility, and Lifetime

- One candidate representation is identified by normalized source event ID plus
  canonical Scope identity. Every current event with a confirmed `member` outcome
  creates one candidate for each matching repository or path Scope. Unknown and
  not-member outcomes create none. Equal event/Scope identity is one item across
  refreshes; one event matching three Scopes is three independently bounded items.
- Rain has a session-local window of `15m`, `30m`, or `60m`, defaulting to `60m`.
  In Rain, `-` selects the next shorter preset and `+` the next longer; either key at
  its endpoint is a no-op. The selected `window 15m|30m|60m` is visible, survives
  view changes and resize, and is not persisted after exit.
- An item is eligible while its effective Rain age is less than the selected window.
  The exact boundary removes it. RG-008's fixed `new`/`recent`/`aging` thresholds
  still choose style; selecting a shorter window does not rescale or reinterpret
  those shared states. Expired at 60 minutes is therefore always removed, while a
  shorter window intentionally removes an item earlier.
- Changing the window immediately reconciles against the current normalized
  snapshot. Shortening removes newly out-of-window items. Lengthening restores
  eligible member representations under the normal column/global admission rules;
  surviving phases remain and restored historical items use deterministic
  distributed startup placement rather than pretending to be new arrivals.

#### Tick and Repeating Motion

- The application owns exactly one Rain timer chain, started once and continued
  while any Overview, Stream, or Rain view is active. Handling generation `G`
  schedules only `G+1`; duplicate, older-generation, equal-time, or older-time
  messages do not advance or start another chain. A message carries its generation
  and explicit logical timestamp; state transitions never read the host clock.
- The first successful snapshot sets `cursor` to its explicit reference time and
  remainder zero. Each later accepted tick saves `oldCursor=cursor` and
  `oldRemainder=remainder`, computes `elapsed=at-oldCursor`,
  `total=elapsed+oldRemainder`, `steps=floor(total/500ms)`, and
  `remainder=total mod 500ms`, then sets `cursor=at` and advances effective age by
  exactly `elapsed`. One message
  applies steps modulo field height without replaying missed frames.
- Before an unpaused successful refresh is reconciled, Rain applies that snapshot's
  reference time through the same advance transition, including remainder, and then
  uses the reference to recompute event age without decreasing surviving age. The
  cursor is therefore already at the refresh reference before the next tick and no
  interval is counted twice. A reference not after the cursor advances nothing and
  cannot move cursor or age backward. New and surviving event age is calculated
  against `max(snapshot-reference,cursor)`, so publication after newer ticks cannot
  under-age an item.
- Each item stores one bounded unsigned-64 `rowPhase`, not cumulative runtime steps.
  Distributed items initialize it to the full row hash, including at zero height;
  runtime arrivals initialize it to zero. Display reduces it modulo positive height,
  and each unpaused transition sets
  `rowPhase=(rowPhase+steps) mod height` when height is positive. At zero height,
  age/expiry still advance and `rowPhase` remains unchanged with no modulo. Moving past the
  last row wraps to row zero, so items continuously repeat until their selected
  lifetime ends. At one row of field height they remain on that row; at no usable
  field row state remains bounded and the view renders its explicit constrained
  state instead of running a movement loop.
- A newly observed membership after the first successful Rain snapshot enters at
  row zero on publication. The first snapshot and items restored by a larger window
  distribute their initial rows with the stable placement function below so startup
  is a steady field rather than a simultaneous wall. Animation phase is retained for
  surviving event/Scope identities through refresh and view changes.
- A continuously eligible candidate first admitted after prior column/global/paused
  omission is historical rather than a new publication arrival and uses distributed
  placement. Only a membership first observed in an unpaused refresh or retained in
  the paused queue enters at row zero.
- Unpaused effective age advances by the complete explicit tick delta, not only the
  modulo movement steps. A successful refresh reconciles it to the event timestamp
  and that snapshot's explicit reference time without decreasing a surviving age.
  Thus delayed ticks can expire an item in one transition even though movement needs
  no catch-up loop.

#### Horizontal Placement and Collisions

- One logical Rain slot is two terminal cells: the RG-008 category glyph followed by
  `~` for qualified current-PR membership or a space otherwise. Narrow clipping may
  hide the qualifier only in RG-006's exact one-cell-column case, which increments
  `clipped qualifications` and keeps the qualification in help/context; color is
  never its replacement.
- The exact horizontal slot count for column interior width `C` is zero for `C<=0`,
  one one-cell slot for `C=1`, and `floor(C/2)` two-cell slots for `C>=2`. Desired
  slot hashing and probing use only this function; one-cell slots apply the clipped
  qualification rule above.
- Stable placement is standard unsigned 64-bit FNV-1a with offset basis
  `0xcbf29ce484222325`, prime `0x100000001b3`, modulo-2^64 multiplication, and
  unsigned modulo. Its exact byte stream is ASCII purpose prefix, byte `00`, UTF-8
  normalized event ID, byte `00`, then `scope-key-v1`. That key encodes the
  lowercase repository key as a four-byte big-endian length plus UTF-8 bytes, then
  kind byte `R` or `P`; a path Scope appends each canonical matcher token as `L` plus
  four-byte length plus literal UTF-8 bytes, `S` for single wildcard, `D` for
  recursive wildcard, or `X` for separator. `scope-key-v1` names this encoding and
  contributes no literal version bytes. Prefix `rain-row-v1` selects an initial row
  modulo positive field height; `rain-slot-v1` selects a desired horizontal slot
  modulo the positive slot count defined above. New runtime arrivals override only
  the row result with row zero.
- For each column row, items are laid out by event timestamp newest first, then event
  ID byte order. Each takes its desired slot or probes right with wraparound to the
  first free slot. Once every slot in that row is occupied, additional retained items
  group into their desired slot. The cell keeps the deterministic first occupant's
  category/qualification token; prepared column state exposes `N collisions`, and
  full help/context explains that count. `N collisions` is exactly the number of
  admitted items on that prepared page that could not obtain a unique slot after a
  full-row probe; successful probes do not increment it. Grouped items remain
  admitted and age/move independently; they are not omissions.

#### Capacity and Refresh Reconciliation

- Candidates in each Scope are ordered by event timestamp newest first, event ID,
  then canonical Scope identity, and truncated to RG-009's 50-item column cap.
  Global admission then takes one remaining candidate per Scope in stable Scope order
  repeatedly until no candidate remains or the 500-item global cap is reached. This
  deterministic round-robin prevents a busy Scope from consuming global capacity;
  every representation still spends one column and one global item. If the cap ends
  a partial round, the stable-order prefix receives that round's one extra item; this
  bounded one-item bias is intentional and resets only when Scope order changes.
- A successful refresh atomically reconciles by event/Scope identity. Surviving
  confirmed memberships preserve phase, newly confirmed memberships enter at row
  zero, and absent, deduplicated-away, no-longer-member, unknown, or out-of-window
  representations are removed. Admission is recomputed from the complete candidate
  set, so newer/fairer candidates may evict older admitted items. Failed source
  refreshes retain the previous Rain snapshot under RG-004 stale semantics.
- Prepared state retains total candidate, admitted, column/global omitted, grouped
  collision, and hidden-page counts. Rendering only consumes that prepared state and
  never hashes, admits, collides, ages, or moves items.

#### Pause, Arrivals, and Resume

- Before the first successful snapshot, `p` is a no-op because no Rain cursor or
  field exists. After first success, `p` in Rain records the current logical cursor
  and toggles pause. While paused,
  ticks may be scheduled but advance neither item phase, effective Rain age, style,
  expiry, nor cursor remainder. Resume sets `needsRebase`; the first temporal input
  newer than the frozen cursor, whether tick or successful-refresh reference, sets
  the cursor without advancing phase/age and clears `needsRebase`. Equal/older inputs
  leave it set. Later inputs continue normally, so paused time never catches up.
  Polling, enrichment, refresh publication,
  navigation, resize, paging, and window controls continue.
- Refresh while paused still removes representations whose event or confirmed
  membership disappeared. Surviving field items retain frozen phase/age. Newly
  confirmed representations are queued rather than admitted; each stores the age
  calculated against the frozen pause reference (events after it clamp to age zero).
  A queued representation that leaves the snapshot is removed.
- The paused queue holds at most 100 representations in addition to the 500-item
  field. On each paused snapshot its candidates are exactly currently eligible new
  representations not already in the frozen field. For each Scope it orders newest
  event first, then event ID; global retention takes one per Scope in stable
  round-robin order until 100. `paused omitted` is current queue candidates minus
  retained queue entries, including a previously retained entry displaced by a newer
  candidate. It is not cumulative across refreshes. Multi-Scope events consume one
  queue slot per representation.
- Resume merges surviving field items and retained queued arrivals, applies the same
  50-column/500-global fair admission, places admitted queued items at row zero, and
  clears the queue atomically. Older field items may be evicted. Paused omissions do
  not materialize on resume; a later successful unpaused refresh may reconsider them
  from its current complete snapshot. Window changes while paused reconcile both
  frozen field and current queue eligibility; restored historical field items use
  distributed placement and do not consume paused-arrival capacity.

#### Columns, Paging, and Resize

- Rain stores items for all active Scopes ordered by lowercase repository key byte
  order, repository Scope before path Scope, then canonical matcher-token encoding
  byte order. RG-012 uses this order when composing Rain with other views. Rain field width `W` is the
  complete terminal width; the field has no horizontal padding/border, while headers
  and footers occupy separate rows. For `N>0`, one page contains
  `K=min(N,max(1,floor((W+1)/13)))` consecutive Scopes with one-cell separators.
  Fixed pages begin at zero-based indexes `0,K,2K...`; the final page may be partial.
  For page start `S`, `M=min(K,N-S)` actual columns use `M-1` separators; remaining
  width is divided by `M` and extra cells go to leftmost columns.
  Width below 12 is one best-effort column with explicit hidden detail accounting.
  `N=0` has one empty-state page and no column arithmetic.
- `[` selects the previous page and `]` the next, wrapping at both ends. The header
  shows one-based `scopes A-B of N` (or the equivalent one-Scope form) plus hidden Scope/item
  counts. Manual paging, rather than tick-driven rotation, keeps motion stable while
  making every Scope reachable without starvation.
- Page and anchor Scope survive view changes and refresh. Resize or any Scope-order/
  count change recomputes columns
  and chooses `floor(anchor-index/K)*K`, the unique fixed page containing the prior
  first-visible anchor. If that Scope no longer exists, its old index selects the
  successor now at that index, or the final predecessor when no successor exists.
  At `N=0` the anchor clears; the next nonempty set selects its first Scope.
  Item row becomes retained `rowPhase mod new-positive-height`; desired slot is
  rehashed modulo new positive slot count, then collision preparation reruns. Resize
  never changes age, admission, pause state, queue order, or omission totals.
- A column with exactly one usable field cell has one one-cell slot: it shows category
  but clips a current-PR `~` with explicit clipped-detail accounting. A column with
  zero usable cells or field rows renders no item token; admitted items remain in
  state and are included in hidden-item accounting. Hash modulo and collision probing
  run only for positive row and slot counts.
- Counters are disjoint: `hidden scopes` is off-page Scopes; `hidden items` is
  admitted items in those Scopes plus admitted visible-Scope items when row/slot
  count is zero; `clipped qualifications` is visible one-cell tokens whose `~` cannot
  render; `collisions` is the grouped-item definition above; and `omitted` is only
  capacity rejection. One representation contributes to at most one hidden-item
  cause and is never counted hidden merely because it is grouped.

### RG-007 Interesting Now Selection Contract

This gate is closed by the following direct recent-activity contract. “Interesting”
means only a bounded Scope-fair sample suitable for the compact strip; it is not an
importance, anomaly, severity, productivity, baseline, or derived-signal judgement.

#### Eligibility and Identity

- A candidate is one normalized source event from the retained current or stale
  snapshot whose effective strip age is `0 <= age < 15m` and which has at least one
  confirmed `member` outcome in an active repository or path Scope. At exactly 15
  minutes it is ineligible. Unknown-only and all-not-member events are ineligible;
  an event member in one Scope and unknown in another is eligible only through its
  confirmed membership.
- Source-event ID is the strip identity. Snapshot normalization has already removed
  repeated IDs by keeping the first canonical-input occurrence before global recency
  sorting; the strip performs no second payload choice. Distinct source IDs remain
  distinct even when actor, repository, entity kind/reference, commit, PR, issue, or
  description is equal. There is no entity/actor clustering or event synthesis.
- One eligible event matching several Scopes is one candidate and one stored entry,
  not one representation per Scope. It retains every confirmed matching Scope in
  RG-006 stable Scope order and retains current-PR provenance per affected Scope.
  Unknown Scope context is not converted to membership; RG-004's separate unknown
  accounting remains visible outside the entry.
- The fixed 15-minute strip window is independent of Rain's selected 15/30/60-minute
  field window and its `-`/`+` controls. Rain pause also does not freeze the strip.

#### Scope-Fair Selection and Ordering

- Each active Scope has a candidate queue ordered by event timestamp descending and
  source event ID ascending by UTF-8 byte order, matching the shipped string
  comparator. Scope turns use RG-006's repository/kind/matcher order. Each turn
  examines and advances past exactly one queue event: it selects that event if not
  already selected, while an event selected through another Scope consumes the turn
  without another selection. Rounds repeat until 20 unique events are stored or all
  queue cursors are exhausted. Overlap therefore consumes each matched Scope's fair
  turn rather than granting extra entries.
- The first successful snapshot starts at the first Scope. Tick recomputation for
  that snapshot retains the same start. Each successful refresh starts at the saved
  next Scope and, after selecting, saves the Scope after the turn that reached 20 as
  the next refresh's start. If fewer than 20 are selected after exhausting all
  queues, the next start remains unchanged. Scope removal chooses its stable-order
  successor now at the removed Scope's old zero-based index, or the final predecessor
  when no successor exists; an empty set clears the anchor and the next nonempty set
  starts first. Prepared state retains the current sponsoring/start facts so the
  rotation is inspectable.
- The Scope whose turn first selects an event is its sponsoring Scope. The entry
  still carries all matching Scopes, so sponsorship affects only explainable
  selection/order and never membership. If the 20-entry bound ends a partial round,
  that refresh's rotated-order prefix receives the final turns; the saved next start
  prevents permanent starvation without becoming an event score.
- Stored order is exact selection order, not a later global-recency sort. The first
  five stored entries are visible when height permits. Thus both stored and visible
  choices preserve the same Scope fairness. Prepared state retains unique eligible,
  stored, visible, and omitted (`eligible-stored`) totals; it never calls the result
  “top,” “important,” “hot,” “unusual,” or ranked.

#### Entry Explanation

- Prepared entries retain the normalized event ID/timestamp, repository, RG-008
  category, optional actor, entity kind/reference, concise description, effective
  age/text, sponsoring Scope, ordered confirmed matching Scopes, and per-Scope
  current-PR qualification. These are direct normalized/application facts; no
  renderer derives or ranks them.
- Textual age is deterministic and truncates toward zero: whole seconds below one
  minute (`Ns`), whole minutes below one hour (`Nm`), whole hours below one day
  (`Nh`), then whole days (`Nd`). Future timestamps clamp to `0s`; therefore an age
  of `14m59.999s` renders `14m`, never the ineligible boundary `15m` early.
- At full width one line presents category/action, actor when present, entity or
  repository context, sponsoring Scope and its `current PR` qualification when
  applicable, `+N scopes` for additional confirmed matches, `Q current PR` counting
  every qualified confirmed Scope, and textual age. RG-008
  rich then compact category forms apply. Missing optional actor/entity detail is
  omitted rather than inferred; repository and sponsoring Scope always remain.
- Width reduction may shorten labels under RG-012, but preserves in order: action or
  category, repository, sponsoring Scope, textual age, current-PR qualification,
  additional-Scope count, then actor/entity detail. The final minimal logical form is
  `glyph repository scope age`; RG-012 may shorten its two labels but not substitute
  other facts. Switching to Stream with `2` makes the same retained source event and
  complete confirmed/qualified Scope context reachable through Stream scrolling;
  this is the strip-specific destination for shortened matching-Scope detail. Color
  is never required to understand why an entry appears.

#### Refresh, Time, and Degraded State

- A successful atomic refresh replaces candidates and recomputes selection from its
  complete snapshot. Source-event survivors have no sticky slot; newer or fairer
  direct events may replace them. Membership changes atomically add/remove affected
  queues, and a current-PR member remains visibly qualified.
- The application-wide explicit RG-006 tick timestamp advances a separate monotonic
  strip reference even while Rain is paused or hidden. The first success initializes
  it to the snapshot reference; every later accepted tick or successful snapshot sets
  it to `max(previous,tick-at,snapshot-reference)`. Event age is
  `max(0,strip-reference-event-timestamp)`. Each accepted transition recomputes
  eligibility/selection from the retained snapshot; repeated, stale-generation, or
  older/equal timestamps do not change strip reference or ages. A successful
  publication still replaces its snapshot and advances the documented refresh
  rotation even when its reference is older. Rendering never reads wall time.
- A failed source refresh retains the previous atomic snapshot and `STALE` state.
  Its strip continues aging against explicit ticks: entries disappear at 15 minutes
  and no post-failure event is invented. Enrichment-only unknown outcomes compose
  through RG-004 without invalidating independently confirmed repository membership.

#### Height Collapse

- Let `B` be body rows remaining for the Rain field plus strip after shared header,
  status, footer, and help rows; these chrome rows are not included in `B`. Rain gives
  the activity field at least three rows whenever `B>=3`.
- Define `D` as rendered entries, `H=stored-D` as retained-hidden, and
  `O=eligible-stored` as capacity-omitted. With eligible entries and `B<=3`, all `B`
  rows belong to the field and the Rain footer replaces optional hints before the
  mandatory quit hint with `interesting: 0 shown/H hidden/O omitted`. At `B=4`,
  three field rows plus that count-only line render in the body. At `B>=5`,
  `D=min(5,stored,B-4)`, actual strip rows are `1+D`, field rows are `B-1-D`, and the
  title is `Interesting Now: D shown · H hidden · O omitted` followed by those `D`
  entries. At constrained width it becomes `I: D shown H hidden O omitted`, then
  `I:D/H/O`; optional navigation hints drop before that accounting, while the
  mandatory quit hint retains FR-011 priority. When `B<=3`, widths 17 and above fit
  worst-case compact accounting plus `q quit`; at widths 6-16 `q I+` renders when any
  strip entry is hidden/omitted (`q quit` otherwise). `I+` is the explicit overflow
  indicator, and `2` reaches every retained eligible source event in Stream. Below six
  dimensions are FR-011 deterministic best effort.
- With zero eligible events and `B>=4`, the strip uses exactly one line,
  `Interesting Now: no recent activity`, and all other body rows remain field rows.
  With zero eligible and `B<=3`, no strip/hidden notice is needed. Collapse changes
  only visible count, never stored selection/order or the 20-entry bound.

### RG-008 Shared Visual Semantics Contract

This gate is closed by the following category, recency-mapping, and capability
contract. Semantic category values and each view's age-to-recency mapping are
calculated in prepared state outside rendering. Every view uses the same mapping;
RG-006/RG-007 define which explicit logical reference supplies each view's age.

#### Category Vocabulary

`comment`, and `other`. Stream rendered explicit rich or compact text and used no

and adds these shared compact glyphs:

| `pull_request` | `pull request` | `pull` | `↗` | `R` |

  assigns an ad hoc glyph or style to an unknown input.
- These glyphs mean event category only. In particular, `↗` does not mean growth,
  `◇` does not mean approval, `○` does not mean status, and none means success,
  failure, deployment, anomaly, priority, productivity, or importance.

#### Discrete Recency

- Recency is calculated from a non-negative prepared event age. An event timestamp
  after its applicable reference is clamped to age zero. Rendering never calls the
  host clock to recalculate age.
- The exact half-open states are `new` for `0 <= age < 5m`, `recent` for
  `5m <= age < 15m`, `aging` for `15m <= age < 60m`, and `expired` for
  `age >= 60m`.
- Overview/Stream use the latest published snapshot reference. Unpaused Rain uses
  RG-006's effective cursor age and freezes it during Rain pause. Interesting Now
  uses RG-007's monotonic strip reference and never freezes. A successful refresh or
  accepted tick recomputes the affected prepared states atomically; all apply the
  exact thresholds above even when their instantaneous ages intentionally differ.
- `expired` removes a Rain item rather than merely hiding it. It does not delete a
  normalized snapshot event or independently remove a Stream row; any
  `Interesting Now` retention rule must be no longer than this shared expiry and is
  closed under RG-007.

#### Semantic Styles and Fallback

| Recency | Full/reduced color | No-color reinforcement | Rain behavior |
| --- | --- | --- | --- |
| `new` | strongest foreground accent and bold | bold glyph/text | visible while inside selected Rain window |
| `recent` | normal foreground accent | normal glyph/text | visible while inside selected Rain window |
| `aging` | neutral, reduced intensity | faint when supported, otherwise normal | visible while inside selected Rain window |
| `expired` | neutral, reduced intensity | faint when supported, otherwise normal | removed |

- Color and intensity reinforce recency only; category remains encoded by glyph or
  text. The palette must not use conventional success/error coloring to imply an
  unsupported event outcome. Existing chrome colors for transport, freshness, and
  errors remain separate semantic roles and cannot be reused to recolor an event
  category.
- Capability is an injectable enum `truecolor`, `ansi`, or `no-color`. Production
  resolution uses the pinned Charm color-profile stack; `TERM=dumb` or non-empty
  `NO_COLOR` forces `no-color`. `truecolor` uses the full palette, `ansi` its nearest
  reduced palette, and `no-color` no color. Bold/faint are optional reinforcement and
  their absence never removes text or glyph meaning.
- When the effective profile cannot render distinct intensity attributes, Rain
  prepares and displays `recency: N new · R recent · A aging` in its legend/context,
  shortened to `age N/R/A`; the counts cover admitted visible-page items and update
  from the same effective Rain age. If constrained dimensions hide that legend, its
  hidden-legend indicator remains under RG-012 and Stream/detail textual ages remain
  reachable. Thus no-color fallback does not require a category glyph to encode two
  meanings.
- UTF-8 glyphs are selected only when the effective locale is UTF-8 and
  `TERM` is not `dumb`. Locale inspection uses the first non-empty value of
  `LC_ALL`, `LC_CTYPE`, then `LANG`; it takes the codeset after the final `.` and
  before any `@` modifier, or the complete value when no `.` exists, and recognizes
  `UTF-8` or `UTF8` case-insensitively. Thus `C.UTF-8` and `en_US.UTF8@modifier` are
  UTF-8. Otherwise the ASCII column is used. `NO_COLOR` changes color only, not the
  already selected character set.
- Capability and reference-time inputs are injectable in tests. Identical category,
  timestamp, reference time, tick, and capability inputs produce identical semantic
  values and output without a live terminal, wall-clock sleep, or color support.

### RG-009 Capacity and Verification Budget

This gate is closed by the following hard capacities and one refresh-pipeline work
ledger. A limit is part of product correctness, not an optimization target. Hitting
one never silently converts incomplete evidence into complete evidence.

#### Selection and Snapshot Capacity

| Resource | Hard limit |
| --- | ---: |
| Distinct repositories in one selection snapshot | 20 |
| Total repository and path Scopes | 100 |
| Path matchers | 100, exactly one per path Scope |
| Repository Events requests per refresh | 20, one bounded page per repository |
| Events requested per repository | 100 |
| Normalized events retained globally | newest 500 |

- Exact CLI selections are expanded and canonically deduplicated before startup.
  If their distinct repositories or Scopes exceed a limit, validation reports the
  requested and allowed counts and exits; explicit intent is never truncated.
- Organization expansion receives only repository and Scope capacity left after
  exact selections. It retains its deterministically ordered prefix and discloses
  every omitted repository count when known, or `more omitted` when bounded listing
  cannot know the total. Exact selections therefore always have capacity
  precedence. RG-010 closes the ordering and eligibility facts.
- Each selected repository contributes at most the existing newest 100 repository
  events. All returned candidates are normalized, source-identity checked,
  deduplicated, and globally reverse-chronologically ordered with the shipped stable
  tie-break before the newest 500 are retained. The retained snapshot records the
  pre-truncation unique count and reports `events: newest 500 of N` when truncated.
- Canonical input traversal for source-ID deduplication is fixed-selection repository
  order followed by each response's API order. Expanded repositories follow their
  closed RG-010 order after exact repositories. The first occurrence is retained as
  shipped; a conflicting later duplicate cannot affect strip or snapshot ordering.
- Enrichment, cache lookup, path matching, aggregation, Rain admission, and
  `Interesting Now` selection operate only on those retained events. A discarded
  candidate performs none of that work.

#### Refresh Pipeline Ledger

One startup, scheduled, or manual refresh command creates one ledger. The pipeline
is `due expansion -> fixed selection snapshot polling -> normalization and newest-500
cut -> cache/enrichment -> membership and aggregation -> atomic prepared-state
publication`. The next refresh command gets a fresh ledger. Rain ticks are a
separate pure state transition and consume no request, enrichment, cache, or matcher
budget. Internal retries remain in the current ledger and cannot reset any counter.

| Work | Per-refresh hard limit |
| --- | ---: |
| All GitHub HTTP requests | 40 |
| Organization listing | first 5 requests/pages, at most 500 listed records |
| Repository event polling | next 20 requests, one per selected repository |
| Enrichment HTTP work | at most `min(20, 40-expansion-polling)`, therefore 15 after full expansion or 20 with none |
| Distinct queued enrichment work units | 100 |
| Concurrent enrichment operations | 2 |
| Enrichment pages for one evidence identity | 10 |
| Normalized changed paths for one evidence identity | 1,000 |
| UTF-8 bytes in one normalized changed path | 4,096 |
| UTF-8 bytes across one evidence identity | 1 MiB |
| Normalized changed paths admitted across the refresh | 10,000 |
| Cache evidence reads | 500 |
| Cache replacement write transactions | 20 |
| Cache hit-touch transactions | 1, touching at most 500 read identities |
| Path-to-Scope matcher evaluations | 1,000,000 |
| Cleanup batches | 1 |
| Cleanup batch contents | 100 evidence records and 10,000 child path rows |
| Incremental-vacuum pages after cleanup | 1,024 |
| Truncate-checkpoint attempts after cleanup | 1 |

- Request shares are deterministic reservations, not parallel independent budgets.
  Due expansion may spend up to five requests first; fixed-snapshot polling may then
  spend one request for each of at most 20 repositories; enrichment receives the
  remaining global budget capped at 20. Unused expansion capacity flows forward only
  within that cap, polling never exceeds 20, and no phase borrows backward from work
  already completed.
- Every attempted HTTP request, conditional request, page, and retry spends one
  request before dispatch. Cancellation does not refund it. Rate limiting stops new
  dispatch according to RG-003; retry metadata is published, and no hidden retry
  obtains a new ledger.
- Retained events are considered newest first with shipped event tie-breaks. Work
  keys are `pr-metadata(repository-key,number)`, `commit(repository-key,head)`, or
  `compare(repository-key,base,head)`; identical keys coalesce at first occurrence.
  Every metadata and API evidence key is one queue/concurrency unit, so current-PR
  metadata and its resulting compare are two units and two HTTP requests on misses.
  Direct-event evidence is no queued unit.
- Direct immutable descriptors are cache-read in event order. Coalesced current-PR
  metadata keys enter the initial queue in that same order. After all admitted
  metadata settles, successful pairs are processed in originating-event/key order;
  each compare receives its cache read and, on miss, enters the queue after the
  initial units. This two-stage admission is independent of response completion
  order. Across both stages at most 500 distinct eligible evidence identities are
  read and the first 100 queued work keys are admitted. Complete hits avoid their API
  unit. Two queued units may run concurrently, while requests and result admission
  remain ledger-bound.
- Exceeding a per-entity page, path-count, or path-byte limit makes that entity's
  evidence incomplete.
  Reaching the queue, global path, request, cache, or matching limit stops admission
  in deterministic event, evidence-identity, then canonical Scope order. Every
  affected path membership remains `unknown`, with quantitative reason counters,
  and may retry in a later refresh. Repository membership remains usable.
- The 10,000 global changed-path count includes direct evidence, cache hits, and API
  results. It counts unique normalized paths once per complete evidence identity
  after within-identity deduplication, counts both old and new rename paths, and
  counts one coalesced identity once regardless of event/Scope reuse.
- A cache replacement is one atomic evidence transaction regardless of child rows.
  The single touch transaction, at most 1,024 incremental-vacuum pages, and one
  truncate-checkpoint attempt are separate ledger counters and do not consume the 20
  replacement-write allowance.
  Functional reads and writes precede the single bounded cleanup batch. Reaching a
  local-work limit defers cleanup or evidence work; it never runs an unbounded
  foreground catch-up. RG-005 sets physical byte, row, age, and lock limits within
  these per-refresh ceilings.
- Work that can be chunked into Bubble Tea commands or messages yields between
  bounded chunks. Network, SQLite, enrichment, matching, and cleanup never run in a
  renderer or keyboard handler, and a pending command cannot prevent quit,
  navigation, pause, or resize messages from being handled.

#### Prepared UI State Bounds

| State | Hard limit |
| --- | ---: |
| Rain items across all Scope columns | 500 |
| Rain items in one Scope column | 50 |
| Arrivals retained while Rain is paused | 100 |
| Stored `Interesting Now` entries | 20 |
| Visible `Interesting Now` entries | 5 |

- One event represented in several matching Rain columns spends one item from each
  column and one global item for each representation. Column capacity is checked
  before global capacity. RG-006 closes deterministic admission, eviction, paging,
  and paused-queue order within these maxima.
- `Interesting Now` stores no more than 20 prepared entries and renders no more than
  five even when height permits more. RG-007 closes selection and fairness within
  those maxima.
- Prepared state retains total eligible, admitted, and omitted counters. Bound
  disclosures use `rain: X of Y items`, `paused: X of Y arrivals`, and
  RG-007's disjoint Interesting Now shown/retained-hidden/capacity-omitted form when
  totals are known; otherwise they state `more omitted`. Responsive contracts may
  shorten these forms. RG-007's 6-16-cell case uses `I+` plus Stream reachability
  instead of silently hiding prepared strip overflow.

#### Deterministic Verification Vectors

- Selection fixtures exercise 20/21 repositories and 100/101 Scopes. Exact input
  passes at the bound and fails one beyond it; expanded input at the same boundary
  retains exact selections first and reports the deterministic expanded omission.
- A fixture returning 2,000 distinct normalized candidates across 20 repositories
  retains exactly the globally newest 500 before issuing any cache or enrichment
  work. A 501-event fixture proves the discarded event causes no evidence lookup.
- A due-expansion fixture dispatches 5 listing, 20 polling, and 15 enrichment
  requests. An otherwise identical non-expansion fixture dispatches at most 20
  polling and 20 enrichment requests. A requested 41st HTTP request is not dispatched;
  retries and cancellations are shown to spend rather than reset the ledger.
- Enrichment fixtures exercise 100/101 queued work units, including current-PR
  metadata whose compare would cross the queue/request boundary, 2/3 simultaneous operations,
  10/11 pages, 1,000/1,001 paths per entity, and 10,000/10,001 paths globally.
  Every over-bound result is incomplete with deterministic unknown counters.
- Local fixtures exercise 500 cache reads, 20 writes, one touch transaction over 500
  identities, one cleanup batch at its record/child-row limits, 1,024 vacuum pages,
  one checkpoint attempt, and 1,000,000/1,000,001 matcher evaluations. Fakes record
  operations without live SQLite, GitHub, credentials, sleeps, or machine-speed
  assertions.
- UI fixtures exercise 500/501 global Rain items, 50/51 items in one column,
  100/101 paused arrivals, 20/21 stored strip entries, and 5/6 visible entries,
  including one event represented in several Scopes. While fake network, cache, and
  matching commands remain pending, key, pause, resize, and quit messages still
  update deterministically.

### RG-010 Organization Selection Contract

This gate is closed by the following bounded expansion contract. Organization
selectors exist only in validated CLI/application input and the GitHub adapter. A
successful expansion emits ordinary canonical repository Scopes plus prepared
selection provenance; no organization type enters domain membership or aggregation.

#### CLI Grammar and Composition

- `--org ORGANIZATION` is repeatable. Quoted `--repo 'ORGANIZATION/*'` is its exact
  alias; quotes are shell guidance, not parser-visible grammar. `*` must be the
  entire repository component and the process must receive it unchanged. Both
  `--repo VALUE` and shipped `--repo=VALUE` forms apply. `ORGANIZATION` uses the
  shipped repository-owner grammar: 1-39 ASCII
  alphanumeric/hyphen characters, no leading/trailing hyphen. Comparison is ASCII
  case-insensitive and the first spelling/form is retained.
- The two forms share one first-occurrence sequence in argument order and
  deduplicate by lowercase organization. At most five distinct selectors are valid;
  a sixth fails with requested/allowed counts before credentials, cache, network, or
  TUI work. Exact `--repo OWNER/REPOSITORY`, qualified paths, selectors, and both
  selector aliases may otherwise be mixed.
- `--include-archived` and `--include-forks` are process-global booleans applying to
  every organization selector. Either is invalid without at least one selector and
  both are incompatible with `--reset-cache`. Repetition is harmless. They do not
  alter exact repository/path Scopes.
- Organization expansion creates repository Scopes only. Bare `--path PATTERN`
  values apply only to exact repository arguments and are invalid when no exact
  repository accompanies them, even if a selector exists. Qualified path Scopes
  remain independent. There is no `--org-path` or organization aggregate.
- Help/version retain RG-001 precedence and perform no expansion. Organization-only
  input passes parse validation and starts the asynchronous first-expansion state.
  Unknown/inaccessible organizations are runtime adapter outcomes, not parser guesses.

#### Listing API, Pagination, and Validation

- Each page is exactly
  `GET /orgs/{organization}/repos?type=all&sort=full_name&direction=asc&per_page=100&page=N`
  with RG-003's media type, API version `2026-03-10`, authentication, user agent,
  timeout, cancellation, sanitized-error, redirect, and rate-limit rules. No
  repository-detail or activity request is made to decide expansion eligibility.
- One due expansion uses RG-009's first five request/page slots and admits at most
  500 listing records. Distinct selectors receive page one in first-request order;
  remaining slots follow valid `rel="next"` links one page per selector round, skipping
  exhausted selectors, until five requests or all lists end. Every dispatch spends
  budget before the request and cancellation does not refund it.
- A next link must be HTTPS on `api.github.com`, target the same case-insensitive
  organization and endpoint, preserve exactly `type=all`, `sort=full_name`,
  `direction=asc`, `per_page=100`, advance exactly from page N to N+1, and contain no
  other query. Malformed, cyclic, cross-host, cross-organization, regressing, or
  unexpected pagination fails the whole expansion attempt.
- Every record requires a valid `full_name`, `name`, owner `login`, owner `type`,
  `archived`, `disabled`, and `fork`. Owner login must equal the requested
  organization case-insensitively, owner type must be `Organization`, and
  `full_name` must split into exactly two lexically valid components whose canonical
  lowercase values equal owner `login` and `name` respectively. The exact first valid
  `full_name` spelling is retained for presentation; canonical equality, not bytewise
  casing equality, validates the repeated fields.
  Duplicate canonical repository records with conflicting required facts fail the
  attempt; consistent duplicates collapse to their first fetched occurrence.
- A successful page body is an array of zero through 100 records. A 101st record is
  malformed and fails the attempt; OrgTop never truncates an oversized response to
  manufacture the five-page/500-record bound.
- A `2xx` malformed page, pagination violation, timeout/transport/`5xx`, denied
  `401`/non-rate `403`, rate-limited response, and `404` unknown-or-inaccessible
  organization are distinct sanitized attempt failures. No valid-looking partial
  selector set is published. A valid five-page attempt with remaining next links is
  instead a bounded successful truncation with an unknown remaining count.

#### Eligibility and Candidate Order

- `disabled=false` is mandatory and has no override. `archived=false` is mandatory
  unless `--include-archived`; `fork=false` is mandatory unless `--include-forks`.
  These exact listing booleans are the complete eligibility filter.
- Visibility, privacy, `pushed_at`, `updated_at`, repository size, issue count,
  language, topics, and permission ranking do not filter a listed repository.
  In particular `pushed_at=null` or old is eligible because comments/reviews may be
  observable without a repository push. The endpoint's authenticated visible set is
  accepted without an extra permission/activity probe.
- Each selector's eligible candidates are sorted by canonical lowercase `full_name`
  byte order, then retained first spelling for an impossible canonical tie. Selector
  allocation visits one next candidate per selector in first-request round-robin
  order until all fetched candidates are examined. An exact repository-Scope
  duplicate consumes that selector turn, adds selector provenance, and creates no
  second Scope. Distinct valid selectors cannot return the same canonical repository
  because every owner must match its selector.

#### Capacity, Truncation, and Provenance

- Exact repository and path Scopes are canonicalized first and have unconditional
  capacity precedence. They must independently satisfy RG-009's 20 distinct
  repositories and 100 total Scopes or parsing fails; expansion receives only the
  remaining capacities.
- An expanded repository Scope consumes one Scope slot and, only when its repository
  is not already referenced by an exact or admitted Scope, one distinct-repository
  slot. A candidate that would exceed either capacity is not admitted, but allocation
  continues to collect duplicate provenance and exact omission counts from every
  fetched valid record. No exact Scope is evicted.
- Per selector, `listed` counts consistent canonical records after duplicate collapse.
  Exclusion buckets are disjoint in `disabled`, then non-included `archived`, then
  non-included `fork` precedence; their sum plus `eligible` equals `listed`.
  `retained` counts eligible repositories whose repository Scope exists after
  allocation, including an exact duplicate that gains selector provenance, and
  fetched capacity-omitted is `eligible-retained`.
- Prepared selection state retains exact Scope count, expansion-created repository-
  Scope count, total Scope/distinct-repository counts, each selector's listed,
  eligible, disjoint-excluded, retained, omitted, and `has_more` values, the derived
  global pagination-remains condition, and for each repository Scope an `exact` bit plus optional
  contributing selector. Provenance never changes Scope identity or behavior.
- Chrome shows `selection: R repos · S scopes · X exact · G expanded`; `X` exact
  Scopes and `G` expansion-created Scopes partition `S`. When capacity omits known
  unique eligible Scopes it appends `· O eligible omitted`, and an unconsumed next
  link appends `· more eligible may be omitted`. Detail/help exposes per-selector
  listed, eligible, disabled/archived/fork exclusion, retained, provenance, and
  `has_more` state. A bounded result is never presented as the complete organization.

#### Selection Snapshots and Re-expansion

- Startup expansion is due immediately. After a successful attempt, the next is due
  15 minutes after that attempt's explicit completion time. Scheduled or manual
  repository refresh before due reuses the latest fixed selection and spends no
  listing request. A non-rate failed due attempt sets next attempt to exactly 60
  seconds after failure completion; the next scheduled/manual refresh at or after it
  retries. A rate-limited attempt instead uses RG-003's later poll/retry time. Manual
  refresh never bypasses either bound; success resets the 15-minute interval.
- A due refresh runs `expansion -> fixed selection polling -> normalization/...` in
  RG-009's one ledger. Expansion may spend five requests; polling retains its next 20
  reservation and enrichment receives at least 15. One immutable selection snapshot
  is passed to every poll in that refresh, so mid-refresh organization changes cannot
  alter its repository set.
- Successful expansion followed by successful polling atomically publishes the new
  selection, events, memberships, aggregates, provenance, and omission state. If
  polling fails, no new selection/event pair is published; the successful internal
  selection becomes the fixed input for the next poll. With a displayed previous
  snapshot, that pair remains `STALE`; on initial polling failure there is no prior
  pair and state is `ERROR`. In both cases the internal selection remains hidden
  until a matching successful poll, and its 15-minute timer starts at expansion success.
- A failed re-expansion with a previous successful selection polls that previous
  fixed set in the same refresh only when the failure does not prohibit further
  GitHub dispatch, and publishes/retains `SELECTION STALE` independently of source
  `CURRENT`/`STALE`. A rate-limited expansion stops dispatch and waits for retry time.
  With a published snapshot it retains `STALE · RATE LIMITED · SELECTION STALE`; with
  only a hidden initial selection it remains `ERROR · RATE LIMITED · SELECTION STALE`.
  Neither path
  publishes successful-selector subsets, narrows, or empties selection. A later
  successful expansion/poll atomically replaces it and clears only recovered causes.

#### Initial, Empty, and Failure States

- Before first expansion, organization-only and mixed input render `LOADING ·
  expanding organizations`; no repository poll starts. If any selector fails, the
  complete initial selection is `ERROR` and no exact or successfully expanded subset
  is polled. Retry remains scheduled with a sanitized unknown/inaccessible, denied,
  rate-limited, malformed, or temporary cause.
- A first successful expansion with no eligible repositories and no exact Scopes is
  a vacuously successful zero-repository source-poll phase and therefore a `CURRENT`
  empty selection: no HTTP poll occurs, all views show
  `No eligible repositories` plus selector/filter context, and re-expansion is due in
  15 minutes. Empty selectors in mixed input contribute zero and exact/other expanded
  Scopes continue normally.
- Cancellation before expansion/poll publication discards any newly expanded internal
  selection and its would-be timer, leaving the prior complete selection, application
  snapshot, and expansion schedule intact. Initial cancellation therefore leaves
  expansion immediately due and publishes neither empty nor error state.

### RG-011 Distribution Channel Contract

The source repository `fmueller/orgtop` and its tag/commit are canonical.
`fmueller/gh-orgtop` is the GitHub CLI companion and `fmueller/homebrew-tap` is the

  or reconciles an unpublished source draft. The workflow then creates or reconciles
  the same-tag extension draft and public tap staging branch
  `release/orgtop-vMAJOR.MINOR.PATCH` from the expected default-branch commit. The
  branch changes only `Formula/orgtop.rb`; it may reveal planned metadata but remains
  inactive because the default branch and install command still select the prior
  formula and its draft source URL is inaccessible anonymously.
- Pushing the source tag makes its commit and GitHub-generated source-code snapshots
  public before staging; those snapshots are not canonical release artifacts. “Draft”
  and “publication” below refer to built release assets. No built source or extension
  asset becomes anonymously downloadable until the source release transition.
- Before public mutation, reconciliation verifies source tag/commit, companion owner/
  topic, exact asset sets/names/sizes/digests, archive-to-raw equality, checksums,
  provenance subjects, version output, argument/credential behavior, formula URLs/
  hashes/tests, tap base, and absence of contradictory same-version state. Draft
  assets are downloaded through authenticated URLs for staging tests.
- Publication order is source release, extension release, then compare-and-swap merge
  or fast-forward of the formula branch onto its verified base. Releases become
  non-draft, non-prerelease and carry the same source version; source notes are the
  exact CHANGELOG section and companion notes link to them. Formula data uses only
  versioned URLs.
- Final reconciliation downloads every public asset, rechecks digests/versions, and
  verifies default-branch formula content and install tests. It generates canonical
  JSON `distribution-complete.json` using the exact schema below. Objects reject
  missing or extra properties; SHA values are 64 lowercase hexadecimal characters;
  commits are 40 lowercase hexadecimal characters; URLs are canonical HTTPS GitHub
  URLs without query, fragment, percent encoding, or trailing slash. The source URL
  is exactly `https://github.com/fmueller/orgtop/releases/tag/<TAG>` and extension URL
  exactly `https://github.com/fmueller/gh-orgtop/releases/tag/<TAG>`, where TAG is the
  schema's ASCII semantic-version tag. `schema_version` is integer `1`; OS is `darwin`,
  `linux`, or `windows`; architecture is `amd64` or `arm64`.

  ```text
  {
    "schema_version": 1,
    "source": {"repository":"fmueller/orgtop","tag":STRING,"commit":SHA1,
      "release_url":URL,"workflow":{"path":".github/workflows/release.yml","commit":SHA1}},
    "extension": {"repository":"fmueller/gh-orgtop","tag":STRING,"release_url":URL},
    "tap": {"repository":"fmueller/homebrew-tap","formula_path":"Formula/orgtop.rb","commit":SHA1},
    "targets": [{"os":OS,"architecture":ARCH,
      "archive":{"name":STRING,"sha256":SHA256,"provenance_subject_sha256":SHA256},
      "raw":{"name":STRING,"sha256":SHA256,"provenance_subject_sha256":SHA256},
      "executable_sha256":SHA256}]
  }
  ```

  `tag` is exact `vMAJOR.MINOR.PATCH`; target records are the six matrix rows sorted
  by OS then architecture byte order. Each provenance-subject digest is the SHA-256
  bound to that exact named subject in the source bundle, separately for archive and
  raw asset; each equals its corresponding published artifact digest. Workflow
  identity uses the stable path and workflow-file commit, never run ID/attempt.
  Output is UTF-8 RFC 8785 JSON Canonicalization Scheme bytes with no BOM/newline.
- The exact manifest bytes are added as release assets to source then extension using
  create-or-compare semantics. Both manifests are necessary but not sufficient for
  completion; the completed ledger event and final reconciliation below are also
  required. One manifest alone is partial; retry compares and adds the missing one.

#### Idempotency, Failure, and Reconciliation

- Every operation is create-if-absent or compare-exactly. Expected drafts, releases,
  assets, checksums, provenance subjects, formula branch/content, and completion
  manifests are reused; missing pieces are created. A mismatched source commit,
  digest, asset set, formula URL/hash, tap base, or manifest fails closed. Assets are
  never overwritten and channels never rebuild independently.
- A failure stops later transitions where possible, fails the workflow, and writes no
  new completion manifest until all preceding public state verifies. Already public
  exact pieces may remain for deterministic retry but are not complete. Retry from the
  same tag reconciles all repositories and resumes at the first missing transition.
  Tap-base movement before formula publication requires rebuilding and retesting only
  the formula staging branch against the new base; artifact bytes remain immutable.
- Transient/API/permission failure may be reconciled repeatedly from exact state.
  Contradictory same-version state is non-reconcilable and mandates withdrawal. No
  later source tag may publish while an earlier partial release exists: the earlier
  tag must first complete or be withdrawn. A failed cleanup is itself partial and is
  retried with delete-if-present/compare-before-revert operations until every channel
  reaches the withdrawal state.
- Before any built release asset becomes public, the protected PR flow appends one
  staged event to source-default-branch `docs/distribution-ledger.jsonl`. Every line
  is one RFC 8785 canonical object followed by exactly one LF; the event digest is
  SHA-256 of the canonical object bytes excluding that LF. Objects reject missing or
  extra properties and use these exact schemas:

  ```text
  staged = {"schema_version":1,"event":"staged","version":VERSION,
    "source_repository":"fmueller/orgtop","source_tag":TAG,"source_commit":SHA1,
    "artifacts":[{"name":STRING,"sha256":SHA256}],
    "checksums_sha256":SHA256,"provenance_sha256":SHA256}
  completed = {"schema_version":1,"event":"completed","version":VERSION,
    "staged_sha256":SHA256,"source_manifest_sha256":SHA256,
    "extension_manifest_sha256":SHA256,"tap_commit":SHA1}
  withdrawn = {"schema_version":1,"event":"withdrawn","version":VERSION,
    "staged_sha256":SHA256,"publication_state":"incomplete"|"completed",
    "reason":STRING,"tap_commit":SHA1|null,"notice_path":STRING,"notice_url":URL}
  ```

  VERSION omits `v`; TAG includes it. The staged `artifacts` array contains exactly
  the 12 build artifacts sorted bytewise by name. `checksums_sha256` and
  `provenance_sha256` hash the exact source metadata assets. Completed/withdrawn
  `staged_sha256` references the staged object digest; reason is nonempty sanitized
  public copy. In `completed`, `tap_commit` is the commit that published the formula.
  In `withdrawn`, it is that same pre-withdrawal published-formula commit, known before
  the withdrawal PR, or null when the formula was never published; it is never the
  later revert commit. `notice_path` is exactly
  `docs/withdrawals/v<VERSION>.md`; `notice_url` is exactly
  `https://github.com/fmueller/orgtop/blob/main/<notice_path>`. The protected
  withdrawal PR creates that durable notice on canonical default branch `main` in the
  same commit as the event; the notice records version, state, reason, affected
  channels, staged digest, irrecoverable download/cache limitation, and replacement
  version when known. Events/notices are never removed when releases/tags are
  deleted. The ledger is authoritative for same-version reuse and reservation.
- Completion order after publication is: final public parity check; source manifest;
  extension manifest; protected PR merge of the exact completed event; then one final
  reconciliation of releases, tap, both manifests, and ledger. Workflow success and
  release completion require all five. Failure before the completed PR merge remains
  partial even when both manifests exist; retry compares them and resumes the PR.
- A moved source tag, changed archive, or same-version differing executable is never
  reconciled. Before completion, a withdrawn/recreated source tag may reuse the
  version only at the identical source commit and with all 12 identical artifact
  digests; checksum content and provenance subjects must describe those exact bytes.
  Formula staging may rebase only as above. Changed source commit or bytes require a
  new semantic version.

#### Withdrawal

- Withdrawing an incomplete publication first merges the protected withdrawal-event
  and notice PR, then compare-and-swap reverts a merged tap formula or deletes its staging branch,
  and then deletes source/extension releases and corresponding tags. The version
  may be staged again only when its ledger record proves the identical source commit/
  digest rule.
- Withdrawing a completed publication first merges one protected PR containing the
  withdrawal event, durable notice, and required CHANGELOG notice, then
  compare-and-swap reverts the tap formula to its
  prior valid version only if default branch still selects the withdrawn version; a
  newer formula is preserved. It deletes both releases and corresponding tags and
  publishes any fix under a new semantic version. A completed semantic
  version is permanently non-reusable.
  Downloaded binaries, caches, attestations, and checksum copies cannot be revoked;
  the withdrawal notice states that limitation.
- Failure or withdrawal never changes executable credentials, arguments, config/cache
  paths, or runtime behavior. Source archives remain a complete installation path on
  systems without GitHub CLI or Homebrew.

### RG-012 Mixed-Scope Presentation Contract

This gate is closed by the following deterministic mixed-Scope presentation
contract. Rendering consumes prepared order, identity, membership, qualification,
and omission state; it does not match, aggregate, enrich, or infer policy.

#### Scope Order, Tokens, and Labels

- The stable Scope identity order is lowercase canonical repository identity in
  byte order, repository Scope before path Scopes in the same repository, then
  RG-002 canonical matcher-token encoding in byte order. This is the RG-006 Rain
  column order and the tie-break order used everywhere below.
- Overview preserves v0.1's confirmed-activity-total descending primary order and
  uses the complete stable Scope identity order for ties. Unknown totals,
  current-PR qualifications, category subcounts, requested/configuration order,
  and organization provenance do not affect row order. Zero-activity and
  all-unknown Scopes remain rows and use the same tie-break.
- A Scope's confirmed activity total is the number of retained normalized events with
  a `member` outcome for that Scope; it is the same direct total RG-004 aggregates and
  never includes unknown or not-member outcomes.
- Every prepared Scope receives a compact presentation token from its one-based
  ordinal in stable Scope identity order: `R<ordinal>` for a repository Scope and
  `P<ordinal>` for a path Scope. The ordinal is global rather than per kind, so a
  stable sequence may be `R1,P2,P3,R4`. Tokens are unique for the current bounded
  Scope set and distinguish a repository Scope from its `**` path Scope.
- A successful atomic selection publication recomputes every token from the new
  complete Scope set. Surviving Scopes may therefore renumber together; no render
  exposes a mixture of old and new tokens. Rain preserves its canonical Scope
  anchor across recomputation rather than anchoring by token text.
- A full repository label is `<token> <first-requested-owner/repository>`. A full
  path label is `<token> <first-requested-owner/repository>:<first-requested-pattern>`.
  For an organization-expanded repository with no exact request, RG-010's retained
  source `full_name` spelling occupies the repository payload. The retained
  requested/source spelling is presentation only; token assignment, order,
  deduplication, matching, and view state use canonical Scope identity.

#### Cell-Safe Shortening

- Label budgets are measured in rendered terminal cells. A grapheme cluster is
  indivisible; combining sequences and wide runes are never split, and byte count
  is never used as display width. A shortened payload contains the single-cell
  ellipsis `…`, so shortening is visible without color.
- Grapheme boundaries and terminal-cell widths are the behavior of the repository-
  pinned Charm stack: `charm.land/lipgloss/v2` `v2.0.6` `Width` and
  `github.com/charmbracelet/x/ansi` `v0.11.8` grapheme-aware operations, with selected
  width/segmentation modules `github.com/clipperhouse/displaywidth` `v0.11.0`,
  `github.com/clipperhouse/uax29/v2` `v2.7.0`,
  `github.com/mattn/go-runewidth` `v0.0.24`, and `github.com/rivo/uniseg` `v0.4.7`.
  Toolchain guards pin the complete set rather than relying on transitive drift. Emoji ZWJ
  sequences remain one grapheme, East Asian ambiguous characters use that stack's
  one-cell policy, combining/variation-selector code points remain attached, and a
  zero-cell cluster attached to no positive-width grapheme renders as one visible
  uppercase `\u{HEX}` escape per code point. Before measurement, C0/C1 control, DEL,
  and bidi controls U+061C, U+200E, U+200F, U+202A through U+202E, and U+2066 through
  U+2069 in presentation payloads also render as visible uppercase `\u{HEX}` text.
  ZWJ and variation selectors remain unescaped only inside a positive-width grapheme.
  User data therefore cannot become ANSI/control or bidi-reordering output. Upgrading
  any pinned behavior module requires updating normative width vectors in the same change.
- If the full token, space, and payload fit, they render unchanged. Otherwise the
  token and one space are retained and the remaining payload budget is split around
  one ellipsis: the prefix receives the larger half of the non-ellipsis cells and
  the suffix the smaller half. The longest whole-cluster prefix and suffix fitting
  those shares are retained; unused cells caused by a wide boundary extend the
  prefix first and then the suffix when another whole cluster fits.
- If the payload budget cannot hold the ellipsis plus at least one whole cluster on
  each side, the forms are `<token> …` and then `<token>`. A positive width smaller
  than the complete token renders the longest whole-cluster prefix of the token that
  fits; zero width renders nothing. The view's range/hidden accounting still
  represents the Scope, and no renderer substitutes an ambiguous unmarked payload
  fragment for the token.
- Overview, Stream, Stream detail, Rain, and Interesting Now use the same token and
  shortening function. Shortening never changes order, membership, Rain column
  width/count, item admission, or any capacity decision.

#### Overview and Stream Viewports

- Overview and Stream retain separate zero-based numeric vertical offsets. Initial
  offset is zero. In Overview, up/down change it by one row and page up/down change
  it by the actual number of data rows available after current chrome, with a minimum
  step of one. Every update clamps it to `0..max(0,N-H)` for prepared row count `N`
  and data-row capacity `H`. Stream navigation follows its focused-index rules below.
- Resize preserves the numeric offset and then clamps it. Refresh, including a
  reorder, also preserves the numeric offset and then clamps it; it does not anchor
  the formerly first visible identity. Repeating the same resize or refresh input is
  idempotent, switching views retains each view's offset, and no clamp may leave a
  blank trailing viewport while rows exist.
- Whenever `N>H>0`, existing active-view header chrome appends `scopes A-B of N`,
  `events A-B of N`, or `lines A-B of N`, using one-based inclusive visible
  positions. The range consumes no body row and disappears when all rows fit. If
  `H=0`, the applicable full form is `<kind> 0 shown of N`; at `40x10`, chrome
  reduction must preserve at least one primary row before this fallback is possible.
- Stream source truncation appends `newest R of T` independently of its viewport
  range. Overview/Stream viewport hiding, RG-006 off-page Rain state, RG-007 hidden
  strip entries, RG-009 capacity omission, source truncation, collision grouping,
  clipped qualification, and hidden status badges are distinct counts and are never
  merged or substituted for one another.
- Header allocation is exactly one non-wrapping line, so chrome height and viewport
  arithmetic do not depend on renderer choice. Applicable segments use this fixed
  priority: `OrgTop <view>`; `POLLING` plus primary freshness; a required overflow
  range; RG-004 secondary status badges; Scope context; stale last-success and
  concise sanitized error; source truncation; then RG-010 expanded
  selection/provenance detail.
- Each segment selects its first fitting form from full to minimum in the cells left
  by higher-priority segments. The brand/view minimum is `<view>`; transport/freshness
  is indivisible; Scope context shortens from `<R> repos · <S> scopes` to `<S> scopes`
  then `<S>S`. Long stale error text uses `last <age> · <sanitized-error…>`, then
  `last <age>`; the marked ellipsis is part of the first form when text is shortened.
  An overflow range shortens from `<kind> A-B of N` to `A-B/N`, then `+X` where
  `X=N-(B-A+1)` is the total currently hidden above and below. Source truncation
  shortens from `newest R of T` to `src R/T`, then `+D source` where `D=T-R`.
  RG-004 badges consume their remaining allocation in closed priority and collapse
  to `+N status`. If no form of a segment fits, that segment and all lower-priority
  segments are omitted; prepared state is unchanged. At positive widths below the
  first segment's minimum, the longest fitting prefix of the active-view name is the
  deterministic best effort.
- The zero-row `<kind> 0 shown of N` form shortens to `0/N`, then `+N`. Stream
  detail uses the same full, compact, minimum, and zero-row range ladder with kind
  `lines`; it introduces no separate overflow formatting policy.
- RG-010 selection detail shortens from its full summary to
  `sel R repos · S scopes · O omitted · more?`, omitting `O omitted` at zero and
  `more?` when no valid next page remains. Its minimum is `SEL O+?`, where decimal
  `O` is the exact eligible-omission count and `?` is present only when more eligible
  repositories may exist. Exact-only, exact-plus-unknown, and unknown-only examples
  are `SEL 480`, `SEL 480+?`, and `SEL ?` respectively.
  Lower-priority source/selection detail yields before any required minimum range or
  status accounting. `TRUNCATED` applies when RG-009 discarded source events,
  RG-010 has a positive exact eligible-omission count, or RG-010 reports that more
  eligible repositories may exist. Several applicable causes still produce one
  summary badge, while source and selection details retain separate exact/unknown
  counts; `TRUNCATED`/`+N status` remains when those details yield. At dimensions too
  small for all mandatory minima, active view,
  transport/freshness, primary body, and quit retain FR-011 priority, while prepared
  counts reappear unchanged after resize.

#### Stream Overlap and Event Detail

- Stream keeps one row in reverse-chronological source-event order for an event that
  is member in at least one Scope or unknown in at least one Scope. It never creates
  one row per Scope. Within row context, member tokens and unknown tokens each use
  stable Scope identity order; not-member Scopes are omitted. `~` suffixes each
  current-PR member token and `?` prefixes each unknown token.
- Complete context renders as `in <members> · unresolved <unknowns>`, omitting an
  empty group. When it does not fit, the intermediate form starts with the first
  token from each nonempty group, appends `+N` to each affected group for its
  hidden-only count, and appends `+Q current PR` for hidden qualified member tokens.
  A group's labels and its `+N` are comma-space separated; member and unknown groups
  are separated by ` · ` and the hidden-current-PR clause is a final ` · ` clause.
  It then adds the next member and unknown token alternately, member first, whenever
  the complete candidate still fits; if one group's next token does not fit, the
  other group's next token is still tried. Hidden counts and the hidden-qualified
  count are recomputed after each addition, and expansion stops when neither next
  token fits. If the initial intermediate form does not fit, the next forms are total
  `<M> member · <U> unknown · <Q> current PR` with zero clauses omitted, then
  `<M>m <U>? <Q>~`. The most detailed fitting complete rung is used; output is never
  sliced after formatting. If even the minimum does not fit, context renders `+K`
  for `K=M+U` when it fits, then `+` at one cell, then nothing at zero width; `enter`
  still reaches the complete prepared outcomes.
- Stream has one focused prepared-event index, initially zero. Up/down move focus by
  one and page keys move it by the current event-row capacity, with a minimum step of
  one. The viewport offset changes only enough to keep focus visible: focus above the
  viewport sets offset to focus; focus below it sets offset to `focus-H+1`; both are
  then clamped. Resize and refresh preserve the numeric focus and offset, clamp both,
  then minimally reveal focus. This extends v0.1 scrolling without changing event
  order.
- `enter` on a focused event opens bounded Stream event detail from the same prepared
  snapshot. Detail performs no API/cache access, normalization, matching, aggregation,
  or ranking. It shows source event ID, timestamp and prepared age, repository,
  category, optional actor, entity kind/reference, description, every member Scope
  and its current-PR qualification, and every unknown Scope with its prepared reason;
  not-member Scopes are omitted.
- Detail serializes/sanitizes fields and greedily grapheme-wraps every logical line
  exactly as A-077 defines. It does not shorten non-Scope facts or full detail Scope
  labels; vertical scrolling, rather than hidden text, bounds their presentation.
  The exact one-cell wide-grapheme placeholder/counter and zero-width preservation
  are its only clipping exceptions.
- Detail uses up/down and page keys with the same numeric/clamp rules. Its active-view
  line offset changes directly by one or by the available detail-row count and clamps
  to `0..max(0,N-H)`; detail has no focused-line state. Its active-view header appends
  `lines A-B of N` when needed. `esc` returns to the unchanged focused
  event and Stream viewport; `q` remains available. While detail is open, refresh
  follows the stable source event ID: if retained, its prepared facts/outcomes replace
  the detail atomically, its detail-line offset clamps, and Stream focus moves to its
  new index with the minimum viewport adjustment. If refresh removes that event,
  detail closes and Stream preserves then clamps its prior numeric focus/offset.
  Detail is not the future cross-view Inspect feature and never fetches additional
  facts.

#### Rain and Constrained Composition

- Rain retains RG-006's canonical-identity anchor, fixed manual pages, `[`/`]` wrap,
  column count and width formula, successor/predecessor fallback, and disjoint hidden,
  omitted, collision, and clipped counters. Scope tokens and shortened labels are
  content inside those columns; they do not select pages or alter geometry.
- Interesting Now retains RG-007 sponsorship, order, bounds, and `+N scopes` overlap
  count. Its full/compact labels use this contract, but its final closed minimum form
  and field/strip height allocation retain precedence when height is constrained.
- At `40x10`, each primary view and Stream detail preserves active view, transport and
  freshness, one primary content/state/detail line, and `q quit`. Secondary labels,
  headings, and reason detail yield before those elements. Status badges retain
  RG-004 priority and `+N status` accounting; compact Scope counts do not erase the
  underlying prepared conditions.
- At smaller positive dimensions, best effort may omit chrome or partial token text,
  exactly as the fallback ladders above require; update/render work remains bounded
  and every prepared row, event membership,
  Rain Scope, and condition remains reachable after resize or explicitly represented
  by the applicable range, compact total, or disjoint hidden/omission count.

## Potential Features

Taskrail uses `Potential Features` headings as coverable decomposition areas. These
areas describe required implementation work under the closed readiness contracts;
normative behavior is defined by the requirements and acceptance scenarios above.

### Unified Repository and Path Scopes

Extend exact repository selection into one validated, canonical Scope model that
supports mixed repository and monorepo path selections, overlap, deterministic
identity, and first-class presentation.

### Organization Selection

Expand a bounded, deterministic organization selector into ordinary repository
Scopes at the adapter boundary, deduplicated against exact selections, with
disclosed truncation and an honest degraded state when re-expansion fails.

### Distribution Channels

Publish the unchanged standalone executable through the GitHub CLI extension
channel and a Homebrew tap alongside the existing release archives, at one version
per tag across every channel and with no new runtime dependency.

### Changed-File Enrichment

Acquire complete normalized changed-file evidence through a bounded, cancelable,
rate-limit-aware GitHub adapter flow without leaking transport types into the domain.

### Explicit Scope Membership

Evaluate member, not-member, and unknown outcomes consistently before aggregation,
retain overlap, and expose incomplete path coverage according to the closed policy.

### Bounded SQLite Cache

Reuse complete enrichment evidence through a private, transactional, disposable,
versioned, and enforceably bounded local cache with deterministic cleanup and safe
degradation.

### Scope-Aware Overview and Stream

Present repository and path scopes as one activity model while preserving direct
counts, reverse-chronological investigation, v0.1 state transitions, overlap honesty,
and responsive layouts.

### Ambient Rain View

Add a deterministic tick-driven third view whose bounded field visualizes direct
scoped event density and whose columns represent repository or path Scopes. It
renders overlapping membership once per matching Scope and supports bounded,
deterministic pause and resume with `p`.

### Interesting Now Strip

Provide a bounded, readable, deterministic Rain companion containing only directly
observable current events, with no baseline or anomaly claims.

### Shared Glyph and Recency Semantics

Use one accessible category vocabulary and discrete recency model across views,
preserving shipped meanings and ensuring color is never the sole encoding.

### Responsive and Degraded Experience

Keep all views interactive and honest through narrow terminals, resizing, unknown
membership, cache/source failure, rate limiting, stale data, and later recovery.

### Integration Documentation and Release Readiness

Wire the closed contracts into the standalone binary, verify bounded end-to-end
flows without live credentials, document Scope/cache/Rain behavior, preserve v0.1
invariants, and pass repository quality gates.

## Implementation Notes (Informative)

- The expected flow is `GitHub adapter -> normalize -> enrich changed paths -> Scope
  membership -> aggregate -> application state -> Overview/Stream/Rain`.
- Enrichment may first consult SQLite and coalesce work by stable repository/entity
  identity before issuing bounded API requests. Exact keys and concurrency belong to
  the readiness contracts, not these notes.
- SQLite is justified by enrichment reuse in this release. It should remain a narrow
  implementation detail rather than becoming a repository-wide persistence layer.
- A tri-state membership type is preferable to a boolean because a boolean invites
  accidental treatment of missing evidence as non-membership.
- Rain needs only Bubble Tea ticks. A pure state transition driven by explicit event,
  tick, and resize messages will make motion and bounds straightforward to test.
- Overview remains the source of the clearest operating picture. Rain must not expose
  facts that cannot also be understood through prepared application state and Stream
  context.
- Bubbles may be added only if a concrete pagination or viewport component reduces
  implementation complexity after the interaction contract is closed.
- Synthetic fixtures should cover renames, pagination, overlap, incomplete evidence,
  cache corruption, and rate limits without containing private activity.
