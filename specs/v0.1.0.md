# OrgTop v0.1.0

**Status:** In Progress

## Release Intent

OrgTop v0.1.0 validates whether a developer can learn something useful about
near-current activity across selected GitHub repositories from one responsive,
terminal-native application.

Given valid existing GitHub credentials and one or more repositories, a user can
run:

```bash
orgtop --repo owner/repo-a --repo owner/repo-b
```

The standalone `orgtop` binary opens a full-screen TUI containing an Overview and a
reverse-chronological Stream. It periodically polls GitHub without blocking terminal
interaction and clearly distinguishes loading, current, empty, error, and stale data.

GitHub's Events API is near-current rather than real-time. This release must describe
itself as `POLLING`, never `LIVE`.

## Terminology

- **Repository identifier:** an exact GitHub `owner/repository` name.
- **Scope:** the deduplicated inclusion set formed by all `--repo` values. Each
  entry has the first requested spelling for fallback display and a lowercase key
  for matching.
- **Source event:** a GitHub API payload owned by the GitHub adapter.
- **Event:** a source-independent OrgTop domain occurrence.
- **Activity snapshot:** the latest completely successful, filtered, deduplicated,
  reverse-chronological event set and its repository aggregates.
- **Refresh:** one attempt to retrieve recent events for every repository in Scope.
- **Current:** the latest refresh succeeded for every selected repository.
- **Stale:** at least one complete refresh previously succeeded, but the latest
  refresh failed.

## Functional Requirements

### FR-001 Standalone Launch and Exit

- `orgtop` is a standalone binary, not a GitHub CLI extension.
- At least one `--repo` is required in v0.1.0. Launch without one exits non-zero and
  prints usage plus an actionable message before entering the TUI.
- Valid configuration launches the full-screen TUI.
- `q`, `ctrl+c`, and a standard process interrupt terminate cleanly.
- Standard Go `flag` parsing is sufficient; v0.1.0 has no subcommands.

### FR-002 Repository Scope

- `--repo` is repeatable and each value must have exactly two non-empty path
  components in `owner/repository` form.
- Validation is intentionally lexical. Owner matches ASCII
  `[A-Za-z0-9](?:[A-Za-z0-9-]{0,37}[A-Za-z0-9])?`; repository matches ASCII
  `[A-Za-z0-9._-]{1,100}`. GitHub remains authoritative for existence and access.
- Repository comparison is case-insensitive. Duplicate flags select one repository,
  and the first requested spelling is retained for fallback display.
- Globs, exclusions, organization inference, paths, and interactive filtering are
  rejected or absent rather than interpreted approximately.
- Only events whose canonical repository identity belongs to Scope may enter the
  activity snapshot or either view.
- Each repository response is associated with its requested Scope entry. Returned
  event repository names must match that entry case-insensitively; a different name
  fails that repository refresh instead of silently changing Scope. The first
  matching returned spelling becomes the display name for that successful snapshot;
  an empty response uses the requested spelling. Repository renames require the user
  to update `--repo` in v0.1.0.
- The selected Scope remains visible in shared TUI context. When space is limited,
  a repository count may replace the full list.

### FR-003 Existing Local Authentication

- Credential resolution occurs before the TUI starts.
- For `github.com`, trim whitespace and resolve the first non-empty credential in
  this order: `GH_TOKEN`, `GITHUB_TOKEN`, then the stdout of
  `gh auth token --hostname github.com`.
- The `gh` command is context-bound with a 10-second timeout. A failed, timed-out,
  or empty result means authentication is unavailable.
- Missing authentication exits non-zero with a concise remediation that mentions
  `GH_TOKEN` and `gh auth login`; it does not print a stack trace.
- OrgTop never logs, displays, or persists a token and does not create its own auth
  or configuration store.
- A 401 response reports that authentication was rejected and recommends checking
  the token or `gh auth login`. A 403 is rate-limited only when
  `X-RateLimit-Remaining` parses as zero or a valid `Retry-After` is present; other
  403 responses report denied access. A 404 reports that the named repository was
  not found or is inaccessible. None include credential values or raw authenticated
  request headers.

### FR-004 GitHub Activity Source

- For each selected repository, the source calls GitHub's documented REST endpoint
  `GET /repos/{owner}/{repo}/events?per_page=100` using media type
  `application/vnd.github+json` and API version `2022-11-28`. A retired contract
  requires a spec revision rather than an implicit behavior change.
- One page per repository per refresh is the deliberate v0.1.0 bound. The product
  presents recent returned activity, not a complete historical record.
- Requests carry the specified media type, the resolved bearer credential, a stable
  user agent, and a cancelable context.
- A refresh obtains all selected repositories outside Bubble Tea's update/render
  path. Network latency must not block keyboard or resize handling.
- At most one refresh is in flight. The next interval starts when the current
  refresh completes, so refreshes never overlap.
- The default interval is 60 seconds. After each complete success, the next interval
  is the greatest of 60 seconds and all `X-Poll-Interval` values from that refresh;
  a later complete success recalculates it from its own responses.
- OrgTop performs no tight retry loop. A failed refresh waits at least 60 seconds
  after completion. For 429 or rate-limited 403 responses, a valid `Retry-After`
  value and `X-RateLimit-Reset` instant are both considered, and the latest resulting
  retry instant wins over the normal interval. `Retry-After` accepts delta-seconds or
  an HTTP date; `X-RateLimit-Reset` is a Unix timestamp. Invalid headers are ignored
  safely.
- Empty successful responses are valid. Non-2xx responses, malformed top-level JSON,
  any event missing ID, parseable timestamp, or repository identity, repository
  identity mismatch, and transport failures become sanitized repository errors and
  therefore fail the atomic refresh.
- Ordinary automated tests use an injected HTTP transport or fixture server and do
  not contact live GitHub or require credentials.

### FR-005 Normalized Event Domain

- The GitHub adapter converts payloads before they reach filtering, aggregation,
  application state, or rendering.
- A normalized Event contains a stable source event ID, timestamp, canonical
  repository reference, optional actor, event category, entity kind, optional entity
  reference, and concise human-readable description data. Entity kinds include at
  least `repository`, `commit`, `pull_request`, and `other`.
- v0.1.0 categories are `push`, `pull_request`, `review`, `comment`, and `other`.
  Pull request merges are represented as pull request activity with a merge-specific
  description; no derived signal is implied.
- At minimum, representative `PushEvent`, `PullRequestEvent`,
  `PullRequestReviewEvent`, `PullRequestReviewCommentEvent`, and pull-request
  `IssueCommentEvent` payloads normalize without exposing GitHub transport structs.
- Pull-request `IssueCommentEvent` has entity kind `pull_request`; an issue-only
  comment normalizes as `other` and does not count as pull-request activity.
- Unsupported but structurally valid GitHub event types normalize as `other`.
  Missing category-specific optional fields use a generic description, but missing
  common required fields fail the repository response as specified in FR-004.
- Events are deduplicated by source event ID and ordered by timestamp descending,
  then source event ID ascending for deterministic ties.

### FR-006 Snapshot Filtering and Aggregation

- Scope filtering occurs after normalization and before aggregation.
- A completely successful refresh replaces the previous snapshot with the combined
  results from all selected repositories, deduplicated and sorted as specified.
- The in-memory snapshot is bounded to the newest 500 events after combination.
- A repository aggregate contains repository identity, total event count, push count,
  and pull-request activity count. Review and pull-request comment events count as
  pull-request activity; unrelated issue comments do not.
- Every selected repository appears in Overview, including repositories with zero
  events in the returned page.
- Aggregation is deterministic and independent of rendering.

### FR-007 Bubble Tea Application Shell

- Bubble Tea v2 owns application state, messages, commands, key input, and terminal
  resize events. Lip Gloss v2 provides shared semantic styles.
- The shared header identifies OrgTop, the active view, `POLLING`, Scope context,
  and last successful refresh when available. A separate freshness marker is
  `LOADING`, `ERROR`, or `STALE` when applicable; current data needs no extra marker.
- The shared footer advertises only implemented controls.
- `1` opens Overview, `2` opens Stream, and `tab` toggles between them without
  losing loaded events or each view's selection/scroll state.
- The initial model issues the first refresh asynchronously and renders immediately.
- Terminal width and height are updated from resize messages. At `40x10`, each view
  retains active view, transport/freshness state, one primary content or explicit
  state line, and a quit hint. Smaller positive sizes are best effort but must not
  panic or enter an unbounded update/render loop.

### FR-008 Refresh and Degraded States

- Before the first refresh completes, both views render an explicit loading state.
- After prior success, an in-flight refresh leaves the current snapshot visible and
  current until that attempt succeeds or fails; an optional non-blocking refreshing
  indicator must not replace the `POLLING` transport label.
- A refresh is atomic across Scope: new data becomes current only when every selected
  repository succeeds.
- If the first refresh fails, the TUI renders an error state with a sanitized,
  actionable cause and remains interactive while scheduled retries continue.
- If a later refresh fails, the last successful snapshot remains visible and the
  header clearly shows `STALE`, the last-success age/time, and a concise error.
- A later complete success clears error/stale state and atomically replaces the
  snapshot.
- A complete success records one last-success time even if all repositories return
  no events.
- Slow, failed, or rate-limited requests do not prevent view switching, scrolling,
  resize handling, or exit.

### FR-009 Overview

- Overview is the initial view.
- It renders one row per selected repository with canonical identity, total recent
  events, pull-request activity, and pushes from the current snapshot.
- Rows are ordered by total events descending, then canonical repository name
  case-insensitively for deterministic ties.
- Metrics are direct counts from the returned snapshot. No percentage, baseline,
  anomaly, productivity, or inferred-normality label is displayed.
- A successful snapshot containing zero events renders an explicit no-recent-activity
  message while retaining the selected repository rows or equivalent zero counts.

### FR-010 Stream

- Stream renders normalized events in the snapshot's deterministic reverse-
  chronological order.
- Each visible event includes timestamp, repository, category glyph/text, actor when
  available, and a concise description.
- Category has a non-color encoding. Color may reinforce but cannot replace text or
  glyph meaning.
- Up/down and page navigation scroll through events when the snapshot exceeds the
  available terminal height. Scrolling is clamped safely after refresh and resize.
- A successful snapshot with no events renders an explicit no-recent-activity state.

### FR-011 Documentation

- The README documents installation/build status, exact repeated `--repo` usage,
  supported credential precedence, required `gh auth login` fallback setup,
  polling/not-live semantics, controls, and development checks.
- Documentation does not claim deferred functionality or require the external design
  document.

## Non-Functional Requirements

### NFR-001 Responsiveness and Cancellation

- Network and subprocess I/O runs in Bubble Tea commands or lower-level cancelable
  operations, never synchronously in rendering or keyboard handling.
- Application shutdown cancels in-flight work and does not wait indefinitely for a
  network request or `gh` process.
- Each HTTP request has a timeout no greater than 30 seconds.

### NFR-002 Resource and API Discipline

- State is in memory only and bounded as specified.
- Polling is no more frequent than the effective interval and does not fetch event
  history beyond the one-page-per-repository contract.
- Rate-limit delay follows the concrete `Retry-After` and `X-RateLimit-Reset` rules
  in FR-004.

### NFR-003 Security and Privacy

- Tokens and authorization headers never appear in output, logs, errors, fixtures,
  snapshots, or persisted files.
- Raw private-repository payloads are not logged by default.
- OrgTop has no telemetry and sends activity only to GitHub.

### NFR-004 Architecture and Maintainability

- GitHub request/response structs remain owned by the source adapter.
- Domain types do not import GitHub adapter or Bubble Tea types.
- Views consume application/domain state and do not calculate source normalization,
  Scope filtering, or repository aggregates.
- Package boundaries are introduced only for current responsibilities. There is no
  speculative collector, persistence, signal, or generic-source framework.

### NFR-005 Portability

- Core code avoids shell-specific and platform-specific assumptions.
- Linux and macOS are required development targets; the repository release build may
  include Windows where dependencies compile without special behavior.

### NFR-006 Verification Quality

- Tests are deterministic and use the standard `testing` package.
- Domain tests cover repository parsing, case-insensitive inclusion, deduplication,
  ordering, filtering, and aggregation.
- Source tests cover credential precedence without leaking values, representative
  fixtures, empty responses, 401/403/404/429 failures, malformed data, repository
  identity mismatch, cancellation, and poll-interval/rate-limit metadata.
- TUI tests cover loading, populated Overview, populated/scrollable Stream, view
  switching with preserved state, empty, first-load error, stale-after-success,
  recovery, resize, and narrow-terminal rendering.
- `task check` passes and CI runs the same format, vet, lint, test, build, Taskrail,
  and release-configuration checks.

## Acceptance Scenarios

### A-001 One Repository

Given valid auth and fixture activity for `acme/backend`, running `orgtop --repo
acme/backend` enters Overview and displays only the canonical `acme/backend` row and
events.

### A-002 Multiple Repositories and Exact Scope

Given successful matching source responses for `acme/backend` and `acme/frontend`,
running `orgtop --repo acme/backend --repo acme/frontend` displays both. At the
domain boundary, a candidate event for an unrelated repository is excluded before
aggregation and never rendered; at the source boundary, a mismatched repository in
a selected endpoint fails the refresh under FR-004 rather than becoming a candidate.

### A-003 Invalid or Missing Scope

Launching with no `--repo`, malformed identifiers, or glob syntax exits before the
TUI with concise usage and no network request.

### A-004 Credential Precedence and Remediation

When trimmed `GH_TOKEN` is non-empty it is used without invoking `gh`; otherwise
trimmed `GITHUB_TOKEN` is used; otherwise an authenticated
`gh auth token --hostname github.com` result is used. With none available, startup
exits non-zero and recommends `GH_TOKEN` or `gh auth login` without exposing command
internals or token values.

### A-005 View Navigation

From populated Overview, `2` immediately opens Stream and `1` returns to Overview.
`tab` toggles views. Loaded data and each view's scroll/selection state survive the
switch.

### A-006 Asynchronous Refresh

While an injected source request is pending, the TUI continues to process view,
scroll, resize, and quit messages. A complete success atomically updates both views
and schedules the next refresh no sooner than the effective interval.

### A-007 Empty Activity

When every repository request succeeds with no events, Overview retains zero-count
repository context, Stream reports no recent activity, and the header records a
successful refresh rather than an error.

### A-008 Initial Error and Recovery

When the first refresh fails, the TUI shows an actionable error and remains
interactive. When a scheduled later refresh succeeds, the error clears and the new
snapshot is current.

### A-009 Stale Data and Atomic Multi-Repository Failure

After a successful multi-repository snapshot, if any repository fails on the next
refresh, none of that refresh's partial results replace the snapshot. Existing data
remains visible under a clear `STALE` marker with last-success context. A later full
success clears `STALE`.

### A-010 Narrow Terminal

At `40x10`, Overview and Stream retain the active view, transport/freshness state, at
least one primary content or explicit state line, and a quit hint. Smaller positive
dimensions are best effort but must not panic or cause a runaway render loop.

### A-011 Clean Shutdown and Secrets

After TUI startup, `q`, `ctrl+c`, or process interrupt cancels in-flight source work
and exits cleanly. A startup process interrupt cancels credential resolution.
Captured stdout, stderr, rendered output, errors, and test logs contain no credential
value.

## Explicit Non-Goals

v0.1.0 does not include:

- Rain or animation physics;
- path filtering, path enrichment, path globs, or virtual monorepo scopes;
- repository glob/exclusion patterns or interactive filtering/search;
- SQLite, saved scopes, persisted events, or any other database;
- historical baselines, interestingness, anomaly detection, derived signals, event
  clustering, or productivity scoring;
- Inspect or event drilldown;
- webhooks, a collector/daemon/server, or a GitHub App;
- GitHub Actions/CI, deployment, release-event, incident, coding-agent, or other
  non-GitHub-repository-event activity sources;
- a GitHub CLI extension or custom browser OAuth;
- Bubbles, unless a later implementation task demonstrates a concrete v0.1.0 need;
- Harmonica;
- generic plugin/source frameworks or abstractions built solely for roadmap phases.

## Potential Features

Taskrail v0.4.0 requires the name `Potential Features` for coverable decomposition
areas. Every area below is required v0.1.0 work; normative behavior is defined by the
requirements and acceptance scenarios above.

### CLI and Authentication Boundary

Parse and validate exact repository Scope, resolve existing local GitHub credentials,
and fail safely before TUI startup.

### GitHub Activity Source

Retrieve bounded repository event pages with cancellation, polling metadata, fixture-
driven normalization inputs, and sanitized failures.

### Event Domain and Repository Scope

Define source-independent event/repository types, normalization outcomes, exact Scope
filtering, deterministic deduplication, and ordering.

### Activity Snapshot Aggregation

Build bounded immutable-style snapshots and direct per-repository counts without
placing calculations in views.

### Application Shell and Refresh Lifecycle

Establish the Bubble Tea model, responsive shared chrome, navigation, resize handling,
asynchronous refresh scheduling, atomic updates, and loading/error/stale/recovery
state transitions.

### Overview View

Render deterministic repository activity counts, empty state, and narrow-terminal
degradation using direct observable metrics only.

### Stream View

Render and safely scroll deterministic normalized activity with accessible category
encoding, empty state, and responsive dimensions.

### Integration Documentation and Release Readiness

Wire the implemented boundaries into the standalone binary, exercise representative
end-to-end model flows without live credentials, document user setup and controls,
and pass the repository quality gate.

## Implementation Notes (Informative)

- A small auth provider interface and source interface are sufficient seams for
  deterministic tests; they are not invitations to build a plugin framework.
- The standard `net/http` client is expected to be adequate for the bounded endpoint.
- A refresh command may fetch repositories concurrently with a modest bound, but the
  application-level result remains atomic.
- Manual Stream scrolling is sufficient; Bubbles is not required by this contract.
- Source payload fixtures should contain synthetic data, not copied private activity.
