# OrgTop v0.5.0

**Status:** Draft

This specification is not ready for decomposition or implementation. The mandatory
decisions and readiness gates in "Open Decisions and Readiness Gates" must close,
and this document must be revised with their outcomes, before Taskrail tasks are
created from its Potential Features.

## Release Intent

OrgTop v0.5.0 defines Real-Time Shared Architecture for durable, organization-level
GitHub activity awareness. It introduces a centrally operated collector that receives
GitHub App and/or organization webhook deliveries, validates and normalizes them,
performs shared enrichment and baseline computation, applies authorization and
server-side scope filtering, and supplies an event-driven stream to authorized OrgTop
clients.

The release is intended to let multiple members of an organization observe a common,
fresh, explainable operating picture without every client independently polling and
enriching the same GitHub data. It preserves OrgTop's terminal-native Overview,
Stream, Rain, and Inspect product model and source-independent domain boundary.

The collector is an additional operating mode, not an implicit removal of local mode.
Existing local behavior remains available unless a later explicit product and
compatibility decision replaces it. A shared client must identify itself as `LIVE`
only while its event-driven connection and freshness evidence support that claim.
Disconnected, delayed, incomplete, or recovering data must be labeled honestly.

This Draft specifies required outcomes and responsibility boundaries. It deliberately
does not choose the client streaming protocol, durable infrastructure products,
delivery guarantees, tenancy and authorization model, retention periods, service
objectives, or deployment architecture. Those choices are release gates because they
affect product semantics, compatibility, security, privacy, and operability.

## Terminology

- **Local mode:** the existing client-owned acquisition path in which OrgTop obtains
  and processes GitHub activity without depending on a shared collector.
- **Shared mode:** an operating mode in which an OrgTop client receives authorized,
  filtered activity and shared derived data from a central collector.
- **GitHub installation:** an installed GitHub App or equivalent approved webhook
  configuration that grants the collector access to a defined organization and
  repository set.
- **Webhook delivery:** one signed GitHub HTTP delivery, including its delivery
  identifier, event type, installation context, headers required for validation, and
  payload.
- **Collector:** the centrally operated OrgTop service boundary responsible for
  webhook intake, validation, normalization, enrichment, shared state computation,
  authorization enforcement, filtering, client streaming, and operational controls.
- **Normalized event:** a source-independent OrgTop domain occurrence produced from a
  validated GitHub delivery. GitHub transport payloads do not become client or TUI
  models.
- **Enrichment:** additional GitHub-derived context needed to interpret or scope an
  event, such as changed paths or canonical repository and pull-request metadata.
- **Baseline:** shared historical activity statistics with a documented population,
  time window, freshness, and confidence state used by explainable derived signals.
- **Team scope:** a centrally defined repository and/or path scope associated with an
  authorized organizational audience. It is a visibility boundary as well as a saved
  product scope.
- **Authorized scope:** the intersection of repositories and paths a principal may
  access with the narrower scope requested by that client.
- **Server-side filtering:** enforcement by the collector that prevents events and
  derived data outside an authorized scope from being sent to a client.
- **Event-driven client stream:** a long-lived or resumable collector-to-client flow
  in which new state is delivered because events arrive, rather than through client
  polling for GitHub activity. Its protocol is an open decision.
- **Freshness watermark:** collector-supplied evidence describing how current and
  complete the presented stream is relative to accepted source input.
- **LIVE:** a client state supported by a healthy event-driven connection, current
  freshness evidence, and no known completeness degradation for the active scope.
- **DEGRADED:** a state in which activity may still be available but timeliness,
  completeness, enrichment, baseline quality, or another material property is known
  to be impaired.
- **STALE:** a state in which the client is displaying a previously valid snapshot or
  stream position without sufficiently recent successful updates.
- **Compatibility contract:** the version negotiation and behavioral rules that
  determine whether a client and collector can communicate safely or must fail with
  actionable guidance.

## Functional Requirements

### FR-001 GitHub App and Webhook Ingestion

- Shared mode requires GitHub App and/or organization webhook ingestion. Periodic
  polling of GitHub's Events API is not the primary real-time ingestion mechanism.
- The collector accepts only configured GitHub event types for installations and
  organizations it recognizes and is authorized to serve.
- Every delivery is authenticated using GitHub's documented signature mechanism
  before its payload is parsed or processed as trusted input.
- Signature verification uses the unmodified request body, rejects missing or invalid
  signatures, and supports controlled secret rotation without accepting an
  unbounded set of old secrets.
- Intake validates request size, media type, event type, delivery identifier,
  installation context, and payload structure against documented bounds. Invalid
  input receives a safe response and cannot enter normalized state.
- The collector records enough sanitized delivery outcome metadata to investigate
  rejection, duplication, delay, and processing failure without logging secrets or
  complete private payloads by default.
- Duplicate delivery identifiers and GitHub redelivery behavior are handled according
  to the gated delivery-semantics decision. Duplicate input must not silently inflate
  user-visible counts or baselines.
- Installation suspension, deletion, repository removal, permission reduction, and
  secret replacement update or revoke ingestion access promptly and visibly.
- Intake behavior under overload, dependency failure, and maintenance is explicit;
  the collector must not acknowledge durable acceptance when the selected design
  cannot honor that acknowledgement.

### FR-002 Collector Processing Boundary

- The collector owns the shared pipeline from validated GitHub delivery through
  normalization, enrichment, scope evaluation, aggregation, baseline update, derived
  signal computation, and authorized client publication.
- GitHub request, response, and webhook payload types remain inside GitHub source
  adapters. Filtering, baselines, application state, and clients consume normalized
  OrgTop domain types.
- Processing preserves source occurrence time, collector receipt time, stable source
  identity, canonical repository identity, installation or organization context, and
  available actor and entity references needed for ordering and explanation.
- Unknown but valid GitHub event types are either normalized to a documented neutral
  category or rejected as unsupported. They never acquire invented semantics.
- Processing outcomes are deterministic for the same accepted input, relevant shared
  state, and rule version. Derived values identify the rule or baseline version that
  produced them.
- The collector isolates installation and authorization contexts throughout
  processing. Data from one context cannot enter another context's scopes, baselines,
  caches, logs, metrics, or streams.
- Failure of enrichment or baseline computation does not transform an incomplete
  event into an apparently complete one. The event is delayed, omitted, or emitted
  with an explicit quality state according to a documented policy established before
  implementation.

### FR-003 Shared Enrichment

- Enrichment required by repository and path scopes is performed centrally so clients
  do not duplicate GitHub detail requests.
- Enrichment uses installation-scoped, least-privilege GitHub credentials and obeys
  GitHub rate limits, cancellation, backoff, and permission changes.
- Shared caches are keyed by all security-relevant context and cannot expose private
  repository metadata across unauthorized boundaries.
- Enriched path information preserves enough semantics to handle renames and one
  change matching multiple path scopes without implying exclusive ownership.
- An event's enrichment state is visible as complete, pending, unavailable, or failed
  where that distinction changes filtering or interpretation.
- Revocation and repository removal invalidate or make inaccessible affected cached
  enrichment according to the gated retention and privacy design.

### FR-004 Shared Baselines and Explainable Signals

- Baselines are computed once for a defined organizational, repository, or path-scope
  population and are shared consistently among clients authorized for that scope.
- Every baseline-backed value documents its measured event set, observation window,
  comparison method, minimum-data requirement, update time, and quality state.
- Scope changes, missing input, collector downtime, enrichment gaps, and rule-version
  changes invalidate or degrade affected baselines rather than producing false
  precision.
- Derived signals remain deterministic and explainable. A client can show the direct
  observations, expected value or comparison, time window, and rule version that
  justify a signal.
- The collector does not publish baseline ratios or anomaly labels when required
  history or completeness evidence is absent. Direct observable activity may remain
  available with an explicit degraded baseline state.
- Baselines and signals are operational views of engineering activity. They must not
  become individual productivity scores, employee rankings, or opaque assessments.

### FR-005 Authorized Team Scopes

- Shared mode supports centrally defined team scopes over repositories and, where
  enrichment permits, path scopes.
- Scope access is granted only to authenticated principals whose current
  authorization permits every disclosed repository or path. Team membership alone
  must not expand access beyond underlying GitHub or approved organizational policy.
- A requested scope is intersected with authorization on the server. The client
  cannot widen access by changing identifiers, filter expressions, stream resume
  positions, or protocol fields.
- Scope definitions have stable identities, human-readable names, ownership, change
  history, and validation against currently available repositories and paths.
- Changes to team membership, repository access, installation permissions, or scope
  definitions take effect within the authorization behavior selected at the readiness
  gate and terminate or narrow active streams when required.
- Empty authorized scopes are valid and reveal no names or counts from inaccessible
  scopes.
- Shared configuration is limited to current OrgTop product configuration. This
  requirement does not create a generic configuration or plugin platform.

### FR-006 Server-Side Filtering

- Repository, path, event-category, and other supported filters are evaluated by the
  collector before publication to a shared client.
- Filtering occurs after required normalization and enrichment but before per-client
  aggregation or transmission, unless an equivalent design proves that unauthorized
  data cannot be inferred or emitted.
- Filter syntax, matching semantics, cost limits, and invalid-expression behavior are
  versioned and documented. The server rejects unsupported or excessive filters
  rather than approximating them silently.
- Filtering applies consistently to events, aggregates, baseline inputs and outputs,
  signals, resume or replay data, counts, error details, and observable metadata.
- Client-side filtering may further narrow received data for presentation, but it is
  never an authorization control.
- The collector prevents filters from being used as an enumeration, timing, or
  resource-exhaustion channel beyond the risks accepted in the mandatory threat and
  privacy design.

### FR-007 Event-Driven Client Stream

- An authorized shared-mode client receives normalized events, snapshots or
  reconciliation data, freshness watermarks, degradation notices, and relevant
  shared baseline or signal updates through an event-driven stream.
- The stream protocol is not selected by this Draft. WebSocket, SSE, gRPC, and other
  options remain candidates until the protocol gate closes.
- Connection setup binds the principal, authorized scope, requested filters, client
  compatibility version, and any allowed resume position before activity is sent.
- A slow or disconnected client cannot cause unbounded collector memory growth or
  block ingestion for other clients.
- Reconnect behavior makes gaps, replay, duplication, and irrecoverable resume
  positions explicit according to the selected delivery semantics. The UI must be
  able to reconcile safely rather than treating reconnection as uninterrupted live
  service.
- Ordering information is sufficient for the client to render deterministic results
  under the selected delivery contract. Source time and receipt time are not treated
  as interchangeable.
- Heartbeats or equivalent liveness evidence cannot by themselves claim source
  completeness. Freshness evidence reflects the health of the full accepted-input to
  publication path.

### FR-008 Honest Freshness and Degraded Semantics

- `LIVE` is displayed only while the client has a healthy event-driven connection,
  current collector freshness evidence, and no known material completeness issue for
  the active scope.
- A connected stream may still be `DEGRADED`; transport connectivity is not proof
  that webhook intake, processing, enrichment, baselines, or authorization state is
  current.
- `DEGRADED` identifies the affected property and provides safe actionable context,
  such as delayed intake, incomplete enrichment, unavailable baseline, or recovery in
  progress.
- `STALE` identifies retained data whose update evidence is older than the threshold
  selected through the SLO and freshness gate. It includes last known successful
  context without presenting old data as current.
- Initial connection, authorization failure, incompatible version, empty scope,
  service unavailability, reconnecting, degraded, stale, and recovered states are
  distinguishable in every primary view.
- Recovery clears warnings only after the collector and client have established the
  required completeness or reconciliation point. Receiving one new event is not
  sufficient evidence by itself.
- Local mode retains its own honest transport label, such as `POLLING`; it does not
  inherit `LIVE` merely because shared mode exists.

### FR-009 Client and Collector Compatibility

- Shared mode has an explicit, testable compatibility contract for client protocol,
  normalized event schema, scope/filter semantics, freshness metadata, baseline and
  signal versions, and error representation.
- Client and collector negotiate or declare supported versions before activity is
  sent. Unsupported combinations fail safely with an actionable upgrade or fallback
  message.
- Additive evolution does not cause older clients to mislabel unknown event or quality
  states. Unknown required semantics trigger incompatibility rather than silent loss.
- Compatibility policy defines the supported client version window, rollout order,
  downgrade behavior, and migration handling before implementation tasks begin.
- Shared-mode configuration and credentials are distinct from local mode. Failure or
  incompatibility in shared mode does not corrupt local configuration or local data.
- Local mode remains available unless a later approved specification explicitly
  changes that product contract. Automatic fallback, if any, must be visible and
  cannot relabel polled data as live.

### FR-010 Operational Administration

- Operators can determine the health and lag of webhook intake, processing,
  enrichment, baseline computation, authorization evaluation, and client publication
  without inspecting private payload contents.
- The collector provides bounded, privacy-reviewed operational metrics, structured
  logs, and audit events for security-relevant administrative and access changes.
- Installation setup, permission review, secret rotation, suspension, removal,
  upgrade, backup or recovery where applicable, and incident response have documented
  operator procedures.
- Overload controls protect webhook intake and shared availability from expensive
  filters, reconnect storms, enrichment amplification, malformed payloads, and abusive
  clients.
- Administrative actions are authenticated, authorized, auditable, and separated
  from ordinary client capabilities.
- User-visible status distinguishes a collector outage from GitHub delivery delay,
  authorization loss, enrichment failure, baseline degradation, and client network
  failure where the system has reliable evidence to do so.

### FR-011 Mandatory Threat and Privacy Design

- A versioned threat model and privacy design are mandatory release artifacts and
  must be approved before implementation decomposition begins.
- The threat model covers at minimum webhook forgery and replay, secret theft,
  installation compromise, confused-deputy behavior, cross-scope and cross-tenant
  disclosure, filter and resume-position bypass, cache poisoning, injection,
  denial-of-service, dependency compromise, operator abuse, audit-log tampering, and
  client credential theft.
- The privacy design inventories every collected, derived, cached, streamed, logged,
  backed-up, and deleted data class, including actor identity, repository and path
  names, event content, baseline history, team membership, access decisions, and
  operational metadata.
- The design defines purpose, legal or organizational authority, minimization,
  access, retention, deletion, revocation, export, backup, incident, and data-location
  behavior for each data class.
- Secrets and credentials are never sent to clients unnecessarily, stored in source
  control, included in logs or errors, or exposed through diagnostics. Storage and
  transport protections are specified by the security gate.
- Raw private GitHub payloads are not logged by default. Debug workflows require
  explicit authorization, redaction, bounds, expiry, and auditability.
- OrgTop activity is not transmitted to third-party analytics or model providers by
  default. Any future telemetry requires a separate explicit specification and
  privacy review.
- Security and privacy acceptance tests derived from the approved designs are part of
  the release gate, not deferred operational follow-up.

## Non-Functional Requirements

### NFR-001 Security by Default

- All external and internal trust boundaries use authenticated, integrity-protected
  communication appropriate to the approved deployment design.
- Permissions follow least privilege for GitHub installations, users, teams,
  operators, services, and data stores.
- Sensitive values use a documented secret lifecycle including provisioning,
  rotation, revocation, access audit, and incident response.
- Input validation, output encoding, dependency review, and secure defaults apply at
  every public collector boundary.
- No production rollout occurs with unresolved critical or high-severity findings
  from the mandatory threat-model review unless an accountable exception process is
  explicitly approved and time-bounded.

### NFR-002 Privacy and Data Minimization

- The collector obtains and retains only data needed for specified OrgTop behavior.
- Authorization is applied to derived and aggregate data as rigorously as raw events;
  aggregation is not assumed to anonymize private activity.
- Logs and operational metrics prefer identifiers, counts, and states that do not
  disclose repository content, paths, actors, or team membership.
- Deletion and revocation behavior is verifiable across active state, caches,
  baseline material, durable storage, streams, logs, and backups according to the
  approved retention design.

### NFR-003 Reliability and Backpressure

- Every pipeline stage has explicit bounded resource behavior, cancellation, timeout,
  retry, and backpressure rules.
- Failure isolation prevents one installation, expensive scope, malformed event,
  enrichment hotspot, or slow client from exhausting shared capacity.
- Restart and recovery behavior preserves the selected delivery and freshness
  contract and does not silently present gaps as complete history.
- Capacity limits and overload behavior are observable and tested before production
  readiness.
- Numeric availability, latency, lag, recovery, and durability objectives are not set
  in this Draft; they must be selected at the SLO gate from measured product needs.

### NFR-004 Scalability and Efficiency

- Shared ingestion, enrichment, baseline computation, and publication avoid
  unnecessary duplicate GitHub calls and duplicate per-client work.
- The design states cardinality and growth assumptions for installations,
  repositories, scopes, paths, events, baseline series, filters, and connected
  clients before infrastructure is selected.
- Expensive operations have quotas or bounds tied to authorized principals and
  scopes.
- Storage and messaging products are selected from measured load and recovery needs;
  Kafka and Postgres are neither required nor prohibited by this Draft.

### NFR-005 Compatibility and Evolvability

- Wire and persisted schemas, if any, have explicit versioning and migration rules.
- Rolling or staged change does not silently mix incompatible signal rules,
  authorization semantics, or freshness meanings.
- A supported client either receives semantics it can represent honestly or receives
  an actionable incompatibility result.
- Local source, domain, application, and TUI boundaries remain usable without a
  collector-specific GitHub payload leaking into them.

### NFR-006 Observability and Auditability

- Operational telemetry measures each collector stage, queue or buffer where chosen,
  source-to-client lag, failure classes, throttling, reconnects, and authorization
  denials without high-cardinality private labels by default.
- Correlation from GitHub delivery to sanitized processing and publication outcome is
  possible for authorized operators.
- Security-relevant actions and configuration changes produce tamper-resistant audit
  evidence with access and retention governed by the privacy design.
- Product freshness labels are derived from the same reviewed health evidence used to
  operate the pipeline, not from a cosmetic client timer alone.

### NFR-007 Testability and Verification

- Automated tests use synthetic fixtures and fakes; ordinary tests do not require
  live GitHub organizations, production secrets, or external shared infrastructure.
- Contract tests cover webhook validation, normalization, authorization, filtering,
  compatibility, stream state transitions, reconnection, freshness, degradation, and
  recovery under the selected gated designs.
- Security tests cover the abuse cases identified by the threat model, including
  cross-scope disclosure and revoked-access behavior.
- Load and failure-injection tests validate selected capacity assumptions,
  backpressure, recovery, and SLOs before release.
- The repository quality gate remains mandatory for client and collector code.

## Acceptance Scenarios

These scenarios become implementation acceptance criteria only after the open gates
define their missing numeric and protocol-specific parameters.

### A-001 Valid GitHub Delivery Reaches Authorized Client

Given a configured installation, a correctly signed supported webhook delivery, an
authorized team scope, and a compatible connected client, the collector validates and
normalizes the delivery, performs required enrichment, applies server-side filtering,
and publishes the resulting event with freshness evidence. The client renders it in
the appropriate view without seeing GitHub transport payload types.

### A-002 Forged, Replayed, and Oversized Delivery

Given a missing or invalid signature, a replay or duplicate delivery under the
selected delivery policy, or a request exceeding approved bounds, the collector does
not admit unauthorized duplicate activity into shared state, baselines, or streams.
It returns safe behavior and records sanitized diagnostic evidence.

### A-003 Authorized Team Scope Isolation

Given two principals with different repository or path access, each receives only the
intersection of the requested scope and current authorization. Events, counts,
baselines, signals, scope names, errors, timing behavior, replay data, and metadata do
not disclose the other principal's inaccessible activity.

### A-004 Path Scope Uses Shared Enrichment

Given one GitHub event whose changed files match two authorized path scopes, central
enrichment is performed according to cache policy and both scopes receive correct,
explainable activity. A client outside either path authorization receives no event or
inference about it.

### A-005 Server-Side Filter Cannot Widen Access

Given a client that submits a malformed, unsupported, excessive, or deliberately
broad filter, the collector rejects or safely narrows the request according to the
versioned filter contract. Changing client fields or resume positions cannot expand
the authorized scope.

### A-006 Honest Live and Degraded Transition

Given a connected client initially satisfying all live criteria, when webhook intake,
processing, enrichment, baseline computation, authorization refresh, or publication
becomes materially impaired, the UI leaves `LIVE` and identifies `DEGRADED` or
`STALE` as defined by the approved freshness policy. It returns to `LIVE` only after
required reconciliation and health evidence are established.

### A-007 Disconnect, Resume, and Irrecoverable Gap

Given a client disconnect and reconnect, the selected delivery contract determines
whether activity is replayed, reconciled, duplicated, or declared unavailable. The
client handles permitted duplicates deterministically and visibly reports an
irrecoverable gap instead of presenting continuous live history.

### A-008 Shared Baseline Quality

Given authorized clients observing the same scope and rule version, they receive the
same baseline inputs and explainable signal outcome. When history is insufficient or
input completeness is degraded, neither client receives a false ratio or anomaly;
both receive direct activity with the correct baseline quality state.

### A-009 Access Revocation During Active Stream

Given an active stream and a repository, installation, or team authorization
revocation, the collector applies the approved revocation bound, stops disallowed
publication, prevents resume or cache access to revoked data, and records an auditable
outcome. The client receives a safe scope or authorization state without leaked
details.

### A-010 Compatibility Mismatch

Given an unsupported client and collector version combination, shared mode fails
before events are sent and provides actionable compatibility guidance. It does not
silently discard unknown required semantics or corrupt local-mode configuration.

### A-011 Slow Client and Overload Isolation

Given a slow client, reconnect storm, expensive filter, enrichment failure, or event
burst, configured bounds and backpressure protect ingestion and unrelated clients.
The affected scope receives honest lag or degradation state, and resource use remains
within the limits approved at readiness review.

### A-012 Local Mode Preservation

Given unavailable or unconfigured shared mode, a user can still invoke the supported
local mode under its existing contract unless a later specification explicitly
changes that behavior. Any explicit fallback remains labeled with local transport and
freshness semantics and never claims `LIVE` for polled activity.

### A-013 Security and Privacy Verification

Given the approved threat model and privacy inventory, automated and manual evidence
demonstrates webhook authenticity, cross-scope isolation, least privilege, secret
redaction, bounded debug access, revocation, retention and deletion behavior, audit
coverage, and absence of default third-party activity transmission.

## Explicit Non-Goals

v0.5.0 does not include:

- non-GitHub activity sources such as third-party CI systems, deployments, incidents,
  chat, project management, or coding-agent platforms;
- a generic source, collector, transformation, visualization, or plugin framework;
- opaque, unexplainable, or model-generated activity signals;
- individual productivity scores, employee rankings, performance evaluation, or
  surveillance-oriented reporting;
- replacement of GitHub as the source of organization and repository authorization;
- a browser dashboard, mobile client, or general-purpose analytics product;
- automatic retirement of local mode;
- a decision in this Draft for WebSocket, SSE, gRPC, or another stream protocol;
- a decision in this Draft for Kafka, Postgres, or any other messaging or storage
  product;
- a decision in this Draft for exact delivery semantics, tenancy, authentication and
  authorization architecture, retention periods, SLO values, or deployment topology;
- infrastructure chosen solely for hypothetical future sources or scale.

## Open Decisions and Readiness Gates

All gates below are mandatory. Their approved outcomes must be incorporated into a
revised non-Draft v0.5.0 specification with concrete acceptance criteria before this
release is decomposed into Taskrail implementation tasks. Experiments may inform a
gate, but they are not permission to implement the release architecture.

### G-001 Client Stream Protocol

Choose the event-driven client protocol only after comparing WebSocket, SSE, gRPC,
and any credible alternative against terminal client support, proxies, authentication,
resume behavior, backpressure, versioning, operations, and deployment constraints.
Define framing, connection lifecycle, liveness, limits, and failure representation.

### G-002 Delivery and Ordering Semantics

Define acceptance acknowledgement, durability boundary, duplicate handling,
ordering domains, retries, replay or reconciliation, resume identifiers, gap
detection, poison-event behavior, and recovery. Explicitly choose the promised
delivery semantics and ensure UI freshness language matches them.

### G-003 Tenancy, Identity, Authentication, and Authorization

Define the tenancy boundary, principal types, client authentication, GitHub identity
or organizational identity mapping, team membership source, operator roles, scope
authorization, revocation timing, session lifecycle, and audit requirements. Resolve
whether and how GitHub permissions are revalidated and how shared scopes are owned.

### G-004 Storage and Messaging Architecture

Use measured event rates, enrichment patterns, baseline queries, recovery needs, and
failure domains to select any durable store, cache, queue, log, or broker. Kafka and
Postgres must not be adopted by default or excluded without evidence. Define schema
versioning, backup, restore, migration, and consistency needs for selected components.

### G-005 Retention, Deletion, and Privacy Policy

Approve the data inventory and set retention and deletion behavior for raw deliveries,
normalized events, enrichment, baselines, derived signals, team and authorization
state, logs, metrics, audit records, and backups. Define installation removal,
repository revocation, user requests, legal or organizational holds, and data
location requirements.

### G-006 Service Levels and Freshness Semantics

Set measurable SLOs and error budgets for accepted-delivery processing, source-to-
client lag, stream availability, authorization propagation, enrichment, baseline
quality, and recovery. Define numeric thresholds and evidence for `LIVE`, `DEGRADED`,
and `STALE`, including treatment of GitHub-side delays the collector cannot observe
perfectly.

### G-007 Deployment and Operations Architecture

Select the deployment topology, trust and network boundaries, scaling units,
regional or single-site behavior, high availability and disaster recovery needs,
upgrade strategy, secret management, observability path, administrative interface,
and ownership/on-call model. Validate that the design can meet approved SLOs and
privacy constraints.

### G-008 Threat Model and Security Design Approval

Complete adversary and abuse-case analysis, data-flow and trust-boundary diagrams,
security controls, credential and key lifecycle, webhook replay defense, dependency
and supply-chain controls, administrative access design, incident response, and
security test plan. Obtain accountable review and resolve critical and high findings.

### G-009 Privacy Design Approval

Complete the privacy inventory, purpose and minimization review, access analysis,
retention and deletion mapping, logging and diagnostics policy, audit-data policy,
data-location decision, user and organization controls, and incident obligations.
Verify that baseline and aggregate outputs cannot bypass source authorization.

### G-010 Compatibility and Local-Mode Policy

Define client and collector version support, schema evolution, rollout and rollback,
filter and signal versioning, fallback behavior, configuration separation, and user
migration. Confirm whether local mode remains a parallel supported mode for this
release; preservation is the default until an explicit later decision says otherwise.

### G-011 Capacity and Cost Validation

Measure or credibly model organization sizes, webhook rates and bursts, enrichment
amplification, path cardinality, baseline state, connected clients, filter costs,
reconnect storms, and GitHub API limits. Establish budgets and prove bounded behavior
before selecting infrastructure and production limits.

### G-012 Product and Operational Readiness

Approve the final user workflows for setup, scope discovery, authorization errors,
freshness states, degraded operation, recovery, and local/shared mode selection.
Require passing compatibility, security, privacy, load, failure-recovery, upgrade,
operator-runbook, and end-to-end acceptance evidence before release.

## Potential Features

The headings below identify prospective coverable areas in Taskrail terminology, but
they are not currently decomposable. They become coverable implementation areas only
after every mandatory gate closes and this Draft is revised and approved.

### GitHub App and Webhook Intake

Establish approved GitHub installation, signed delivery validation, bounded intake,
redelivery handling, installation lifecycle, and safe diagnostics under the selected
delivery and deployment designs.

### Collector Domain Pipeline

Implement the source adapter, normalized event boundary, deterministic processing,
shared aggregation, quality metadata, and isolation required to turn accepted GitHub
deliveries into publishable OrgTop state.

### Shared Enrichment and Baselines

Centralize rate-limit-aware GitHub enrichment, security-scoped caching, documented
baseline computation, explainable signal versions, and explicit incomplete-data
behavior.

### Team Scopes and Authorization

Provide centrally managed repository and path scopes, current principal and team
authorization, revocation, ownership and audit history, and safe empty or denied
states under the approved identity and tenancy model.

### Server-Side Filtering

Define and enforce bounded, versioned filters consistently across events, aggregates,
replay or reconciliation, baselines, signals, counts, and metadata before any client
disclosure.

### Real-Time Client Stream

Implement the selected event-driven protocol, compatibility handshake, scope binding,
ordering, bounded flow control, reconnect and recovery behavior, and freshness
evidence without equating a connected socket with complete data.

### Shared-Mode TUI Experience

Integrate shared mode with Overview, Stream, Rain, and Inspect; render honest `LIVE`,
`DEGRADED`, and `STALE` states; expose authorized scope and baseline quality; and
preserve local-mode transport semantics and responsive behavior.

### Operational Hardening

Deliver capacity controls, isolation, observability, auditability, administration,
secret rotation, upgrades, recovery, runbooks, and failure-injection evidence needed
to operate the approved architecture.

### Security and Privacy Controls

Implement and verify the approved threat-model mitigations, least-privilege access,
cross-scope isolation, data minimization, retention and deletion, safe diagnostics,
incident controls, and privacy-reviewed telemetry boundaries.

### Compatibility and Release Readiness

Establish schema and client compatibility, migration and rollback behavior,
local/shared configuration separation, end-to-end contract tests, security and privacy
evidence, performance validation, documentation, and release gates.

## Implementation Notes (Informative)

- A useful conceptual flow is `GitHub webhook -> validate -> normalize -> enrich ->
  authorize/filter -> aggregate/baseline/signal -> event-driven stream -> OrgTop
  client`. This flow defines responsibilities, not processes, services, queues, or
  deployment units.
- Keep GitHub transport types in the source adapter and collector protocol types at a
  compatibility boundary. The existing OrgTop domain and TUI should consume
  source-independent models.
- Prefer one normalized semantic contract across local and shared modes where the
  underlying evidence is equivalent. Preserve mode-specific freshness and failure
  facts instead of forcing superficial uniformity.
- Baseline calculation may require durable history, but the retained data and storage
  mechanism must follow the approved privacy, retention, scale, and recovery gates.
- Team scopes are security-sensitive shared objects. Treat their names, membership,
  repository lists, path patterns, and activity aggregates as potentially private.
- Server-side filtering should reduce disclosure and bandwidth; it must not be used to
  justify processing unauthorized raw data in a broader context than the approved
  tenancy design allows.
- Webhook acknowledgement, queueing, persistence, and client replay form one delivery
  contract. Do not implement them independently before G-002 closes.
- `LIVE` should be derived from end-to-end evidence including accepted source input,
  processing progress, authorization currency, and stream publication. A heartbeat
  can support connection health but cannot establish source completeness.
- Avoid scaffolding generic source plugins or non-GitHub event adapters. v0.5.0 is a
  GitHub shared-architecture release.
- No built-in LLM or external model provider is needed. Shared signals remain
  deterministic, versioned, and explainable.
